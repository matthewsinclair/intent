## Summary

`intent doctor` reports EVERY undeclared issue's absent view as a missing generated view. On this estate that is 284 findings out of 285, at rc=1, on a tree `intent organize --apply` had just made correct -- and doctor is a preflight gate, so it refuses the release on a healthy estate.

## What it is

`views::skew`'s absent-view arm asked `owning_thread` and nothing else:

```rust
let dehydrated =
  owning_thread(project, &view.path, canon).is_some_and(|owner| !realised.declares(&owner));
```

`owning_thread` answers `None` for `intent/issues/<nnnn>.md`, and `None` inside `is_some_and` is `false` -- which reads as *this view's owner is declared*, so the finding fires for every issue view in the estate. The manifest is never consulted for an issue at all.

**The same shape as the projection defect fixed at 49a00fb80, in the sibling reader**: a thread-shaped question asked of an issue path, answered `None`, and `None` making the whole condition false in the unsafe direction.

## Why no fixture held it

Every arm that reaches an issue does so through `issues add`, which DECLARES the issue. No fixture built that way can hold an undeclared issue, and all 284 of this estate's were undeclared. It was found by the estate, immediately after `organize --apply` removed the 284 views the WP-01 projection fix had wrongly materialised.

## Fix

One predicate, `views::dehydrated_owner`, asking the manifest for either artefact kind -- the thread by id, the issue by `ISSUE:<nnnn>` through `intentfiles::declared_key` -- and `false` for a project-level view that belongs to no artefact. Arm: `view_skew_check::an_issues_absent_view_is_silent_only_where_the_manifest_says_undeclared`, both halves against one fixture, because a blanket silence for issue views passes half of it.
