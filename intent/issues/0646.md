## Measured (vc, ic and utilz-ic, 2026-10-25)

- `native/macos/Intent/Intent/Masthead/masthead.yaml` uses arca_swift's ArcaMasthead as Gtools' and menuz's do: `heading: "{name} {version}"`, `subheading: "{commit} · {kind}"`. The row is right; its input is wrong. `VersionService.parse` (Services/VersionService.swift near line 91) still matches the pre-ST0087 line `intent <version> (<commit>) <kind>`; ST0087 WP-01 (976fad577, in the pair since 14:09Z) changed the line to `intent <version> (<tree>, <sha12>[+dirty]) at <root> <provenance>`, the match fails, and the parser's fallback returns the whole line as `{version}` with commit and kind nil, so the heading shows the raw line and the subheading collapses. The design recorded this reader and moved it to WP-03's Swift half; vc accepted the gap on 2026-10-25 as "the dev Intent.app shows the degraded masthead between the build all and ic's landing", which hv has now rejected by looking at it.
- The ` at <root>` and trailing `dev` are the contract's T4 line (devbin docs/dev-opt-brew.md v0.4, agreed by the four estates' nodes as SAME on 2026-10-24, not ruled by hv in those words); the same line is live in Utilz and devbin. The app was never meant to show them: masthead.yaml shows version, commit and kind only.
- The page's data call is `/op`, which requires `Authorization: Bearer <token>`; `intent estate status --browser` opens the page with the token in the URL fragment, which shell.html reads and stores; the app's Open item opens the bare URL, so every fetch is refused and the page shows the refusal as its content. Opening the bare URL in a browser by hand meets the same.

## The fix, specified (vc, 2026-10-25)

(a) `VersionService.parse` reads the contract's line: version, tree, sha12 (shown as the first eight), optional `+dirty`, root, optional provenance word, and still the old shapes; the masthead shows `Intent 3.2.6` over `397d7568 · dev` exactly as masthead.yaml says and as menuz's row reads; the root is parsed and never shown. This is the parser already written in ST0087 WP-03's Swift draft, split out as its own bank with its four arms (AT-03.4), so it lands before the rest of WP-03. Its judge is `bin/devbin macos app-test` (IntentTests) plus the swift critic; the arms cover the new line, its +dirty form, the brew form and the `(dev, unknown)` form.
(b) The intentd flyout's Open item runs the one URL builder instead of opening a bare URL: it execs `intent estate status --browser` through the `intent` it already resolves, so the token travels in the fragment exactly as from the command line and there is one implementation of how the page is opened. An arm drives the item's command.
(c) shell.html's no-token state is a sentence, not a refusal dump: it says the page is opened with `intent estate status --browser` (or Intent.app's Open) because its data needs the daemon's token, and shows no Bearer text; an arm in intentd's tests asserts the page's text with no token present.
(d) After the landing, ic builds the app and installs it to /Applications by the route of 2026-10-24's build, relaunches it, and tells hv; the dev app then shows the row as every other menubar app does. The CLI's own line is not changed by this issue: whether `intent --version` keeps ` at <root>` and the provenance word is a contract question vc has put to hv separately.
