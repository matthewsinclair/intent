**THE STORE'S WRITE-AHEAD LOG FILE NEVER SHRINKS: IT KEEPS THE HIGH-WATER MARK OF THE LARGEST BURST IT HAS TAKEN.** On rhadamanth on 2026-11-17, Intent's own `intent/.cache/intent.db-wal` was 296,471,112 bytes (71,959 frames of 4 KiB) beside a 244 MB `intent.db`. hv's watchout 11 records a 559 MB WAL truncated by hand on 2026-09-10, and hv ruled on 2026-11-17 (hv decision 59) that it is fixed in the next release.

**The mechanism, read from the files without writing to the store** (cc, 2026-11-17, at Intent 0640cd65a with brew 3.3.3):

- The WAL-index header in `intent.db-shm` holds `mxFrame` 220 and `nBackfill` 0: the log held 220 live frames, none checkpointed yet.
- Its reader marks hold 220 in `aReadMark[1]`, the end of the log, and the rest unused: no reader was pinned behind the end.
- The WAL header's checkpoint sequence is 12,026: the log had been restarted from its first frame that many times.

So checkpoints are not being starved. The log is checkpointed and restarted as SQLite's default autocheckpoint (1000 pages) intends, and each restart reuses the file from its start. The size is a high-water mark: some past burst grew the file to 71,959 frames, either a large transaction or a spell when a reader held an old snapshot, and nothing has cut it back since. SQLite truncates a WAL file only to a connection's `journal_size_limit`, at the first commit after a restart, or on a `wal_checkpoint(TRUNCATE)`, and deletes it when the last connection closes cleanly. `Store::open` (`native/rust/crates/intentsvcs/src/store.rs`), the one writable open, sets `journal_mode=WAL` and `busy_timeout` and no `journal_size_limit`, and nothing in the Rust tree checkpoints. The last-close delete seldom comes while a long-lived intentd and other processes hold the store open, and watchout 11 records that a SIGTERM'd daemon does not checkpoint.

**The fix.** `Store::open` sets `journal_size_limit` to 16 MiB, four times the log an autocheckpoint lets gather at this store's 4 KiB pages. SQLite then cuts the file back to that at the first commit after any restart, so a burst leaves no more than that on disk once the next write restarts the log. A checkpoint at a clean shutdown is not needed for the bound: the next restart after any burst cuts the file back whether or not the daemon stopped cleanly. Owner: cc. It rides Intent's next release with 0696 and 0698, in one whole `bin/devbin gate rust` run.
