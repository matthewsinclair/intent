## What

`st dehydrate`, `st renumber` and `issues renumber` remove files from disk, and each leaves the store's `file_index` row for every path it removed. The drive reads `file_index` (path, sha256, updated_at) through `?immutable=1` before and after each verb, in a scratch git project with a commit between verbs, and counts a removed path as recorded only when its row is gone after the verb.

- `st dehydrate ST0001` removed `intent/st/ST0001/acceptance.md` and `intent/st/ST0001/info.md`. Both rows were still there afterwards.
- `st renumber ST0001 ST0002` removed `intent/.canon/st/ST0001.json`. Its row was still there afterwards. The new path's row was written.
- `issues renumber 0001 0002` removed `intent/.canon/issues/0001.json` and `intent/issues/0001.md`. Both rows were still there afterwards.

The instrument's positive control: in the same run, `issues add` wrote rows for its new files. So the drive sees rows the verbs do write, and a row it reports left behind really is there. `.intentfiles` never gets a row, even in the control, so it is outside what this measurement can see and is not part of this issue.

## Why it matters

`file_index` is what the store believes is on disk. A row for a file that is gone is a claim the disk contradicts. What reads that belief (organize's observe step, which takes the previous index, and doctor's view-skew checks) has not been measured against these leftover rows. That consequence is the first thing to measure, before any fix.

## Expected

A verb that removes a file removes that file's `file_index` row in the same step, or the index records the path as absent. Which of the two is the implementer's to propose against the readers of the row.

## What an implementer owes

- The drive re-run, showing each removed path's row gone after its verb, with the control still recording `issues add`'s rows.
- A measurement of what a leftover row does to `organize` and `doctor` today, taken at the base before the fix.
- One arm per verb family, red at the base.

## The fix, specified (vc, 2026-10-25)

Measure first, at the base and in dc's drive project after `st dehydrate`: what `organize --apply` (its observe step takes the previous index) and `doctor` read or report with the leftover rows present. That is the consequence this issue asks for, recorded before any code, and where it shows it is the arm's red at the base.

The fix: the store gains one function beside `upsert_index_row` that deletes the `file_index` rows for named paths, and every verb that removes a tracked file calls it where the file is removed, in intentsvcs (dehydrate, `st renumber`, `issues renumber`), never in render.rs. The `removed:` set the one printer has carried since issue 0632 is the witness: for each verb, the rows deleted are exactly the paths it printed as removed. `replace_file_index` stays the sync scan's whole-set writer, untouched. `.intentfiles` stays outside, as the issue says.
