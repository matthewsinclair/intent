## What

In a linked git worktree, Intent's post-merge, post-rewrite and branch-switch post-checkout carriers run `intent sync --apply` against the worktree's OWN store, and that store can be older than main. In Molt, a rebase in a worktree re-rendered peers' whiteboard views backwards: molt-cc's board showed an old name and focus. The re-rendered views were then swept into a commit made from the worktree.

Molt's workaround: run `git checkout -- intent/whiteboard` after creating a worktree, and never commit `intent/` from one.

## Relation to 0483

Issue 0483 (closed 2026-09-19) stopped the carrier on a fresh worktree's first checkout, when the previous HEAD is the null id. Its closing note keeps the rest as it was: "a branch switch inside an existing checkout still syncs, and post-merge and post-rewrite are unchanged". This report is that remainder, seen in use.

## Not yet measured here

Reported by molt-dc from molt-vc's board (Molt, 2026-10-22), on Intent 3.2.4. vc has NOT reproduced it in Intent. The lane that takes this measures first:

- which carrier fired;
- what store the worktree held, and from which commit it was built;
- what the sync wrote, and in which direction.

Only then does it choose between skipping the carriers in a linked worktree, building the worktree's store from the tree it now stands on, and refusing to write views backwards.

## Expected

A sync inside a linked worktree never writes a view older than the commit the worktree stands on. Nothing a hook writes in a worktree can be swept into a commit as a regression.

## A lead from dc, 2026-10-22

This is a lead, not a finding. It reproduces nothing from Molt, and Molt's own sequence was not driven. dc drove two of the three carriers in clean scratch projects while weighing 0614 for the v3.2.5 known-defects page, on three pairs: the dev build at dcd9057d4, the released 3.2.4 at f89b8285b, and build all #2's pair at 8bef2bb7a, which carries 0619's fix and is in 3.2.5. On each pair the control built two projects with nodes aa and bb. In each, a linked worktree was added and its store warmed cold, by a first `intent` read, from the commit the worktree was created on; then on main aa was renamed (`wb register --correct`) and given a focus (`wb pickup --focus`), and the worktree took main by a rebase in one project and by a merge in the other. The control is `refs/bank/dc/325kd/e_worktree_carriers.sh`, with its logs beside it: `control-dcd9057d4.log`, `control-324keg.log` and `control-final.log`.

What the runs showed:

- No carrier rewrote a file on any pair: after every carrier, `git status --short` in the worktree was empty and `git diff -- intent/whiteboard` showed nothing.
- The rebase's only carrier line came from post-checkout, and post-rewrite printed none. The merge's came from post-merge.
- On the two pre-fix pairs (dcd9057d4 and 3.2.4), each carrier took the event file into the worktree's store but not the board: `intent (post-checkout): took 1 event file(s) from the files into the store`, and the same line from post-merge. Afterwards the worktree's files carried main's board, while its store still answered `Node A`, `paused` and an empty focus. That matches 0619's mechanism: a store warmed cold kept no index row for a board's files, so a change git brought to them did not count as moved.
- On 8bef2bb7a's pair, each carrier took the board as well (`took 1 change(s) from the files into the store: board aa; and 1 event file(s)`), and the worktree's store answered main's name and focus.

The candidate: on 3.2.4 a carrier leaves a worktree whose files are newer than its store, and writes nothing itself. A later write that renders those views from the store would put the older board over the newer files, which is the backwards render reported here, and the next commit from the worktree would carry it. Which verb renders a peer's board from a stale store was not measured, so the candidate is unconfirmed.

Not driven: the branch-switch post-checkout carrier; any write in the worktree after a carrier; and the released 3.2.5 pair at 2e0e9215d, which carries the same fix.

What would settle it: on the 3.2.4 pair, the same setup, then one write in the worktree after the carrier that renders aa's board, then `git status --short` and `git diff -- intent/whiteboard`. The same steps on 3.2.5 show whether 0619's fix removes the stale store the candidate needs.
