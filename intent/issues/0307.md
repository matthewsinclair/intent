**Two doors write the same canon extract and disagree on a trailing newline, so the committed file is not the output of the writer that made it.**

`intent/.canon/st/ST0069.json` carries `objective` and `context` with their trailing newline intact, written by the projection a mutation runs -- the `wp done` that wrote the committed file. An UNSCOPED `intent sync --to-disk` rewrites the same file from the same store with that trailing newline normalised off both fields.

So one store yields two different canon extracts depending on which door wrote it, and neither is marked as the canonical rendering. The committed bytes are the mutation projection's; a node that runs an unscoped to-disk on a clean tree finds `intent/.canon/st/ST0069.json` dirty with no model change behind it.

**Reproduction, as reported:** on a clean tree, run an unscoped `intent sync --to-disk`; `git status` then shows `intent/.canon/st/ST0069.json` modified, the diff confined to the trailing newline on `objective` and `context`.

**Why it is worth fixing rather than living with.** The canon commit guard compares the bytes in the index against the bytes the store would write, so a divergence between two writers of the same file is exactly the input that makes a correct tree look wrong. A node meeting it will either commit a byte change carrying no model change, or spend the afternoon looking for the model change that is not there.
