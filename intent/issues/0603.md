## What was seen

Reported by utilz-vc, 2026-10-16, measured on Intent 3.2.3 dev (701c4d98) in another estate's project that declared `lua` that day for a Hammerspoon module (its `tmp/check/20261016-0750.CRITIC.out`): the headless critic, in that project's `check all` and in its commit gate, reports

```
lua -- 0 of 7 rule(s) ASKED of this run; 0 armed in total ... 7 declared unanswerable
```

The report is honest and loud, so nothing is hidden. But the lua pack gates nothing headlessly: every one of its seven rules is declared unanswerable, so only the `critic-lua` agent ever reviews Lua, and a commit touching Lua passes the gate on no rule at all.

## What was expected

A language pack a project can declare carries at least the rules a commit gate can ask, armed with a greppable proxy or a named tool, as the critic contract (`intent/docs/critics.md`) provides. A pack whose every rule is unanswerable headlessly is a gap in the pack, not in the runner.

## The fix, as vc would shape it

Arm the two rules that carry most of a gate's value for Lua with a Detection heuristic: `IN-LU-CODE-001` (local over global: an assignment to a bare identifier at chunk level that is not `local`, a grep with a short deny list) and `IN-LU-CODE-005` (module return: a file under a module path whose last non-blank line is not `return <name>`). Others follow as proxies become clear; a rule with no honest proxy stays unanswerable and says so. Size S per rule, in the rule library (`intent/docs/rules.md` is the authoring guide), with the pack's own bats arm that a planted violation is found and a clean fixture is not.

## Where it belongs
