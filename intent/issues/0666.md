**`intent daemon start --at-login` PRINTS `ok:` AND ENROLS NOTHING WHEN A DAEMON IS ALREADY RUNNING.**

**Measured by rhadamanth-sysadm on rhadamanth on 2026-10-31, and relayed by devbin-vc.** intentd 3.2.8 (b14e274) was running as pid 50369, `/opt/homebrew/bin/intentd`, answering at `~/.local/state/intent/run/intentd.sock`. No LaunchAgent was in `~/Library/LaunchAgents`, and none was in `launchctl`'s `gui/501`. `intent daemon start --at-login` printed `ok: intentd is already running (pid 50369)` and exited 0. Afterwards there was still no LaunchAgent and no `launchctl` entry, and `intent daemon status` was unchanged. rhadamanth stays un-enrolled rather than stop the daemon that every session on it is using.

**The mechanism, read by intent-vc in Intent's tree at d664d44fa.** `daemon_start` (`native/rust/crates/intent-cli/src/render.rs:12016`) runs only the off-macOS refusal ahead of its already-running check. It then returns at `render.rs:12038-12040` with `ok: intentd is already running (pid N)`, before it reaches the `--at-login` branch that writes and loads the plist (`launchagent::write_plist` and `launchagent::load`, `render.rs:12056-12057`). So with a daemon up, `start --at-login` behaves as a plain `start`. It reports success for a request whose enrolment half never ran, and its success line says nothing about enrolment.

**The mirror verb already gets this right.** `daemon_stop` with `--at-login` (`render.rs:12184-12204`) unloads and removes the plist whatever is running, then stops a daemon that was started by hand. So `stop --at-login` reaches its postcondition from either state, and `start --at-login` does not.

**What a fix has to decide**, which is the reporter's to rule:

- Write the plist whether or not a daemon is running, and leave the running one answering. This has to handle the race that the enrolled path's own comment names (`render.rs:12051-12054`): the plist carries `RunAtLoad`, so loading it starts a second daemon that races the running one for the socket.
- Or hand the running daemon over to `launchd`: stop it, then enrol.
- Or refuse, naming the running pid and the stop-then-enrol remedy, so the verb never says `ok:` for an enrolment it did not make.

On Linux the `brew services` route is unaffected, because enrolment is refused there before this check.

**Ruled by hv on 2026-11-01, by selection in the TUI in devbin-vc's window, relayed by devbin-vc (received by 07:02Z on intent-vc's date -u). hv chose the third option, refuse, which intent-vc recommended.** With a daemon running, `intent daemon start --at-login` refuses, naming the running pid and the stop-then-enrol remedy, `intent daemon stop` and then `intent daemon start --at-login`. It never says `ok:` for an enrolment it did not make, and it never restarts the daemon that every session on the machine uses.

**vc's reading under hv's ruling, 2026-11-01, settling two cases the ruling's text does not separate (cc asked; the reading is vc's, not hv's).** With a daemon running and a current plist (`launchagent::is_enrolled` true, `launchagent::is_stale` false), the postcondition already holds, so `start --at-login` says `ok:` naming both facts, enrolled at login and running (pid N), writes nothing and exits 0. With a daemon running and a stale plist, it rewrites the plist through the same `launchagent::write_plist` that the enrol path and intentd's boot-time heal (`heal_the_policy_stamp`) use, loads nothing, leaves the daemon answering, and says `ok:` naming the rewrite. That is a repair of an existing enrolment, which `is_stale`'s own doctrine separates from making a new one, and intentd's heal-failure remedy already names `intent daemon start --at-login` as the command that rewrites a stale plist while the daemon runs. Only a missing plist, which is a new enrolment, refuses as ruled.
