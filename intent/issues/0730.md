Found by critic-rust on ST0096 WP-02 (its R11), and left after WP-02 as this issue on vc's word, so it rides this release (hv decision 69). Owner: ic.

`intentsvcs::gitstate` answers "does git track this path" two ways:

- `is_tracked(root, path)` takes one path, and reads a git that cannot be asked as no work tree (`is_work_tree`, the bool reading of `work_tree`), and so as untracked. `facade::store_tracking` (issue 0551's store advisory and the upgrade's report), `canon.rs` and `facade::remove_event_log_leftover` (issue 0459) ask it.
- `tracked_matching(root, patterns)` takes patterns, asks the three-way `work_tree`, and returns a git it could not ask as an error. The aggregate views (ST0096 WP-02) ask it.

So one question has two answers for a git that cannot be asked. `store_tracking` says the store is untracked where doctor says of the aggregate views that git was not asked. WP-02 gave doctor's two "git was not asked" advisories one builder, and asks the aggregate question once per run, but the two git questions remain.

Fix: make `is_tracked` the one-path reading of the same question. One way is `tracked_matching` over the path as a `:(literal)` pathspec, so a path holding glob characters is never read as a glob. Its callers then take the error where they now take `false`, and `StoreTracking::Unasked` becomes that error.
