**Seen.** At 16:08Z on 2026-09-21, vc ran `intent sync --to-disk` in the Intent checkout while intentd was watching this tree, and it refused. The refusal gave the two-families reason: "`sync` and `ingest` are the two families that would genuinely run twice against it". Its remedy was "stop the daemon process and run again".

**Expected.** A store-to-disk projection runs beside the daemon, as every mutating verb's projection did all that afternoon (`wb add`, `wb archive`, `issues close`). Such a projection lands only the bytes that differ and records them as landed, so the daemon does not read them back as an edit.

**Why this looks wrong, from a source READ, not a drive.** Nobody has yet run `--to-disk` beside a live daemon to show that it is harmless.

- The refusal is in the CLI's one store door, not the library. `engine()` at `intent-cli/src/render.rs:604` refuses a `StoreNeed::Exclusive` open when `watching_this_project` answers yes.
- Only two call sites open `Exclusive`: `sync --to-disk` at `render.rs:1237` and `sync --to-store` at `render.rs:1247`. `sync --apply` opens `Shared`, and the guide calls it safe beside a running daemon.
- `Facade::sync_to_disk` at `intentsvcs/src/facade.rs:8159` has no daemon check of its own. It loads canon from the store, projects the views, commits only the paths whose bytes differ, and records what landed. It runs no ingest walk and watches nothing.
- The hazard the refusal names, two engines both ingesting one tree, is real for `--to-store`, which replaces the store from the extract and so races the daemon's ingest. The read finds no such hazard for `--to-disk`.

**Candidate fix, as a candidate.** Open `sync --to-disk` as `Shared` and keep `sync --to-store` `Exclusive`. Add a test that drives `--to-disk` beside a daemon watching the tree and checks that the daemon does not re-ingest what landed.

**One line in the same place.** The `Exclusive` doc comment at `render.rs:168` still says the predicate "fires on any answering daemon, not on one watching THIS project". The code already narrows to this project, so the comment is stale.

**What this does NOT block.** This refusal blocks nothing that was waiting on it. The seven closed-issue views still carrying the 3.1.0 footer were never waiting on `sync --to-disk`. cc measured, and vc confirmed, that a closed issue's view leaves the disk through `intent organize --apply`, which today's closes skipped. So the refresh path was never the door for them. The refusal has a remedy, which is to stop the daemon and run again, hence severity low.
