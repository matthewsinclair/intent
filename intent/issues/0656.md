## What happens

0654 (landed at 44fd5b190) tells a unit's author to run `git worktree remove <path>` once the checks pass, and never to use `--force`. A unit is banked from its worktree's index, so a landed unit's worktree still holds its bank staged, and git's clean check refuses that.

Measured on 2026-10-26 in a scratch repository: a worktree with one staged change and an ignored build directory gave "fatal: '../wt' contains modified or untracked files, use --force to delete it", rc 128. So the step refuses every normal banked worktree.

gtools-vc's question about mutant worktrees found it. The step also leaves a mutant on disk: a mutant holds a planted defect, so its index tree is never its base with its landed banks applied. No node has acted on the text, because every removal waits on hv's Spotlight exclusion.

## Expected

- Once the checks pass, the staged banks are the worktree's one difference from its base, and main holds them. So `git -C <path> reset --hard` drops them, and a plain `git worktree remove <path>` removes the tree with its ignored build target.
- The same scratch repository measured both halves. After the reset, the plain remove succeeded and took the ignored directory with it. With an untracked file present after the reset, it refused again. So `--force` stays out, and an untracked file is still a finding.
- gtools-vc's rule for mutants: a mutant worktree, which is a bank plus a planted defect kept for a red run, goes with its unit's worktree once that red run's END is on the record. The same checks apply, with the planted defect as its one expected difference.
- 0654's 3.2.7 CHANGELOG line says the same.
