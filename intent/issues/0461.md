An authored file named `info.md` below a thread's view depth cannot be carried. The two answers Intent gives to "what is this file" disagree about it, and the v2 prune then withholds it forever with a line that names no remedy.

**The disagreement, read from the code at ba4c37b57:**

- `Project::classify` (project.rs) calls `info.md` a generated view only at the thread root and at `WP/<NN>/info.md`, depth 3. Its own comment says a deeper `info.md` "is neither, and matching on the bare name would take an author's file and call it ours". So `WP/_superseded/01/info.md`, at depth 4, is `ThreadFile::Attachment`.
- `address::parse` (address.rs) refuses any path segment in `VIEW_NAMES` (`info.md`, `acceptance.md`, `todo.md`, `steel_threads.md`, `info`, `acceptance`) at any depth, with `ViewAddressed`.
- `attachment_name` round-trips every attachment path through `address::parse`, so the name `WP/_superseded/01/info.md` is `NotAddressable`. The ingest leaves the file unheld, and `intent st attach` refuses the name.
- The v2 prune's `bucket_verdict` (legacy.rs) classifies the file as an attachment, finds no attachment of that name in the thread's canon, and withholds it with "`<ID>` carries no attachment `<name>`, so its content is on disk and nowhere else". Nothing can ever put that attachment in canon, so the file is withheld on every run.

**Why no test caught it:** `generated_views_are_unaddressable.rs` asserts one direction: every basename `classify` calls a generated view is refused by `parse`. Its module doc says "The reverse is not required and is not asserted". This defect is the reverse: a name `parse` refuses that `classify` hands to the attachment path.

**Where it bit:** Lamplight, 2026-09-18. ST0037's `WP/_superseded/{01..08,MVP}/info.md` are nine authored files, 16427 bytes, withheld by the prune with no way to carry them. On vc's ruling, ic repairs them in Lamplight by renaming each to `spec.md` and attaching it with `intent st attach ST0037`. Nothing Intent printed named that remedy.

**The ask:**

1. A decision on which answer moves. Either `parse` refuses a view basename only at a view's depth, so a deep `info.md` is addressable as an attachment, or `classify` treats a view basename as unownable at every depth. Then the file is refused as an attachment by name, and the refusal says so rather than calling the file the author's.
2. Whichever answer moves, the withheld line should name the remedy when the reason is an unaddressable name: rename the file, then `intent st attach <ID> <new name> --from <file>`. Today it says only that the content is on disk and nowhere else.
3. The unaddressable test should assert the direction it now skips, so the two answers cannot drift apart again unnoticed.

Severity low: a rename repairs each file by hand, and the prune withholds rather than deletes, so nothing is lost.
