Reported on 2026-09-23 from gyges, hv's test bed for running Intent from `brew install matthewsinclair/intent/intent` with no dev tree. The evidence below was read on the machine and in Intent's source. Nobody has reproduced it end to end, because gyges has not been upgraded yet.

Seen:

- `~/.local/share/intent/home` on gyges reads `/opt/homebrew/Cellar/intent/3.2.0/libexec`, which is the versioned keg path.
- `install::resolve` (`native/rust/crates/intentsvcs/src/install.rs:147`) deliberately canonicalises the executable before walking up to the install root: Homebrew's `bin/intent` is a link into the Cellar, and a walk up from the link climbs the wrong tree. So on a brew install, the root it finds, and the root `intent bootstrap` records, is always `<prefix>/Cellar/intent/<version>/libexec`.
- `brew upgrade` runs `brew cleanup` on the upgraded formula unless `HOMEBREW_NO_INSTALL_CLEANUP` is set (it is unset on gyges), and the cleanup deletes the previous keg.
- The project shim refuses a pointer whose target has no `lib/templates` (`lib/templates/hooks/pre-commit-shim.sh:119`), with exit 1 and the remedy "run `intent bootstrap`". So after an upgrade, every commit in a gated project is refused.
- `intent bootstrap` is the pointer's only writer (`render.rs` `bootstrap` calls `bootstrap::run`, which calls `install::publish_home`), so nothing repoints it after an upgrade.
- The formula's caveat (`bin/.devbin/cmd/macos`, `def caveats`) says to run `intent bootstrap` only "if that file does not exist yet". After an upgrade the file does exist, and it names a deleted keg.
- A stable path exists: `<prefix>/opt/intent` links to whichever keg is current.

Expected: a brew upgrade leaves the gate working. The pointer names a path that survives upgrades. A machine whose pointer already names a deleted keg is told what to run when it upgrades, not at its next refused commit. That covers every brew install of 3.2.0 or earlier when it upgrades to 3.2.1.

The same pattern in one more place, read from source but not driven: intentd's LaunchAgent plist records `current_exe()` (`native/rust/crates/intentd/src/main.rs:1062`). Whether that path is the `bin` link or the Cellar keg depends on how intentd was launched, since macOS's `_NSGetExecutablePath` can return a link. It also regenerates itself when a new intentd starts, and the CLI starts its sibling intentd. So at worst it misses one login until the next `intent` command. The builder confirms which case holds; it is not a second fix unless the drive says so.

Ruling (vc under hv's pen, 2026-09-23): this goes in 3.2.1, because the 3.2.1 cut is the first upgrade that triggers it. Two parts:

1. `intent bootstrap` records the stable path when one resolves to the same root. Where the canonical root sits under `<prefix>/Cellar/intent/<version>/`, and `<prefix>/opt/intent` resolves to that same keg, the pointer records `<prefix>/opt/intent/libexec`. The walk still starts from the canonical executable, and the resolution stays a pure function tested against a planted Cellar-and-opt tree. A pointer naming the stable path reads as Unchanged after an upgrade.
2. The formula's caveat also tells a machine whose pointer names an Intent version that is no longer installed to run `intent bootstrap` once. The caveat is the only lever that reaches a 3.2.0 install at its upgrade to 3.2.1, because no 3.2.1 code runs before the pointer breaks. It stays conditional, so it never moves a machine whose pointer names a live source checkout.

Behaviours, one line each:

- On a planted brew layout, the pointer `intent bootstrap` writes is `<prefix>/opt/intent/libexec`.
- On that layout, after the keg is replaced by a newer version, the shim finds the gate and `intent bootstrap` reports the pointer Unchanged.
- A root outside any Cellar is recorded exactly as it is today.
- The caveat names the upgrade case, and `int macos formula` renders it.
