Owner: intent-cc. Target: 3.5.x. Found by intent-dc during the 3.5.0 rehearsal; vc's ruling: not a regression from 3.4.0, so it did not hold the cut.

## What happens

`intent st attach <ID> <path> --from <file>` on a thread whose directory is realised records the attachment in the store and canon, but writes no file into the thread's directory when that path is absent. The file appears only when `intent organize --apply` or `intent st hydrate` realises it. Until then `intent doctor` reports nothing, and only Intent's own repo-local canon_commit_check notices (as ABSENT).

## Why

`Facade::place_attachment` hands the realised file to `replace_realised` (`native/rust/crates/intentsvcs/src/facade.rs`), which overwrites an existing file (issue 0715) and returns early on NotFound by design, as its doc comment says. 3.4.0 wrote no file at all, so a new attachment behaves as it did in 3.4.0, and only the overwrite case changed.

## The fix

`place_attachment` writes the file when the thread is realised and the path is absent. How it does so (intent-cc's refinements, accepted by intent-vc after the cut):

- **Realised is the record's answer, not the disk's.** The test is the thread record's own `realised` field (`intentfiles::declared_by_records` reads `t.realised`), which `place_attachment` already holds as `holder`. The store is the truth: a directory left by a hand `mkdir` or a half dehydrate is not a reason to write into it, and an unrealised thread keeps nothing on disk.
- **A realised thread with no directory yet gets one, as `place_attachment`'s own realisation of this one file**: the file's parent directories are created for it, and nothing else. It does not render the thread's views or reconcile the tree, which stay `st hydrate`'s and `organize --apply`'s, so this is no second copy of hydrate.
- **The rollback tells a created file from a replaced one.** `replace_realised` returns `Option<old bytes>` today, and the store-failure arm writes the old bytes back. It becomes an enum (`Untouched`, `Replaced(old)`, `Created`), and for `Created` the failure arm removes the file it wrote, with its own error when that removal fails, beside `RealisedAttachmentNotRestored`.

## Proof

One arm: on a realised thread, `st attach` of a new path writes the file with the attached bytes, prints it under `wrote:`, and a commit of what the verb printed passes canon_commit_check with no `organize --apply` in between. The store-failure path is the one the issue 0715 tests already drive for the overwrite; for a created file it must leave no file behind.
