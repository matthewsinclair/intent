Owner: intent-cc. Target: 3.5.x. Found by intent-dc during the 3.5.0 rehearsal; vc's ruling: not a regression from 3.4.0, so it did not hold the cut.

## What happens

`intent st attach <ID> <path> --from <file>` on a thread whose directory is realised records the attachment in the store and canon, but writes no file into the thread's directory when that path is absent. The file appears only when `intent organize --apply` or `intent st hydrate` realises it. Until then `intent doctor` reports nothing, and only Intent's own repo-local canon_commit_check notices (as ABSENT).

## Why

`Facade::place_attachment` hands the realised file to `replace_realised` (`native/rust/crates/intentsvcs/src/facade.rs`), which overwrites an existing file (issue 0715) and returns early on NotFound by design, as its doc comment says. 3.4.0 wrote no file at all, so a new attachment behaves as it did in 3.4.0, and only the overwrite case changed.

## The fix

`place_attachment` creates the file when the thread's directory is realised and the path is absent, under the same rollback as the overwrite: if the store write fails, the created file is removed. A thread whose directory is not realised stays as it is, with nothing written to disk.

## Proof

One arm: on a realised thread, `st attach` of a new path writes the file with the attached bytes, prints it under `wrote:`, and a commit of what the verb printed passes canon_commit_check with no `organize --apply` in between.
