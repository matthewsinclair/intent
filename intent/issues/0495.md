`intent doctor` reads 0 findings while a board view on disk is BEHIND the store, although it reports the same board when the file is ahead, so the state a failed board render leaves is the one direction no checker sees.

**Driven 2026-09-20** in a scratch project on the 0487 landing's binary, with a positive control on the instrument first.

- **The positive control fires.** A hand-edited `intent/whiteboard/cc/wip.md` gives `doctor: 1 finding(s)`, and a corrupted `board.json` gives a named refusal. So doctor's board coverage is real and this issue is NOT "doctor does not look at boards". It looks.
- **The failing direction.** Make the node's own directory refuse writes, then run a CONTENT-bearing board write: `intent wb add watchout "..." --node cc`. The row lands, the warning prints, and the rendered board does not move. `intent wb show cc` finds the item in the store; `grep` finds it absent from `wip.md`. **`intent doctor` then reads `0 finding(s) across 0 thread(s), 0 issue(s), 3 view(s), 13 file(s)`.**
- **So the gap is DIRECTIONAL.** A board file AHEAD of the store, which is what a hand edit makes, is reported. A board file BEHIND the store, which is what a failed render leaves, is not. The second is the one a board write actually warns about.

**`intent organize --apply` agrees, and that is the half that makes it expensive.** Against the same stale board it reports all zeros, because `.intentfiles` carries no whiteboard row and `organize.rs` no board code. Before the 0487 landing the board write's own remedy sent a reader to a third command, `intent st sync`, which would also have reported success without touching a board. **Three clean reports against one stale board**, and the only true signal is a warning that prints once and scrolls past. The staleness is then cured silently by the next board write, which is why it has never been caught: the window closes on its own and leaves nothing behind.

**0487's own text is where this hid.** It recorded "`intent doctor` read 0 afterwards because the next render caught up", offering the catch-up as the explanation for the clean read. That was never tested against a view that had NOT caught up. It reads 0 either way, so its verdict said nothing about the tree.

**AND THE MEASUREMENT TRAP, recorded because the first version of this issue fell into it and would have been filed false.** The obvious way to stage this is `wb touch`, which moves the heartbeat. **The rendered heartbeat has MINUTE granularity**, so a failed touch in the same minute as the last successful one produces a file that is byte-identical to what a fresh render would write -- there is no skew, doctor is right to read 0, and the run proves nothing while looking exactly like a finding. The stage must change rendered CONTENT, and the check must be that the item is in `wb show` and absent from the file, rather than that a hash did not move.

**The ask:** doctor reports a board or inbox whose rendered form differs from the file in either direction, not only where the file is ahead. Whether organize should grow a board door is a separate question and this does not ask it -- the checker is the cheaper half and the one a node actually runs.

**Two things this issue does NOT establish**, both from dc's read of `doctor::file_checks` and `views::render_all` on 2026-09-20. First, `views.rs:2203` skips a registered-but-unmigrated board deliberately and correctly, since its markdown stays authoritative until `wb migrate` carries it -- so on a partly-migrated estate "doctor: 0 findings" says nothing about those boards either, for a different and legitimate reason. Second, the four families `render_all` enumerates are threads, issues, boards and inboxes, and the two aggregate views; **anything generated outside them is a surface doctor cannot report skew on by construction**, and `AGENTS.md` is one such, with zero occurrences of `agents` in `doctor.rs` and its only true signal in `intent agents validate`. dc established that AGENTS.md is outside the reach and explicitly did not establish that it is the only one; the unchecked candidates named are the `docs/reference` generated pages, the skills SHA256 manifest and `.claude/settings.json`. The better question for that half, in dc's words, is **which generated surfaces are outside `render_all`, and what holds each of those to its source instead** -- it has an answer per surface and names the missing mechanism where there is none. That is its own issue, not this one. S.

**Not closed by 0487**, which landed a remedy naming the door that works. A correct remedy still depends on the node reading the one warning; this asks that the state be detectable afterwards.
