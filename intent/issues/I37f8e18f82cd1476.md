The MCP test harness can deadlock. `mcp_session_with_env` (intent-cli/tests/common/mod.rs) writes every frame to the server's stdin before it reads any stdout.

Seen: gate all at bank 188842aa4 on rhadamanth, 2026-11-24 06:25Z to 06:56Z. `an_address_where_a_thread_id_is_wanted_is_refused_whole::the_mcp_thread_tools_refuse_an_address_whole` ran for 27 minutes. A sample of both processes showed:
- `intent mcp` blocked in `mcp_stdio::write_frame`, writing a reply to stdout that nobody read;
- the test blocked in `write_all` to the server's stdin (common/mod.rs:338), because the server had stopped reading.

It depends on the pipe buffer size, which macOS sizes by memory pressure, so it does not hang every run. The same test passed in two earlier gate runs that day. A test that can hang can also hang the cut's own gates.

Fix (owner cc, size XS): read the server's stdout on its own thread while the frames go to stdin, then join it after stdin is closed and the child has exited.
