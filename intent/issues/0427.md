## What happened

ST0069 built the tree-sitter index and the boundary that should route a model's code search into it (WP-20, WP-24). The model does not use it. Measured on 2026-09-16 across this project's 85 session transcripts:

- MCP `intent_search` tool calls: none, although `.mcp.json` loads the `intent mcp` server in every session here.
- Bash commands running `intent search --kind def`, `--context` or `--outline`: 53, not classified between real lookups and tests of those verbs, so an upper bound.
- Bash commands running `git grep`: 520, plus thousands of plain `grep` and `rg` commands.
- Calls to Claude Code's Grep tool: 3.

The index answers correctly and is current: `intent search --kind def nearest_project` and `intent search --context awaited` returned today's landed code.

## Why the boundary does not fire

1. `post-tool-symbol-context.sh` matches `tool_name == "Grep"` only. Sessions search through Bash, so the hook would almost never run.
2. It is off by default (not in the settings.json template, by design), and Intent's own `.claude/settings.local.json` declares no hooks.
3. Not measured: whether a PostToolUse hook's plain stdout reaches the model at all. If Claude Code shows exit-0 stdout only in the transcript view, the append must be emitted as the hook's JSON `additionalContext` instead.

## The fix (vc's ruling, 2026-09-16, routed to dc on hv's word)

- The hook also answers a Bash call whose command runs exactly one grep-family search (`grep`, `rg`, `git grep`) with one symbol-shaped pattern: the existing rule, one identifier, bare, in word anchors, or given with `-w`. Anything else appends nothing: a regex, several patterns, several searches in one command. It never parses beyond that, never blocks, and keeps the all-or-nothing freshness rule per answer.
- Its output reaches the model. Settle item 3 by a live drive, not by reading.
- Intent turns it on in `.claude/settings.local.json` on hv's machine (PostToolUse, matchers `Grep` and `Bash`). The template's default stays off.
- Proof: one arm per trigger (the Grep tool; a Bash grep with a symbol; a Bash grep with a regex, which appends nothing), then a live session greps a known symbol through Bash and sees the index's answer.
