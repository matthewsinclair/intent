`gen_reference.sh` renders a register `note` on ARGUMENT rows and on no other level. An ENTRY's own `note` -- the paragraph a register row carries about the verb as a whole -- reaches no page under `docs/reference`. This issue asks which of two things that is: a deliberate omission, which the generator and the reference's own front matter should then say, or a gap in the generator.

## Measured, 2026-09-18

- `intent/st/ST0056/parity/tools/gen_reference.sh:223`, inside `arg_rows`, is the only place the generator reads `.note`: `((.note // .default // "") | cell)`. Nothing renders `.note` on an entry or a family.
- The case that surfaced it: issue 0444 corrected the `wb migrate` entry's note at `0702809cf` (register path `families/29/entries/15/note`). Neither the old wording ("An over-bound") nor the new ("After the carry the two bounds differ") appears in ANY page, in the set committed before the 3.1.0 regeneration or in the regenerated set at `d254b53b8`.
- The consequence it already had: the unified plan for 2026-09-18 ordered 0444 BEFORE the `docs/reference` regeneration because "its register note reaches docs/reference through the register". It does not, so that ordering protected nothing. It cost nothing, because 0444 landed first anyway, but a plan was built on a claim about the renderer that nobody had driven.

## What deciding it needs

Whether an entry note is written for a reader of the reference or only for the register's own maintainers. Some entry notes are maintainer rationale -- the `wb migrate` one explains why the node is a positional -- and would read oddly on a user page, while others describe behaviour a user meets.

- If the reference should carry them, the generator renders an entry's note under its command row, and every entry note becomes reader-facing prose that has to be written that way.
- If it should not, the generator says so where it explains what a page carries, so the next plan does not assume otherwise.
