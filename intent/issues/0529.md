Found on 2026-09-23 by cc while reading the store's restore path for 0525, and named rather than folded into 0523 stage 2. Read by vc in `store.rs` (`restore`). Not driven yet.

Seen:

- The store's restore diffs its board rows against the offered boards by a natural key (`crate::model::board_changes`). For a message, that key includes the body, so a body change is not `Changed` but `Removed` plus `Added`. The `Changed` branch updates `re`, `fyi`, `state`, `handled_at` and `authored_at`, and never the body.
- `Added` takes the next id "in the order the boards hold it, which is the order the inbox reads back", so a re-added row sorts after every row it did not replace.
- `intent wb edit message` (0523 stage 2) changes a message's body in place in the store where it runs. So on a SECOND clone of the project, a restore from a pulled `board.json` that carries the edit deletes the old row and re-adds it. The edited message moves to the end of its inbox on that clone, and `<anchor>#<n>` can renumber within one heading minute. An edit addressed `#<n>` on that clone could then reach a different message from the one the same address named before the pull. The refusal's remedy text says "an inbox only grows, so a number never moves", which is false on that path.
- A shared store on one machine never takes this path, because the edit writes the store first and the restore then finds nothing to change.

Why the body is probably in the key, and what a fix must keep: messages carried by `wb migrate` from hand-authored inboxes can share one stamp, so `(sender, recipient, recorded_at)` alone may not be unique. The body would then be what tells them apart. A fix must keep the key unique for those rows, for example with an ordinal among equal stamps in board order, and must update the body in `Changed`.

Expected: an edited message keeps its row, its id, its place in the inbox and its `#<n>` on every clone, and a restore after a pull updates its body in place.

Unmeasured: the drive itself (two clones, an edit on one, a pull and a restore on the other), and how often carried messages actually share a stamp in the fleet's stores.
