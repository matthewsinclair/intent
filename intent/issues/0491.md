`daemon_logs_prints_and_follows::no_tail_survives_follow_however_it_ends` (intent-cli) hangs FOREVER, not fails, when the suite is started with SIGINT ignored. Its `child.wait()` has no bound, so a whole suite run stalls for hours, and a person who kills the stuck child to get unstuck gets a PASS from the arm.

**Where it bit:** cc's T4 run on 2026-09-19. The intent-cli suite was launched as a detached zsh `&!` job, which starts with SIGINT ignored. The arm stalled for 3h46m with its child `intent daemon logs --follow` alive; killing that child let the arm finish, reporting ok.

**The cause, measured, not inferred:** the test binary was run on the one arm under a hard 90s limit, twice:

- With SIGINT ignored (`perl -e '$SIG{INT}="IGNORE"; ...'`): TIMEOUT at 90s, hung.
- With SIGINT default: `1 passed; 0 failed`, 0.28s.

The arm's INT case sends `kill -s INT` to the verb and then waits. A process that inherited SIGINT as ignored keeps it ignored across exec, so the verb never exits and `child.wait()` never returns. Load plays no part, although that was the first reading.

**Two defects, one arm:**

1. **An unbounded wait in a test.** A child that does not exit must fail the arm by name within a bound (eg poll `try_wait` against a deadline, then kill and panic naming the signal), never hang the suite. As written, the failure mode is silence, and the only way out, killing the child, turns it into a pass.
2. **The arm assumes SIGINT is deliverable.** Under an inherited-ignored SIGINT the INT case measures the environment, not the verb. Either the arm resets SIGINT to default for the child it spawns, or it says it is skipping INT because the signal is ignored. Whether `intent daemon logs --follow` itself should restore SIGINT's default is a separate question for the verb's owner; nothing here shows a user-facing harm.

Severity medium, on vc's ruling: a suite that can hang for hours without saying so, and a pass that can be produced by killing the process under test. Found and measured by cc.
