## What happened

The model does not use the index's MCP search tool: this project's 85 session transcripts hold no call to `mcp__intent__intent_search`. ic drove the door on 2026-09-16 (main at b48e193da) and found three causes, one of them a silent defect.

1. **The search filters are dropped without a word.** `mcp.rs` reads `kind`, `tier` and `lang` only through `.as_array()` (and outline's `ref` switch the same way), while the tool's schema publishes them as strings, and the model sends a string. A string is ignored and the unfiltered envelope comes back: `kind=def nearest_project` answered 7 hits and about 4 KB, where the CLI's `--kind def` answers one line. `strings()` in the same file already accepts a string as a one-element list; search bypasses it.
2. **Nothing reaches the model about the tool.** The intent tools arrive deferred, as bare names, and `mcp_stdio.rs` `initialize_result` sends no `instructions`, the one field Claude Code puts in the system prompt for a deferred server. No canon file, skill or session hook names the MCP tools; `CLAUDE.md`, `AGENTS.md` and three skills name `intent search --kind def` only as a prior-art check before creating a module. A ToolSearch for "find where a function is defined and its callers" does not return `intent_search` in its top 3, because its description leads with prose search and sends code lookups to grep.
3. **Every whole-tree text query tells the model to prefer grep.** The envelope answers `complete:false` because of 12 binary files and one symlink (`bin/int`) that no text search could match, and the tool's description says to trust grep over a `complete:false` answer.

Where the door works, it beats grep: `outline` returns every symbol of a file with start and end lines, and `context` returns the definition with its extent and the same call sites grep finds, without grep's canon JSON lines.

## The fix (hv's word to ic, 2026-09-16, "Ok, do that")

- `kind`, `tier` and `lang` go through `strings()`, so a string is honoured and a value of the wrong type is refused with a remedy. The outline `ref` switch reads the same way.
- The server sends `instructions` on initialize: for a code symbol, load `mcp__intent__intent_search` through ToolSearch and ask `kind=def`, `outline` or `context`; the answer carries spans with end lines; a `complete:false` answer names the paths to grep. The text has one source (the register or a template), never an inline string.
- Proof: an arm per defect (a string `kind` filters; a wrong type refuses; the handshake carries the instructions), then a live fresh session asked where a symbol is defined, recording which tool it reaches for first.

Not in this fix, and filed as 0430: the `complete:false` answer caused by binary and symlink skips, and the description's lead.
