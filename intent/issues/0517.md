A hold placed on a bank under `lib/templates/` controls the durable record and not the running behaviour, and every node that has said "held pending a suite" about that directory has been promising something the arrangement cannot deliver.

**MEASURED, 2026-09-22, on the 0506 bank (vc, confirmed through the pointer rather than assumed).** `~/.local/share/intent/home` is a 30-byte regular file, not a symlink, containing `/Users/matts/Devel/prj/Intent`. So the install root every estate on this machine resolves IS this tree, at this path. The runner at the install root and the runner in the working tree hash identically; the committed bytes of the parent commit hash differently. **Every estate's gate had been executing the new dispatch loop from the moment the file was SAVED** -- before the commit, before the judge's PASS, and before the judge's retraction.

**SO THE HALT WAS NEVER PROTECTIVE FOR THIS CLASS OF FILE.** A retraction arriving before the commit would have made the record cleaner and the fleet no safer. This is a property of the arrangement rather than of anyone's timing, and it is why it is filed rather than absorbed into an incident.

**IT IS NOT THE SAME AS THE SHIM TRAP AND THE TWO ARE EASY TO CONFLATE** (issue 0510 carries the other one). The shim trap is that a WORKTREE cannot test a file the shim resolves from the install root, so a judge reads a green from bytes it never executed. This is the mirror: the MAIN TREE cannot hold a file under `lib/templates/` out of production, so an author cannot stage a change for judgement without shipping it. One makes judging blind; the other makes holding vacuous. Both follow from the same live-on-save resolution and neither implies the other.

**WHAT THE CONTAINMENT ACTUALLY IS, and two nodes reached it independently today for an unrelated reason:** a detached worktree. Work on a file under `lib/templates/` is only out of production while it is in a tree that is not the install root. That is a working rule the estate already has in its hands; what it does not have is the rule written down as the CONDITION for holding such a bank, rather than as a convenience for running suites cleanly.

**WHAT THIS ISSUE IS NOT ASKING FOR.** It is not asking to move the install root, which is forbidden and is the 2026-09-19 `publish_home` incident. It is not asking that `lib/templates/` stop being served live, which is the property that lets a canon fix reach every estate without a reinstall and is deliberate. The defect is that the protocol's vocabulary -- HALT, HOLD, "held pending" -- reads identically for a file where it works and a file where it cannot, with nothing at the point of use saying which.

**THE TRIGGER THAT WOULD RAISE THIS FROM ITS SEVERITY:** a bank under `lib/templates/` that is REFUSED after being worked in the main tree. Every instance so far has passed, so the live window has cost nothing yet; a refusal would mean every estate on the machine ran rejected bytes for the length of the judging.
