A workspace test run under the operator's real HOME lets a worktree binary publish its own root as the machine's install pointer, and every estate's pre-commit gate then resolves its guards from that scratch tree without saying so.

**Seen 2026-09-19.** `~/.local/share/intent/home` was rewritten at 16:17:33Z to `.../scratchpad/wt-0481base`, a private worktree, inside a `cargo build -p intentd && cargo test --workspace --no-fail-fast` run there (16:16:23Z to 16:20:06Z). That run, and every whole-suite run ic made that day, used the ambient environment: HOME=/Users/matts, no XDG_* set. The release gate sets HOME to a private directory for the same cargo line (bin/.devbin/cmd/build.d/release:730); a hand-run copy of the line does not. Devbin's, dc's and cc's commits after 16:17Z ran their guards from that worktree, which was main at 35b902fd9 without T3. Earlier whole-suite runs from other worktrees that day may have published their roots the same way in their own windows.

**The writer, named.** Only `intent bootstrap` writes the pointer (render.rs `bootstrap`, `intentsvcs::bootstrap::run`, `install::publish_home`), and it publishes the RUNNING binary's own root. The arm is intent-cli's separate test target `dual_path_conformance` (tests/dual_path_conformance.rs; its own `[[test]]` in intent-cli/Cargo.toml, outside the one `suite` target), in `invariant_every_shipped_verb_answers_identically_down_every_route`. Its in-process route `via_library` calls `intent_cli::dispatch` in the test process for every shipped verb that `HAZARDS` does not refuse, and `bootstrap` is not in `HAZARDS` (the daemon, app, discover, explore and mcp rows are). So `bootstrap` runs in-process under the test process's real HOME, `install::home()` resolves the test binary's own worktree, and `publish_home` writes it. `via_binary` is isolated through `testkit::fixture_home`; the in-process route cannot be, which is what `Hazard::ActsOnAmbientUserState` exists to declare. `testkit::fixture_home` itself exists because two `dispatch_ssot` arms published a scratch worktree on 2026-08-27, so this is the class's second firing.

**Evidence.** In one worktree's build, each run under a fresh sentinel HOME: `cargo test --workspace --no-fail-fast` wrote `<sentinel>/.local/share/intent/home` naming that worktree; each of the nine test binaries run alone under its own sentinel, and only `dual_path_conformance` wrote it (intent-cli's lib and suite, intentd's three targets, intentsvcs's lib and suite and testkit's suite left it empty). The machine's real pointer was untouched throughout.

**The probe (a second defect).** `intent claude upgrade` WITHOUT `--apply` prints no "different install" note while the pointer names another tree (measured by devbin-vc: grep counts 0); the note appears only on `--apply`. The dry run is silent in exactly the state the note exists to report.

**Fix candidates:**
1. `("bootstrap", &[Hazard::ActsOnAmbientUserState])` in `dual_path_conformance`'s `HAZARDS`, the declared exclusion its siblings already use.
2. `install::publish_home` refuses a root that is a linked git worktree (`--git-dir` differing from `--git-common-dir`) or lies under the system temporary directory, naming the root and the remedy, so the next arm that forgets cannot redirect the machine.
3. `claude upgrade`'s dry run prints the "different install" note whenever the pointer differs from the running binary's root, exactly as `--apply` does.
4. Every intent-cli arm that spawns the binary does so through `testkit::fixture_home` by construction.

Severity high: while the pointer names a scratch tree, every estate's pre-commit gate runs guards nobody reviewed for that estate, and nothing says so. M.
