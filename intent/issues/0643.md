## What happens

A write through the `at` path re-sorts a thread's whole `tests` array by string id, so `AT-01.10` lands before `AT-01.2`, and the generated acceptance view then reorders rows nobody touched. The `criteria` array is sorted the same way by the sync-side put arm, so the two arrays of one thread can follow different orders depending on which verb last wrote each.

## Measured (conflab-vc, 2026-10-25, Conflab commit 4269f178)

Adding `AC-03.9` and `AT-03.26` to Conflab's ST0121 and re-citing `AT-03.3` produced a 325-line diff of `intent/.canon/st/ST0121.json`:

- Before: `tests` ran `AT-01.1`, `AT-01.2` ... `AT-01.9`, `AT-01.10`.
- After: `AT-01.1`, `AT-01.10` ... `AT-01.15`, `AT-01.2`.
- `criteria` kept its natural order (`AC-01.1` ... `AC-03.1`), so the two arrays in one file now follow different orderings.
- The id sets differ only by the two new rows (96 ids before, 98 after); the rest of the diff is pure churn.

## The source (vc, 2026-10-25, at 6afb46998)

Three sites in `native/rust/crates/intentsvcs/src/facade.rs` order rows by `a.id.cmp(&b.id)`, a byte comparison of the id string: `at_new` (`prospective.tests.sort_by`, line 15343), and the put arm's `holder.tests.sort_by` (line 16707) and `holder.criteria.sort_by` (line 16774). Under a byte comparison `AT-01.10` sorts before `AT-01.2` because `1` precedes `2`. `ac_new` pushes without sorting, so a criteria array is re-sorted only by the put arm; and Conflab's criteria kept their order in the measurement only because none of ST0121's criteria has a two-digit minor yet (conflab-vc's precision of 07:1xZ, by its own account), so lexical and natural order agree there and the sort at 16774 was invisible rather than absent.

## Why it matters

Churn in canon reads as review and buries the real change in the diff, and a thread's two arrays can disagree about what order means. Canon is reviewed by diff in every estate.

## The fix, specified (vc, 2026-10-25)

One order for ids, natural rather than lexical, defined once in the model: an id compares segment by segment, letters as text and digits as numbers, so `AT-01.2` precedes `AT-01.10` and `AC-01.1` precedes `AC-10.1`. The three sites above call that one comparator, and nothing else orders criteria or tests (grep the crates tree, tests included, before narrowing the judge). The views render the arrays in canon order as they do today, so the view follows. A thread whose canon still holds the lexical order re-sorts once at its next acceptance write, which is one churn per thread and the last.

Arms in intentsvcs' acceptance tests, each red at the base: `at new` of `AT-01.10` into a thread holding `AT-01.1` to `AT-01.9` leaves `AT-01.2` before `AT-01.10`, and the array with the new row removed equals the array before the write; the same through the put arm for tests and for criteria; and the fixtures carry an `AC-xx.10` beside an `AC-xx.2` and an `AT-xx.10` beside an `AT-xx.2`, because without a two-digit minor the two orders agree and no arm can fail; and a comparator unit arm over `AT-01.2`, `AT-01.10`, `AC-10.1`, `AC-1.1` naming the order.
