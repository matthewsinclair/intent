Seen: a project that declares `shell` gets no structural index for its shell files -- `intent index status` reports `grammar: shell no-grammar` -- yet the search envelope answers `"complete": true`, with `skipped` and `stale` empty and `reconciled: true`. So a definition in a shell file reads as ABSENT in an answer that says it is complete:

- here, `intent_search` with `kind=def` and `query=roster_unchecked` answers 0 hits under `"complete": true`, while `git grep` finds `roster_unchecked()` at `lib/templates/hooks/pre-commit-guards.sh:121`;
- here, `outline` of that same file answers no symbols under `"complete": true`;
- in Devbin, `kind=def` for `vendored_paths` answers 0 hits while it is defined at `lib/install:258`, and the same holds for outline and context queries on every function under `lib/`.

The control: `kind=def` for `is_claim_address` finds `native/rust/crates/intentsvcs/src/model.rs:201`, so the instrument works where a grammar exists. The CLI's human form of the same shell query prints only its reconcile note and says nothing about the language it cannot see.

Why it matters: the CLAUDE.md Intent generates tells an agent to ask the index before grep and to "fall back to grep only when its answer says the index is not complete for the paths involved". In any project that declares a language with no grammar, that fallback never fires, and the agent reads "no definition" as the answer -- which is also how a Highlander check concludes that nothing of that name exists yet.

Expected: an answer that a file in a declared, grammarless language could have changed says so -- `complete` is false for those paths, or the envelope names the language as unindexed -- and the CLI's human form says it too, so the generated instruction's fallback fires. `author` and `content` also report no-grammar; whether prose languages belong in the structural question is part of the fix, stated rather than assumed.
