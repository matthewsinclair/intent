This repository has THREE behaviours for one situation -- a suite arm whose subject is an armed tool that is not installed -- and the worst of them is the default.

**Found by a red CI run on 2026-09-22**, run 35739715195, sha 940e07ee8, both legs identically. Two arms of `tests/unit/staged_format_guard.bats` failed: 624 "unformatted staged Markdown is refused" and 627 "prettier judges the blob under the config the file's OWN path resolves". The guard was working exactly as designed. Neither GitHub runner ships prettier, `tests.yml` did not install it, and `staged-format-guard.sh:197` correctly reports `UNENFORCED -- markdown(prettier)` and returns 0 -- while both arms assert status 1. **An arm asserting a REFUSAL requires the tool to be PRESENT, and that is a precondition on the environment that no local run can expose**, because the dev machine has prettier from Homebrew.

## The three behaviours

1. **PANIC.** `require_prettier()` in the Rust suite aborts deliberately when prettier is absent. Its own reason, quoted in `rust.yml:89-93`: "a skip here is a green that means nothing, on a criterion about instruments that pass without measuring."
2. **SKIP.** An existing bats arm degrades silently. Visible in the very run that went red: `ok 160 a fmt sweep leaves every fenced root markdown byte-identical # skip prettier unavailable offline`. It reports `ok`.
3. **ASSERT AND FAIL UNINTELLIGIBLY.** The new guard arms, which say only that `[ "$status" -eq 1 ]` failed. A reader of that output cannot tell a broken guard from a missing tool.

**Three homes for one question is the Highlander shape**, and the three disagree about whether a missing tool is fatal, invisible, or a test failure.

## What is owed

The bats suite needs the PANIC form: a `require_prettier` equivalent that fails with the tool NAMED, so a missing tool reads as a missing tool rather than as a guard that stopped refusing. The skip form should go with it -- arm 160's `# skip prettier unavailable offline` is the green that means nothing, by the Rust suite's own argument.

**This is not a request to re-litigate `rust.yml`'s install step**, which is correct and which `e0f030bb0` has now mirrored into `tests.yml`. That stops today's red. This stops the class: the next arm written against an armed tool will otherwise inherit whichever of the three behaviours its author happened to copy.

## Why it survived, which is the part worth keeping

**The lesson was already written in this repository, as a prediction, in the neighbouring file.** `.github/workflows/rust.yml:96-99`: "NEITHER RUNNER SHIPS PRETTIER ... Without this step the prettier arms fail on BOTH legs while passing locally: the primary dev machine has prettier from Homebrew, so a local green does not show the runners lack it."

That is this incident's postmortem, written weeks in advance, naming both legs, naming Homebrew, and naming the false local green. It was not consulted. vc read all three workflow files the same morning while measuring an unrelated question about `paths-ignore` and did not connect it.

**And the judging failed the same way.** vc judged 0505's twelve arms and did not take dc's log -- it re-ran the suite itself and got 12/12. That felt like verification and was not: the same instrument on the same box, which adds confidence and no information. The question that would have caught it is not "do these arms pass" but **"where could these arms fail"**, which for an arm asserting a refusal is answered by naming what must be installed for a refusal to be possible at all.
