Recorded by cc while shaping issue 0601's (b), and filed on vc's word when (b) landed at ae1bb7fb4; not a defect anyone has hit.

Claude Code's docs say `CLAUDE_CONFIG_DIR` overrides the configuration directory, default `~/.claude`, and that every `~/.claude` path, `skills/` included, then lives under it (code.claude.com/docs/en/env-vars and /claude-directory, read 2026-10-15 for 0601; refs/bank/cc/0081/evidence/0601-hooks-doc.md). Intent names `$HOME/.claude` in three places that would then disagree with where Claude Code loads skills from:

- the in-session skill's release line, `bash "$HOME/.claude/skills/in-session/scripts/release-gate.sh"` (in-session SKILL.md);
- the prompt gate's releaser check, require-in-session.sh, and session-context.sh's Next line, both since 0601 (b);
- `intentsvcs::userstate::claude_dir`, which `intent claude skills install` writes to.

So on a machine that sets `CLAUDE_CONFIG_DIR`, `intent claude skills install` writes skills where Claude Code does not look, and the gate looks for a releaser that is not where the skill was loaded from. The docs do not say whether `CLAUDE_CONFIG_DIR` reaches a hook's environment (hooks inherit "the parent environment", and `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1` removes it), so a fix that reads it in the hook first measures that it arrives.

Shape, if taken: `userstate::claude_dir` honours `CLAUDE_CONFIG_DIR` when set, and the release line and the two hook scripts resolve the same way, so the check, the release and the install read one path. Size S. Measure before building: whether a session started with `CLAUDE_CONFIG_DIR` set exports it into the Bash tool and into hooks.

## Resolution (cc, 2026-10-16)

Landed at 89bce6328 (patch-id e392553208f4), judged by vc as part of the 3.2.4 composition. `userstate::claude_dir` returns `$CLAUDE_CONFIG_DIR` when it is set and non-empty, and `$HOME/.claude` otherwise, so `intent claude skills` and `subagents` install, and `intent doctor`'s releaser advisory looks, where Claude Code loads skills. `require-in-session.sh`, `session-context.sh` and the in-session release line read `${CLAUDE_CONFIG_DIR:-$HOME/.claude}`, so the install, the release and the check read one path. hv granted the read on 2026-10-16 (vc decision 65), confined to `userstate.rs` (rows in `no_intent_home.rs`).

Measured before building, Claude Code 2.1.301: a `claude -p` under `CLAUDE_CONFIG_DIR=<scratch>` delivered the variable to its SessionStart and UserPromptSubmit hooks. Not measured: whether the Bash tool receives it, or whether Claude Code loads skills from `$CLAUDE_CONFIG_DIR/skills`; the fallback leaves today's path wherever the variable does not arrive. The test doors (`testkit::fixtured_command`, the bats helper) remove the variable so a developer's own value cannot reach a temp-HOME arm.
