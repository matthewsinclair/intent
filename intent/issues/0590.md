Requested by hv on 2026-09-28, raised from a Lamplight session: filing this issue and the one before it meant cd-ing into Intent first, because every `intent issues` verb takes its project from the working directory (Project::discover walks up from the start directory, intentsvcs/src/project.rs:1561), and no flag or environment variable names another one. Proposal: `intent issues --project <project> add <title> ...`, and the same for the other issues verbs (`new` is already `add`'s alias), acts on a project from the machine's registry, $XDG_CONFIG_HOME/intent/projects.json, instead of the project the working directory is in. The registry lists roots and nothing else (intentsvcs/src/projects.rs:1-13), so `<project>` would resolve by reading each registered root's own intent/.config/config.json: its `project_id`, its `project_name` (case-insensitive), or the registered root path itself. A value that matches more than one project is refused, naming each candidate; a value that matches none is refused, listing the registered projects. It never falls back to the working directory's project, because that would file the issue in the wrong estate without saying so. The write goes through the target project's store exactly as a run from inside that project would, so its event, canon file and view land in that project's tree, and the answer names the project and its root so the caller can see where the issue went. Design question to settle first: whether --project belongs to `issues` alone, or is a global flag that every project-scoped verb honours (st, wp, ac, wb and the rest), with issues as its first user.

## Resolution

Fixed at 4c6903d0b (issue 0590, banked as refs/bank/dc/324b/0590, patch-id 8668291397dd, judged by vc as part of 3.2.4's second train), on hv's rulings of 2026-10-16 (vc decision 64): `--project` belongs to the `issues` family alone in 3.2.4, and the resolver lives once in intentsvcs, so a global flag later is wiring.

`intent issues --project <project> <verb> ...` acts on a project from `$XDG_CONFIG_HOME/intent/projects.json`. The flag is declared on the family row of `surface/dispatch-table.json`, before the verb, so every issues verb and the bare `list` take it. `intentsvcs::projects::resolve` answers it in two tiers. The exact tier is a path or a `project_id`; a value is read as a path only when it has a `/` in it, so a bare name that is also a directory under the working directory stays a name. The name tier is the directory name or `project_name`, case-insensitive. Both name forms are matched because the directory is what tells two checkouts of one project apart (hv, 2026-09-03). A name two projects carry is refused naming both, a name none carries is refused listing the registry, and a registered root that no longer opens is listed and never matched. Nothing ever falls back to the working directory's project.

`render.rs` routes all seven issues arms through one door, `issues_open`, into the same `engine` as before, so the event, canon file and view land in the named project's own tree. The answer names the project and its root: on stderr for `list` and `show`, so a table or JSON document stays clean; on stdout ahead of a write's output; and as `project` and `root` fields in `show --format json`. `--daemon` with `--project` is refused by `run`'s existing `refuse_unservable`, because no issues row has a `serving_op`. The MCP tier is unchanged, since tool schemas come from each verb's own row and the family row is not exposed.

The arm is `intent-cli/tests/issues_project_names_another_estate.rs`. Four tests were red at base on the unknown flag and all five are green with the fix. They cover: a case-folded directory name, a directory name against a shared `project_name`, a `project_id` and a path each landing one issue in the named project's canon while the working directory's project stays byte for byte; the ambiguity and no-match refusals naming their candidates and the stale root; the read naming its project on stderr with pure JSON on stdout; and `--daemon` refused.
