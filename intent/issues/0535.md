Reported by gtools-dc through gtools-vc on 2026-09-23, measured on Gtools with Intent 3.2.0 at c5cca7e26. Reproduced by vc on Intent's own estate at 6a4d0fef9 with the same installed pair.

**What happens.** A store that does not exist yet is warmed from canon on its first open: `ingest::load_fresh` calls `resync_inner(.., Load::WarmIfCold)`, which calls `Store::warm_if_cold`, and that warm carries threads and issues only. Boards reach the store only through an unscoped `Load::Restore`, which is `intent sync --to-store` (ingest.rs: "ONLY AN UNSCOPED `Restore` CARRIES BOARDS FROM DISK INTO THE STORE"). So every fresh clone and every fresh worktree opens with a store holding every thread and every issue and no whiteboard at all, while each node's `board.json` is committed beside it. `load_fresh`'s own comment states the rule this breaks: a cold store is warmed with `Scope::All` because "a partial store looks exactly like a small project".

**The remedies it prints lead somewhere worse.** Driven in a detached worktree of Intent at 6a4d0fef9, made with `git worktree add --no-checkout --detach` and then `git reset --hard`, as gtools-dc made theirs:

1. `intent wb status` prints `no nodes are registered` and names `intent wb register`. `intent wb show vc` refuses with the same remedy.
2. `intent wb register` registers five nodes, each with an empty board, and exits 0. `intent wb show vc` then reads items 0, archived 0, messages 0.
3. `intent wb touch --node vc` refuses, correctly under 0412: vc is registered and not migrated. The remedy it names is `intent wb migrate vc`.
4. `intent wb migrate vc` exits 0. It reads the RENDERED `wip.md` as though it were hand-authored markdown, coerces section prose into items (`NO PUSH, NO RELEASE.` became a doing item), and carries 10 items and 106 messages. It then rewrites all five nodes' `board.json`:

| node | items before | archived before | messages before | after: items / archived / messages |
| ---- | ------------ | --------------- | --------------- | ---------------------------------- |
| cc   | 197          | 193             | 37              | 0 / 0 / 0                          |
| dc   | 230          | 227             | 28              | 0 / 0 / 0                          |
| hv   | 49           | 14              | 37              | 0 / 0 / 0                          |
| ic   | 247          | 244             | 42              | 0 / 0 / 0                          |
| vc   | 186          | 181             | 106             | 10 / 0 / 106                       |

`git diff --stat` over `intent/whiteboard/` read 9 files changed, 1012 insertions, 10258 deletions. Every step exited 0 and each one named the next. A board commit from that checkout publishes the loss for every node. Git history still holds the boards, so it is recoverable, but only by someone who notices.

The remedy that was right all along, `intent sync --to-store`, is named by none of these steps. In a first cold worktree, run after the two reads of step 1 and instead of `wb register`, it carried 1164 differences, `intent wb status` then listed all five nodes with their boards, and the tree stayed clean. The register-and-migrate drive above was a second cold worktree.

**What the fix has to do.**

- The cold warm carries the boards. Under the same write lock as the thread and issue warm, a store found cold takes each `board.json` from disk, as an unscoped `sync --to-store` does. The reason the Ingest arm carries no boards (intentd's pass must not outvote a store holding a board write whose extract has not been projected yet) does not apply to a store that holds nothing. Whether "cold" also counts board rows, so that an estate with boards and no threads or issues still warms, is part of the change.
- `intent wb migrate <node>` refuses a node whose `board.json` on disk records it as migrated. That board is a generated view with its extract beside it, not hand-authored markdown, and carrying the render drops everything the render does not show: archived items, handled state, and every other node's rows.
- While the store holds no node and `board.json` files sit on disk, the `wb` reads name `intent sync --to-store`, not `intent wb register`.

**Not in this issue.** gtools-dc also reported doctor refusing every commit in such a worktree with view skew. In the cold worktree of Intent's own estate, doctor reported one counted finding, `gate-not-running` (the untracked `.githooks/pre-commit.intent` carrier, which doctor already names as an open item), and no whiteboard finding. The Gtools view-skew lines have been asked for and not yet read.

**A second symptom, measured by gtools-vc and gtools-dc on Gtools the same day.** In a cold Gtools worktree, doctor refused commits with `residue: view-skew` on inbox views: two at 3a37f6b, and five in gtools-dc's proof worktree. The skew itself is Gtools' commit timing, since a recipient committed its `board.json` without its inbox views. What is Intent's: the remedy doctor prints for that finding is `intent sync --to-disk`, and on the cold store it printed `ok: extract written for 10 thread(s) ...`, exited 0, and changed no file, because the store it renders from holds no board. Doctor then reported the same findings. A warm store renders the boards, so the cold warm carrying them (the first bullet above) is what makes that remedy do what it says. The fix is proven by driving `sync --to-disk` on a cold store holding a skewed inbox view, then doctor.
