Reported by utilz-vc on 2026-10-16 from Utilz's estate and reproduced by vc on the installed pair (intent 3.2.3, 701c4d98b, dev) in an isolated HOME.

**What was measured on Utilz.** intent/.cache/intent.db was 28,635,136 bytes at the 04:56:35Z backup and 5,290,971,136 bytes at 14:25 local the same day, with a 5.8 GB WAL. dbstat put the bytes in doc_sections_content (3,336 MB) and doc_sections_data (1,656 MB). doc_sections held 1,873,488 rows over 2,438 distinct (owner_type, owner_id, file, seq) keys and 264 files: every key present 2,048 times, which is 2^11, so the store doubled eleven times in the day. The doubled rows are owner_type `wb_node` (1,236,992 rows, 2,355 MB) and `file` (635,904 rows, 230 MB); `thread`, `issue`, `board` and `work-package` rows were not duplicated. Every write then cost about three minutes at full CPU and 3.6 GB RSS (`wp new`, `sync --to-store`), because each write's FTS5 `rebuild` rewrites the whole index, and a write holding the lock that long made every other node's write fail on the five-second wait.

**The mechanism, read in the code and then reproduced.** `ingest::compose_scoped` (ingest.rs, called for every SCOPED restore: `intent sync --to-store <ID>` and the daemon's `disk.sync_from_disk` of one thread) builds the canon it installs by reading EVERY stored section back with `read_sections`, dropping the named thread's, and adding the thread's sections from disk. That list then goes to `Store::replace_doc_sections`, whose canon half deletes only `owner_type NOT IN ('file', 'wb_node')` before inserting every section it is handed. The `file` and `wb_node` rows just read back are therefore inserted again beside themselves: one doubling per scoped ingest, canon-owned rows untouched. Today's Utilz log carries 7 `disk.sync_from_disk` and cc's `sync --to-store ST0026` retried about four times, which is the eleven.

**Reproduced on the pair's binary.** A scratch project with one README (49 file sections after `intent index rebuild`) and one thread: three `intent sync --to-store ST0001` in a row read file rows 49, 98, 196, 392 with 49 distinct keys throughout; an unscoped `intent sync --to-store` neither doubled nor repaired (392 stayed). `intent index rebuild` brought the file half back to 49 on the scratch store. On Utilz, hv ran it at about 11:10Z after closing every `intent expl` reader, and an immutable read at 11:12Z showed BOTH halves back to one row per key: 604 `wb_node`, 1,475 `file`, 289 `issue`, 137 `board`, 96 `work-package`, 71 `thread`, with no WAL or shm file left beside the db. So the shipped repair recreates the whole table (vc first read it as reaching the file half only, from a partial read of `index_rebuild`, and the measurement corrected that). The db file stays at 5,290,971,136 bytes, since SQLite keeps freed pages; only a VACUUM shrinks it, and no verb ships one.

**Shipped in every v3.1 release.** The read-back landed at 4819e5aa8 (issue 0447) and is in v3.1.0 through v3.2.3. Intent's own store shows no doubling only because no scoped ingest has run here since 2026-09-26 (`disk.sync_from_disk` last then), which is why the class went unmeasured until an estate exercised the path daily. It is issue 0234's class again (every mutation appends a copy of the index) through a third mechanism.

**Shape of the fix (vc), size M, a 3.2.4 blocker.** (1) The guard at the one place sections become rows: `Store::write_doc_sections` under `ProseHalf::Canon` inserts only sections whose owner_type is one its DELETE removes, so no caller can re-insert the file or whiteboard halves, and `compose_scoped` filters them from its read-back for the same reason. (2) A migration rung (user_version 30 to 31) that deletes duplicate doc_sections rows keeping one row per (owner_type, owner_id, file, seq) and then runs the FTS5 `rebuild`, so every affected store repairs itself on its first open under the fixed binary; a store that is not duplicated is unchanged. (3) Tests: a scoped sync run twice leaves the row count where it was, by owner type; the rung on a planted duplicated store leaves one row per key and the content findable. (4) A doctor check that counts duplicate keys in doc_sections, uncounted and shown, so the class is visible the next time. **Remedy for an affected store today:** close long-lived readers so the WAL can checkpoint (a reader blocks it), run `intent index rebuild` once for the file half, write no scoped ingest and make no disk edit under intent/st/ until the fixed pair is installed, which repairs both halves, measured on Utilz; the migration rung is for the stores nobody rebuilds by hand; no hand SQL on the store.

## Resolution

Fixed by 915245eb2 for 3.2.4: the canon-half write in `Store::write_doc_sections` inserts only the sections its delete removed, `compose_scoped` reads back the canon half alone, schema rung 31 (`DOC_SECTIONS_DEDUPE`) leaves one row per (owner_type, owner_id, file, seq) on the first open under a fixed Intent, and `intent doctor` shows any duplicates found after that, not counted, with `intent index rebuild` as the remedy. Arms: `a_scoped_sync_does_not_double_the_prose_index.rs`.
