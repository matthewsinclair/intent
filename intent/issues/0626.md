Found by cc on 2026-10-22, reading v3.2.5's release assets for ST0081 WP-01. vc measured it the same night.

v3.2.5's `intent-support.tar.gz` (sha256 d0938ba5832f..., the published asset) carries three directories that git does not track:

- `lib/templates/eng/`
- `lib/templates/issues/`
- `lib/templates/prime/`

Each is empty in the tarball, and `git ls-tree -r v3.2.5` names no file under any of them. They come from this Mac's working copy, where `lib/templates/eng` holds only a `.DS_Store` and `issues` is empty. `bin/int macos stage` tars the support paths straight from the working copy (`bin/.devbin/cmd/macos`, around line 995), with `.DS_Store` excluded. Its drift check compares files only, so an empty directory rides into the asset unseen.

THE CONSEQUENCE TODAY: none that runs. No code names those directories, and the Linux packages, which do not carry them, behave the same. But the release asset's bytes depend on the release machine's working copy, not only on the tag's tree. So two cuts of one tag on two machines can publish different support tarballs, and the stage's own check would pass both.

THE ASK: the support tarball is built from the tag's tree (eg `git archive` of the support paths at the tag), or the drift check compares directories as well as files, so that the asset is a function of the tag.
