Two board writes in the same second can leave a node's board split between the store and its files. Seen in another of hv's estates (Laksa) on 2026-10-28 at about 19:57Z, during a lean-out when several nodes edited their boards at once.

What was left behind:

- The store holds a `wb.edit` of dc's todo 69 (event 01M621DZ9R80X9QPBP3RJ7N4ER, edited_at 2026-10-28T19:57:44.685Z).
- No event file exists for that event under `intent/.canon/events/`.
- dc's `board.json` still carries todo 69's previous text and edited_at. Measured by vc: a normalised diff of `intent wb show dc --json` against `board.json` differs in that item and in nothing else.

Consequence: doctor reports the board as skewed, and every board write in the estate is refused until `sync --to-store` or `sync --to-disk` runs. Each remedy discards one side wholesale, so an operator who cannot tell which side is the superset is stuck. A fresh clone would never see the edit, because its event file was never written.

Expected: a board write that the store committed also writes its event file and re-renders `board.json`, or it rolls back. Two writes landing in the same second must not interleave so that one's file output is lost. Doctor's finding should also say which side holds more, so the remedy is chosen by measurement.
