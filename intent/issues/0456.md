Found by ic on 2026-09-18 rehearsing ST0078 P4's drive against a pair built from e447f15cf (P3, P2 and P5 landed), with no daemon; traced in the source by dc the same hour.

Repro: `intent init`, `intent bootstrap`, `intent claude upgrade --apply`, commit; `git switch -c b`, `intent st new X`, commit; `git switch main`. The post-checkout hook runs `intent sync --apply`, prints `intent (post-checkout): took 1 change(s) ... ST0001 (removed)`, and leaves `?? intent/.canon/` behind: an UNTRACKED `intent/.canon/project.json` holding `{"schema": "intent/project@3.0"}`. The next `git merge b` refuses: `untracked working tree files would be overwritten by merge: intent/.canon/project.json`. That is the ordinary PR flow, a branch merged into main, and it is broken on every clone whose main never committed project.json.

Cause: the facade's write projection adds `intent/.canon/project.json` on EVERY write, whether or not the project has a todo watermark to record, and `intent init` writes none. So a fresh main has no such file, the first write on a branch creates and commits a schema-only one, `git switch main` removes it, and any write on main recreates it untracked, the post-checkout hook's ingest included. A plain `intent st new` on main does the same with no hook at all; the hooks only make it happen at the moment the next merge trips over it. An absent file and a schema-only file mean the same thing to the reader (no cutoff recorded).

Fix (dc's recommendation, ruled by vc under the pen): the projection does not CREATE project.json when there is no watermark to record; it still rewrites one that exists and still writes one when a flush sets a cutoff. Rejected: `init` writing the file so it is always tracked, because every existing estate would keep the hazard. Built in ST0078's P5 follow-up bank with a CLI arm driving this repro through to a clean merge, and P4's drive runs on the commit that carries it.
