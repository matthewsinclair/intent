## What was seen

On hv's Ubuntu VM (kovacs), 2026-10-15, in a real Claude Code session hv opened in a project that ORDER 7 of ST0081 had set up from the Linux package (3.2.3 at 11017d7bd, `intent bootstrap`, `intent init`, `intent claude upgrade --apply`, with hv's real `HOME` and only `PATH` changed), the first prompt was refused by the gate, as designed:

```
● UserPromptSubmit operation blocked by hook:
  [intent claude hook require-in-session]: Intent project: /in-session must run before your first prompt.
  Run /in-session now -- it loads project coding standards and releases this gate.
  (Expected sentinel: /tmp/intent/in-session-59097651-f3bd-4ab1-a23a-5fb83dec9bac.sentinel)
```

and the release it names was not there:

```
● Unknown command: /in-session
```

`intent claude skills list` on that machine shows `in-session  -  canon`, not installed; `~/work/o7h/proj/.claude/` holds `settings.json` and `settings.local.json` and no skills. Nothing on the install path had installed any skill. The session was locked out of every prompt that does not start with `/`, and the SessionStart hook's own line, "Next: run /in-session to load coding skills and release the UserPromptSubmit gate", names a command the machine does not have. Found by kovacs-sysadm, reading hv's transcript; the transcript is the artefact.

## What was expected

A machine that follows `docs/install.md` and then runs `intent claude upgrade --apply` can prompt Claude Code in that project. The gate's release is a skill, so the verb that wires the gate installs the skill, or refuses to wire the gate without it, or at the least names the missing step in its report; and the install page names it.

## The mechanism (read, not run)

`intent claude upgrade --apply` writes `.claude/settings.json` from `lib/templates/.claude/settings.json`, which wires `UserPromptSubmit` to `intent claude hook require-in-session`; `canon.rs` has no skills step and its report never mentions one (grep `skills` in `native/rust/crates/intentsvcs/src/canon.rs`: nothing). `require-in-session.sh` passes a slash command through and otherwise exits 2 until `/tmp/intent/in-session-<session id>.sentinel` exists; the only writer of that sentinel is `release-gate.sh` inside the `in-session` skill, which reaches `~/.claude/skills/` only through `intent claude skills install in-session` or `--all`. `docs/install.md` and `docs/getting-started.md` name no `skills install` step at all; `intent/docs/working-with-llms.md:635` ("Verify `/in-session` installation") is in the source repository, not on the install path. hv's own machines never showed it because their skills were installed in March 2026 and every session since has released the gate.

## Two more readings from the same session

The gate also refused an inbound cross-session message (a peer's `SendMessage`, delivered as a prompt), so a fresh project session is unreachable by peers until `/in-session` has run; on hv's estates every session runs it at boot, so this only bites a machine without the skill. And the SessionStart hook's reminder goes into the model's context rather than onto the screen, so hv's transcript on screen does not show it; the session's `.jsonl` would.

## The fix, as vc would shape it

`intent claude upgrade --apply` installs `in-session` (the skill the gate it wires depends on) when it is absent from `~/.claude/skills/`, and reports it as it reports each root file; or, if a project verb must not write a user-level directory, it refuses to write a settings file that wires the gate while the skill is absent, naming `intent claude skills install in-session`. `intent doctor` gets an advisory for a wired gate whose releasing skill is absent on this machine. `docs/install.md`'s macOS and Linux sections and `docs/getting-started.md` gain the one line after `intent bootstrap`: `intent claude skills install --all` (or `in-session` at the least). Size S for the docs and the doctor advisory, M if `upgrade --apply` installs. A test: `claude upgrade --apply` under a `HOME` with no `~/.claude/skills/in-session` either leaves that skill installed or refuses the settings file and names the verb.
