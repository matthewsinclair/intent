On a project that has flushed its DONE list, `intent upgrade` writes an `intent/todo.md` that `intent doctor` then reports as a hand-edited view, so the upgrade's own output fails the commit gate.

**Seen** on Lamplight's wave-one upgrade to 3.1.0 (Lamplight 71ba6903f): `intent upgrade` wrote a todo.md of 122958 bytes against doctor's render of 24247 bytes, byte-equal to the committed file. Lamplight restored the file from HEAD to reach doctor 0.

**Reproduced** on a clone of Lamplight at 884f2e3ae (the commit before its upgrade), in a scratchpad under an isolated HOME with the 3.1.0 keg binary (11ce80ad5):

- `intent upgrade`: rc 0, todo.md is 122958 bytes. Doctor: `intent/todo.md -- generated view differs from the model (122958 bytes on disk, 24247 rendered, first difference at byte 23622)`, rc 1.
- The difference: the committed heading is `## DONE:2026-08-27T21:41:41Z`, the flush watermark, and the DONE list under it is short. The upgrade writes `## DONE` and lists every finished thread and work package, 1877 more lines.
- `intent todo update` straight after writes the same 122958 bytes, and doctor still reads 1.
- `intent sync --to-store`, then `intent todo update`: 24247 bytes, byte-equal to HEAD, and doctor reads 0.
- With the watermark already in the store, a second `intent upgrade` still writes 122958 bytes. `intent todo update` after it writes 24247, and doctor reads 0.

**Mechanism** (read in code at HEAD): the watermark has two readers that are meant to agree (views.rs, `RenderContext::todo_watermark`, whose comment warns that the writer and doctor disagreeing makes doctor report todo.md as hand-edited). Two paths get it wrong:

1. `intent upgrade` renders its views through `migrate::assemble` (migrate.rs), which builds its `RenderContext` with `todo_watermark: None`. So the upgrade always writes an unflushed DONE list, whatever the store or canon hold.
2. On a cold store, `intent upgrade`'s rebuild (`Store::rebuild`, facade.rs `Facade::upgrade`) never carries project state: the clone's store had no `project` row afterwards. So `Facade::projection`, which reads the watermark from the store, renders without it too, while `Facade::doctor` reads it from canon's `intent/.canon/project.json`. `ingest::load` and `resync` carry it (`carry_project_state`), which is why `sync --to-store` repairs it.

**Reach:** only projects whose canon holds a `todo_watermark`. Of the fleet's 3.0.3 estates (wave two of the 3.1.0 upgrade), none does, so upgrade's unwatermarked render equals the correct one there, and wave two is unaffected. Lamplight was the one flushed estate.

**Fix direction:** `migrate::assemble` takes the watermark from canon's project state, as `Facade::doctor` does, and the upgrade's rebuild carries project state into the store. One authority for the value, per the views.rs comment. S. It is a crate change: bank it with intentsvcs's whole suite.
