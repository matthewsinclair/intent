Suppose a command-line write lands while intentd's background sync is between its snapshot and its file commit. The sync then writes the render it took before that write over the write's canon file and view, and records those bytes as the store's own render. Disk now holds the subject as it was before the write, and the store holds it as it is after. Nothing reports this when it happens. The next write to the same subject warns `overwrote bytes that were not the store's render -- an edit to a generated file is gone`. Until then, a commit records the stale canon.

Found when `intent issues close 0439` warned over `intent/.canon/issues/0439.json` on 2026-09-17, although every write to that issue since its filing had been made by the store's own verbs. The close chain edited each issue and then closed it, with intentd running.

Reproduced by ic the same day, on a scratch copy of this estate at `1a25373a6`, with its own git repository, store and HOME, through the installed pair `ea81a6c58`. The steps were `issues add` for two issues, the edit-and-commit steps on one of them, then the close chain verbatim over both:

- **With no daemon**, no warning; doctor 0; store and canon agree.
- **With intentd holding the project open**, the warning fires on the second issue's close and names exactly that issue's canon file. The scratch event log reads `issues.edit 0441` at 16:36:02.419Z, then `disk.sync_from_disk` at 16:36:03.698Z writing `.canon/issues/0441.json` and `issues/0441.md`, then `issues.close 0441` at 16:36:03.770Z.
- **The close rewrote the canon file but not the view.** Closing unlists the issue, and an unlisted view is rewritten only when disk equals the store's prior render. That scratch estate therefore ends at doctor 1: view skew on `issues/0441.md`, which reads open with the body from before the edit. No sync rewrites it, and organize will not remove it.

The cause, from ic's read of the source at `1a25373a6`:

- **The check that warned is correct.** `Facade::foreign_bytes` compares each target's disk bytes with the render of the store as it stood before the write.
- **The stale writer is the ingest pass.** intentd's watcher runs `Facade::ingest_from_disk` after 250 ms of quiet, and it calls `load_from_disk` under `Load::Ingest`. That pass renders the projection over every thread, issue, board and declared view from one snapshot. `set.commit()` then writes whatever differs from disk, and `record_landed` records those bytes as the store's own.
- **Nothing checks whether the store moved** between the snapshot and the commit.
- **Every subject the sync renders is exposed.** The warning appears only on writes that report through `Outcome::with_overwrites`. The `wb` verbs never compute foreign bytes, so a reverted `board.json` or board view stays silent until doctor.
- **This is the disk-side sibling of issue 0216**, which fixed the same race for store rows.

What is wanted (vc, 2026-09-17, under the pen):

1. **Guard the sync's commit.** The ingest pass commits its files only if no other connection has committed since its snapshot, judged by `PRAGMA data_version`. The check, the file commit and `record_landed` share one hold of the store's write lock.
2. **Re-render when the store moved.** If it moved, the render is discarded, and the pass snapshots and renders again, at most three times. If the bound runs out, a logged line names the subjects not written.
3. **Check the command-line side too.** The write's own foreign-bytes check, store commit, file commit and record must hold the lock the same way. If they do not, the same bank fixes that.
4. **No narrowing.** This fix does not narrow the sync to the subjects it changed.
5. **One arm.** A seam makes a second facade's `issues edit` land between the snapshot and the file commit. The arm asserts that disk equals the store's render afterwards, and that the close which follows carries no overwrite note.
