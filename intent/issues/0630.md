## What happened

dc's fold commit on 2026-10-22 was refused by the commit gate's doctor with a counted view-skew on cc's `wip.md`, 3266 bytes on disk and 1410 rendered. cc's fold was writing at that moment. The same commit passed when re-issued.

## Mechanism, read and then driven

`WriteSet::commit` (`intentsvcs/src/write_set.rs`) lands a write's files one at a time, a temp file and a rename each, in path order. For a board that order is `board.json`, then the inbox views, then `wip.md`. Doctor's skew check (`views::skew`) renders each view from the canon on disk. So between the first rename and the last, a reader sees a NEW `board.json` beside an OLD `wip.md`: the view disagrees with its own canon, and the counted `view-skew` arm reads it as a hand edit ("either it was edited by hand, or the store changed after it was rendered"). In a peer's write that is still landing, the gate's doctor counts it, and an unrelated commit is refused.

The state just before the views land is not the problem. With a board write whose views cannot land (aa's directory read-only), doctor raises only an uncounted `store-stale` advisory, and an unrelated commit passes (`refs/bank/dc/skew/repro.sh`, blob 52fdfd900e26).

`refs/bank/dc/skew/repro2.sh` (blob 65ef1da7cd7d) runs on the installed 3.2.5 pair (2e0e9215d), in a scratch project with the gate installed and two nodes:

- HELD STILL. After a normal board write by aa, aa's previous `wip.md` is put back beside the new `board.json`. This is the disk between the renames. Doctor exits 1 with `view-skew -- 1 finding: intent/whiteboard/aa/wip.md -- generated view differs from the model (845 bytes on disk, 772 rendered, first difference at byte 185)`. bb's unrelated commit through the gate is refused on that finding. Once aa's view lands (`intent wb touch --node aa`), the same commit passes.
- LIVE. aa makes 80 board writes in a loop while bb's doctor reads in a loop: 5 of 19 reads counted a view-skew.

So a node's commit is refused whenever its gate's doctor reads during a peer's board write. A fold is a burst of such writes, which is when nodes commit most.

## Expected

A view that is a write in progress is not a hand edit, and a peer's write in progress refuses no one's commit. Two shapes:

- **(a) Provenance, in doctor.** The file index records the bytes of every view the store writes, and `record_landed` updates it only after the whole set has landed. So during the window the old `wip.md` on disk still matches the index's record for it. A view whose bytes equal the index's record is the store's own last render, not an edit. It can be reported uncounted, as the views lagging their canon with `intent wb touch` or `sync --to-disk` as the remedy, while a view that matches neither the render nor the record stays a counted hand edit.
- **(b) Scope, in the gate.** The commit gate counts a view-skew only on paths the commit stages, and shows the rest uncounted.

(a) keeps doctor's answer true for every caller, and (b) narrows only the gate. A doctor that waits on the writer's lock is a third shape, and it puts a wait on every gate.
