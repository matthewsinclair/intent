## What

`intent wb ask <node> --re "<anchor>"` accepts an anchor that isn't a whole `YYYY-MM-DD HH:MMZ` stamp. It returns ok and renders the partial anchor as the new message's `Re:` line, which threads against nothing.

This happened twice on 2026-10-18, on one project's whiteboard, with intent 3.2.4. One node's replies, sent at 18:05Z and 19:01Z, went out with `--re "2026-10-18 18:0"` and `--re "2026-10-18 18:5"`. Both were stored and rendered as `Re: 2026-10-18 18:0` and `Re: 2026-10-18 18:5`. Each needed a correction note through `intent wb edit message`.

## Expected

The verb refuses an anchor that isn't a whole minute stamp. It also refuses one that matches no message the recipient sent the sender. Either refusal names the messages the anchor could have meant, so that the sender can copy the right one.

## Workaround

Copy the full anchor from the inbox file in the same turn as the reply.


## The shape

Ruled by vc on 2026-10-22, under hv's word that cc builds 0610 on vc's recommendations.

1. **One resolver.** `wb ask --re` resolves its anchor through the resolver `wb edit message` uses (`message_address`), with the direction reversed: the anchor must name a message the addressee sent the asker. Both verbs share one parser and one grammar.
2. **It accepts `<minute>#<n>`,** as `wb edit message` does, and refuses an ambiguous minute with the listing, as that verb does. A partial anchor is refused, and so is an anchor that matches no message. Each refusal names the messages the anchor could have meant, ready to copy.
3. **`re` stores the canonical anchor the resolver returns:** the whole minute stamp, plus `#<n>` when the resolver took one. It carries no message id; ids belong to issue 0612.
4. **Existing `re` values stay as written.** Nothing migrates.
5. **It is built against the store as it stands,** and banks after 0612 lands, rebased on it, because both touch the `wb ask` path. ic reviews the refusal texts before the bank.
