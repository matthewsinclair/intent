The Rust critic's rule IN-RS-CODE-004 (no `Result<T, String>`) is enforced at the pre-commit gate by a greppable proxy, and the proxy reads a nested generic whose inner type ends in `String` as a `Result` whose error is a `String`.

Seen 2026-09-17 at the landing of ST0076's level-3 core: the gate refused `Store::resolution_basis` in `native/rust/crates/intentsvcs/src/store.rs` for

```
.collect::<Result<std::collections::BTreeMap<String, String>, rusqlite::Error>>()?;
```

whose error type is `rusqlite::Error`. The `String>, ` that closes the map's type parameters is what the pattern matched. cc moved the collection's type onto the binding (`let indexed: BTreeMap<String, String> = ... .collect::<Result<_, rusqlite::Error>>()?`) to get past the gate, and says `guide.rs` and `export.rs` already carry the same workaround for the same proxy. So three call sites have bent their code to a pattern, and the third did it at commit time, which made the landed bytes differ from the bank vc had judged (the difference was two lines and was verified by a tree diff).

What is wanted: the proxy does not fire on a `Result` whose error parameter is not `String`. The error parameter is the text after the LAST top-level comma inside `Result<...>`, so a pattern that cannot count angle brackets should at least require `, String>` to close the `Result` itself rather than an inner generic; the rule's Detection section says which, and one arm in the critic's own tests holds a nested-generic `Result` with a typed error as clean. The existing workarounds may stay or go; they are harmless.

Low. It costs a recomposition at the gate each time it fires, never a wrong program.
