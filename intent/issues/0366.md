The daemon never builds its search index when it opens a project. Found by cc's reading (2026-09-13, read-only, at e70c3528a) while chasing 0354, and matched exactly by dc's runs 4 and 5.

How the index is driven today: the open path indexes nothing (`registry.rs handle_for` runs `ProjectHandle::open`, whose store thread does `open_facade` -> `Facade::open` -> `ingest::load_fresh`, then `consider_backup` at intentd store.rs:280-284, then the work loop at :289). The only daemon writer of `index_file` is the `Work::IndexRefresh` arm (store.rs:321-341), whose only sender is `ProjectHandle::index_refresh` (:489-492), called only from the watcher's `on_index_batch` (watch.rs:233), one message per debounced path (watch.rs:191-200), each reconciling that path's subtree, or the root's own files when the path is the root (reconcile.rs:181-185). The CLI's daemonless `intent search` reconciles the whole scope before it answers (render.rs:3648-3652), `intent index rebuild` rewrites it (render.rs:4348), and `st list` never touches it. Daemon-served search deliberately does not reconcile (the `Op::Search` arm's comment in store.rs).

The measurement: run 4's store, read directly, holds rows for exactly the top-level directories in sorted path order up to `intent` (root 12, .archive 9, .claude 3, .githooks 4, .github 4, bin 69 = 101 at the first hot sample; + docs 65 + examples 41 = 207; + intent 968 = 1175) and ZERO rows for lib, native, schema, surface and tests (35, 485, 6, 4 and 118 tracked files at e70c3528a). Run 5's 13 rows are the 13 root-level tracked files and nothing below the root: one root-granularity event and no other. So which directories a fresh daemon indexes depends on which FSEvents arrive after its open (late delivery of the clone's own checkout writes, or a MustScanSubDirs; neither measured), and a daemon opening a quiet checkout indexes nothing below the root. Daemon-served `intent search --daemon` then answers from whatever arrived: run 4's daemon would search with no `lib/`, `native/` or `tests/`. Daemonless search is unaffected.

Independent of 0354: the spin ran beside the indexing at the same rate with and without it (run 4's row 18, about 10M syscalls in the 31s that indexed 1074 files, then 21.6M in the 52s with counts frozen), so the parker never drove the index and the parker fix changes none of this. Candidate fix (cc): after the ready signal, beside `consider_backup`, one whole-scope `facade.index_refresh(None)`, the same reconcile daemonless search already runs; on a current store it is one survey with no writes. Open question for the shape: one whole-scope transaction blocks every `Work::Client` for the build's duration on a fresh clone (about 34s of CPU in run 4), where per-directory messages would interleave with clients.

Fixed at 524f5f868 (cc, ST0069/WP-22, 2026-09-13): after `consider_backup` the store thread takes `Facade::index_stale_roots` (one whole-scope survey against the index as it stands: the root if a root-level file is stale, plus each top-level directory holding a change, sorted) into a queue and refreshes one directory at a time only when the work channel is empty, so a waiting client op always goes ahead of the next directory; a current store costs the one survey and no writes; the survey and the refresh share one `index_change`, and the build and the watcher's arm share one `refresh_index` that reports a failure. AC-22.4 with AT-22.4 (`intentd/tests/a_daemon_indexes_a_project_when_it_opens_it.rs`): red on the unfixed tree (13.05s, "never found notes/deep/marker.md"), green on the fix; the intentd suite 36 passed, 0 failed, 1 ignored, plus the 8 unit tests and the 5 subscription tests. Closes on the delivered pair once the live daemon runs it.
