An intent-cli test that spawns the binary without a fixture HOME runs a verb against the developer's own per-user state, and nothing in the crate refuses one.

**The class, and why it is filed separately.** Issue 0492 closed the install pointer specifically: `publish_home` now refuses to let a scratch root replace a pointer naming a real install, whatever HOME the spawn inherited. That is one file. The spawns themselves are unchanged, and the rest of per-user state is not covered -- the project registry `~/.config/intent/projects.json` that issue 0445 records, the state directory under `~/.local/state/intent/`, the daemon socket and log, and the config `~/.config/intent/config.json`.

**Measured on the tree at 2026-09-20.** Of the intent-cli test files that spawn `CARGO_BIN_EXE_intent`, about a third pass `testkit::fixture_home`, a little under a third set a HOME of their own, and the rest -- 48 files at the time of the count, since reduced by one -- set none at all and inherit the operator's. Three of those name a verb already declared as acting on ambient user state in `dual_path_conformance`'s HAZARDS: `cli_write_moves_only_what_changed.rs`, `mcp_stdio_serves.rs` and `the_struck_doors_refuse_as_retired.rs`. The other 44 drive project-scoped verbs against a tempdir fixture, so the exposure there is latent rather than demonstrated -- which is the same shape as `bootstrap` before 0492, a row whose subject changed underneath the test.

**Why a count is not the fix.** `testkit::fixture_home`'s own docstring records the reason: it exists for tests that *cannot know whether they touch per-user state*, because the verb under a row can grow a new reach long after the row was written. `bootstrap` answered the unwired marker until it was implemented, and two `dispatch_ssot` arms published a scratch worktree on 2026-08-27 the day it became real. So the ask is a mechanism that refuses an unfixtured spawn, not a one-off sweep that the next new file is free to miss.

**The ask, with the mechanism left to the plan.** Either a guard arm that scans the crate's tests for a spawn of `CARGO_BIN_EXE_intent` that does not set HOME and names each one, in the idiom of the existing declaration checks, or a spawn helper in `testkit` that every arm goes through and that cannot be called without a HOME. Whichever is cheaper to keep true; the guard is the cheaper to write and the helper is the harder to evade. The sweep to make the chosen mechanism green is the bulk of the work, roughly seventy call sites across the files above.

Severity medium: nothing is known to be corrupted by it today, the pointer is closed by 0492, and the remaining reach is reads plus the registry writes 0445 already records. M.


**CORRECTION, same day, forward rather than rewritten (dc, who asked which line said so).** The paragraph above names three files -- `cli_write_moves_only_what_changed.rs`, `mcp_stdio_serves.rs` and `the_struck_doors_refuse_as_retired.rs` -- as naming a verb already declared `ActsOnAmbientUserState`. **That is wrong, and the instrument is why.** The scan behind it matched the quoted literals `bootstrap|discover|explore|daemon|app|mcp`, which is a WIDER set than the eleven rows actually carrying that hazard (`daemon start|stop|restart|logs|status`, `app start|stop|restart|status`, `discover`, `explore`). What it hit in those three files was `("st", "bootstrap")` and `args: &["st", "bootstrap"]` -- the RETIRED `st bootstrap`, a string about a door that no longer exists -- and `.arg("mcp")`, whose hazard is `NeverReturns` rather than ambient state. dc read the roster, got eleven rows, could not reproduce the three, and asked rather than assuming either of us right.

**Re-measured against the eleven rows alone, including their split-argument spellings: of the 47 files, ZERO name an ambient-state verb.** So the whole population is LATENT rather than demonstrated, and no file in it is a live case today. That strengthens the argument for a mechanism over a sweep rather than weakening it: the exposure this issue is about is the one a literal scan cannot see, because a row's subject changes when the verb underneath it grows a new reach -- which is exactly what `bootstrap` did between the day `dispatch_ssot` was written and the day it published a worktree. A census arm that counts unfixtured spawns is then the one number worth having, and it is a number about spawns rather than about verbs.

**And the reporting rule this cost, stated because the error was mine and cheap to repeat:** a claim that a file "names a hazardous verb" is a claim about a ROSTER, so the scan has to be the roster and not a superset of it that happens to be easy to type.
