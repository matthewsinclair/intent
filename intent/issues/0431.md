## What happened

On 2026-09-16 hv reported that `intent app restart` still fails with "Intent.app did not register with it within 15s", and that `intent app status` says "not running" while Intent.app (pid 96907) is up. `lsappinfo list` shows the app registered 0.07 s after launch, so the app is fine.

## Cause, found by cc

This host runs macOS 27.0 (26A428). Its `lsappinfo info -only pid <bundle id>` no longer prints `"pid"=96907`. It prints the whole record template, with `[ NULL ]` for every other field and the pid as `pid = 96907`, unquoted and with spaces around the `=`. The bundle path arrives the same way, as `bundle path="/Applications/Intent.app"`.

`macapp::parse_ls_field` (intentsvcs/src/macapp.rs) split on the first `=` in the text, which is now `bundleID=[ NULL ]`. So `pid()` was always `None`, and a bundle-path read would have returned the literal `[ NULL ]`. Issue 0423's launch deadline (f330805da) is correct. It waited on a reading that can never succeed on this OS.

## The fix (cc, judged by vc)

- The parse reads the named field in either spelling (`"pid"` or `pid`, `"LSBundlePath"` or `bundle path`), quoted or bare, where the key starts a token.
- An empty value or `[ NULL ]` is absent, never a value.
- Arms: the verbatim macOS 27 output for both fields (red on 04a667c7c), the old format, and the nothing-running case for both fields.
- The live proof is hv's `intent app restart` after the rebuild.
