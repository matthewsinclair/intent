The repository's commit gate passes a commit with every ST0056 parity gate skipped when the gate's own tools are not on disk.

`bin/.devbin/cmd/precommit` runs its parity guards from `intent/st/ST0056/parity/tools`, which is a thread's realised directory. When that directory is absent, because ST0056 was dehydrated, renumbered or re-keyed, the gate prints one warning ("every ST0056 parity gate SKIPPED this commit"), sets `HAVE_TOOLS=0` and carries on (precommit, around line 255). Only the database and whiteboard guards still run, and the commit goes through.

That exit status is the same one a run of every guard returns. Nothing that reads the gate's verdict can tell a full gate from an empty one, and the warning text is the only thing that carries the difference. The repository has already ruled on this shape: `thread_view_skew_check.sh` retired its own fail-open on 2026-08-27 under IN-AG-NO-SILENT-001, because "exit 0 is the SAME STATUS a run that examined every view returns".

vc's Highlander sweep for ST0095 found it (report C, cluster M, `refs/bank/vc/st0095/highlander-C-non-rust-20261119`), and dc confirmed it on 2026-11-19 against `precommit` at HEAD. The tools stay on disk only because `intent/.intentfiles` declares `STEELTHREAD:ST0056`. ST0096 changes how realisation is declared, so the trigger is live in this release.

Remedy direction: refuse rather than skip, and name `intent st hydrate ST0056` as the remedy. Addressing the gate's own tools by a thread's path is ST0084's subject and stays there.
