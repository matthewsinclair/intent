The probe witnesses the rows `surface/dispatch-table.json` declares `exposed_on_mcp: true` and `read_or_mutate: read`. It reads that population from the table, but runs a hand-written invocation map, and the two have drifted both ways:

- **16 declared rows are never run**, which the probe itself reports and exits 1 on: ac show, at lint, estate status, events, graphql, id, index status, outstanding, todo, todo list, wb brief, wb profile, wb show and wb status (plus schema and search, named in NO_V2).
- **16 rows in its map (COVERED) are no longer in the population, and it runs them anyway.** `st edit` and `doctor` are declared `mutate`. info, config get, agents template, lang list, lang show, modules check, modules find, plugin list, plugin show, ext list, ext show, ext validate, version and critic are declared read but not exposed on MCP. The probe runs each and prints a change to the tree as "DECLARED read AND CHANGED THE TREE". So `st edit`, which realises the thread and writes the store and two canon events, as its `mutate` declaration says it may, was reported as a mislabelled read. The table is right; the probe's label is false.

The probe checks the map against the population in one direction only: a declared row missing from the map is caught, and a mapped row that left the population is not.

Expected: the probe runs only rows in the declared population, refuses a COVERED entry that is not in it (naming the entry and its declaration), and the map covers the 16 declared rows or names each in NO_V2. One run then exits 0 or names a real mislabel.
