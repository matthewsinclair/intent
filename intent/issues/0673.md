**testkit's `a_run_leaves_no_corpse_of_its_own_behind` FAILS WHEN ITS SIBLING'S SWEEP LANDS BETWEEN ITS PLANTING AND ITS COUNT.**

**Seen on kovacs on 2026-11-01, in Intent's Linux preflight at 64cf9e251** (kovacs-sysadm's END 2026-11-01T09:28:18Z, relayed to intent-vc). `crates/testkit/tests/abandoned_fixtures_are_swept.rs:143:3` panicked with "the probe did not grow its own family, so it measures nothing", left 2, right 3. The other eight tests in testkit's suite passed. The preflight at 721b4efdc that morning was green, and neither testkit nor `native/rust/Cargo.toml` nor `Cargo.lock` changed between the two. The test is unchanged since 3a82fae27 (2026-09-10).

**The mechanism, read from the source by intent-vc.** The test plants three fixture directories in `/tmp`, each named for a pid it has just spawned and reaped (`a_dead_pid`), so each is an abandoned fixture by construction. It then asserts that the family counts 3 (`:140-147`). Its sibling in the same suite binary, `a_dead_fixture_is_removed_and_a_live_one_survives_the_same_sweep` (`:85-92`), calls `testkit::sweep_abandoned_fixtures()`, which removes every abandoned fixture in `/tmp` whatever its tag. The two run on parallel test threads, so a sweep that lands between the planting and the count removes some of the probe's fixtures. Left 2 means one was swept. The test's own doc (`:122-133`) moved off a global `/tmp` count for this kind of race, but the tagged family can still be swept by any concurrent sweeper.

The probe stops counting its family in `/tmp` and asserts on the three directories it planted, each name checked against the sweep's own predicate, so a concurrent sweeper can only remove a corpse, which is the property the test holds. dc's storm run on 2026-11-01 read 2 red of 40 probes at the base and 0 of 40 with the fix (`refs/bank/dc/testkit-race/run-v1-stamps.txt`). intent-vc judges it in 3.3.0's first train.
