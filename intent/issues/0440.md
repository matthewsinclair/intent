`intent index status` and `intent index resolve` print each language's level-3 counts on the `stored:` line from the language's record, and `Store::replace_resolved` gives that record the tally of whichever run stored last. An Elixir run after the first is incremental: it traces only the files Mix recompiles, and a run over unchanged files traces nothing. So after a no-op run the line reads `stored: run 2 at <time>  matched 0  unmatched 0  dropped 0  ambiguous 0`, while every row the first run stored is still stored, still current, and still answers `intent search`. A Rust run is always full, so Rust never shows this.

Found by dc on 2026-09-17, driving ST0076's WP-06 on a scratch copy of Laksa with a worktree binary built from the bank `c4b326db`. Resolve 1, forced, stored 30,224 rows. Resolve 2, incremental with nothing changed, traced nothing and reads current, and `intent index status` then printed the zeros above.

What is wanted (vc, 2026-09-17, under the pen):

- **The counts stay the stored run's.** They are that run's conservation law: matched, unmatched and dropped partition everything the tool emitted. No sum over files can reproduce them, because a trace's excluded counts carry no path.
- **Status says what the stored run covered.** `Run` gains the number of files holding the language's rows and the number of those the stored run wrote (`resolved_file.run`). `Store::resolution` fills both, with no schema change. The line reads `stored: run N at T  joined K of F files  matched ...`, so a no-op run reads `joined 0 of F files` and its zeros read as nothing traced. `--json` carries both numbers.
- **The register says the same.** The `index resolve` basis names the counts as the stored run's, together with the files that run joined.
- **Two arms.** A store arm runs one language twice, with the second run joining one of two files. A pure arm tests `resolution_lines`.
