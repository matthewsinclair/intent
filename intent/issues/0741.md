Found by devbin-dc on ST0096 WP-04's AC-04.1 run 2 (Desk 01M7X2ZT, 2026-11-20 18:24Z), reproduced by hand on this build. A pull brings a thread and an issue minted in another working copy, which the puller's store never held. The non-interactive intent sync --apply (what the post-merge and post-checkout hooks run) plans: 1. ingest (quiet): take 2 change(s) from the files into the store; 2. views (reversible): write 2 and remove 6, the pulled records' own view paths; and reports left: 1 step(s): views (reversible) -- run intent sync --apply on a terminal, or with --yes. The views step is computed from the store BEFORE the plan's own ingest step, so it plans to remove the views of the records the ingest is about to take; removing files is reversible, so the hook's non-interactive sync leaves it for a person. Running it is harmless: sync --apply --yes recomputes it and reports views: wrote 0 and removed 0, the tree stays clean, and a fresh intent sync says nothing to do. So a hooked user is told after every such pull to run a step that does nothing. A pull of the copy's own merged records does not trigger it. Remedy wanted: the views step is planned (or re-planned) after the ingest it follows, so a step that will do nothing is never left. Owner: cc (sync's plan); filed by dc. Rides this release (hv decision 69).
