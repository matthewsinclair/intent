A comment that BEGINS `# shellcheck ` is directive syntax, so a sentence written there disarms shellcheck for the rest of the script -- silently, in the project that arms shellcheck as a critic.

**Measured by devbin-vc on 2026-09-22, in Intent's own `.github/workflows/tests.yml`, and driven rather than reasoned.** `actionlint .github/workflows/tests.yml` at HEAD, before any edit, reported SC1072 "Expected '=' after directive key" and SC1073 "Couldn't parse this shellcheck directive. Fix to allow more checks", both anchored at the `run:` of the macOS job's "Install dependencies" step. To establish that it predated the edit rather than inferring it from the diff, the file was extracted with `git show HEAD:.github/workflows/tests.yml` into a clean scratch tree and actionlint run there: the same two codes. After rewording so the line no longer begins with the directive token, actionlint reports nothing at all for the file -- **so the re-enabled checks came back clean, and nothing was hiding behind the silence.**

**The mechanism.** A comment beginning `# shellcheck ` is a DIRECTIVE and takes one of six keys: `disable`, `enable`, `source`, `shell`, `external-sources`, `source-path`. The offending line began `# shellcheck IS AN ARMED TOOL FOR THIS PROJECT`, and `IS` is not a key, so the directive is unparseable -- and shellcheck's answer to an unparseable directive is to STOP CHECKING THE REST OF THAT SCRIPT. SC1073's own text says so: "Fix to allow more checks".

**Why this is worth more than its instance.** The sentence was written to emphasise that shellcheck is armed here, and its effect was to disarm it. The general shape, cc's wording: a tool whose own configuration surface accepts prose will read a comment as configuration, and BEING DISARMED IS NOT A STATE IT REPORTS. The failure is a silent loss of checking rather than a red, so nothing distinguishes a script whose checks were skipped from a script that passed them -- which is why it survived in a tracked workflow, in the one project that arms shellcheck as a critic, until an unrelated fleet sweep tripped over it.

**Fixed in this tree already**, at `9d9eb6c52`, by the devbin 0.1.6 sweep that found it. This issue exists for the POPULATION, not the instance.

**The cheap census, not yet run outside devbin and Intent.** `git grep -nE '^[[:space:]]*#[[:space:]]*shellcheck[[:space:]]+'` over a tracked tree, minus the six real keys, names every prose comment sitting in directive position. devbin-cc ran it over devbin's whole tracked tree: devbin is clean, so devbin's ShellCheck leg green is not hollow.
