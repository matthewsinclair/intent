A comment that BEGINS `# shellcheck ` is directive syntax, so a sentence written there disarms shellcheck for the rest of the script -- silently, in the project that arms shellcheck as a critic.

**Measured by devbin-vc on 2026-09-22, in Intent's own `.github/workflows/tests.yml`, and driven rather than reasoned.** `actionlint .github/workflows/tests.yml` at HEAD, before any edit, reported SC1072 "Expected '=' after directive key" and SC1073 "Couldn't parse this shellcheck directive. Fix to allow more checks", both anchored at the `run:` of the macOS job's "Install dependencies" step. To establish that it predated the edit rather than inferring it from the diff, the file was extracted with `git show HEAD:.github/workflows/tests.yml` into a clean scratch tree and actionlint run there: the same two codes. After rewording so the line no longer begins with the directive token, actionlint reports nothing at all for the file -- **so the re-enabled checks came back clean, and nothing was hiding behind the silence.**

**The mechanism.** A comment beginning `# shellcheck ` is a DIRECTIVE and takes one of six keys: `disable`, `enable`, `source`, `shell`, `external-sources`, `source-path`. The offending line began `# shellcheck IS AN ARMED TOOL FOR THIS PROJECT`, and `IS` is not a key, so the directive is unparseable -- and shellcheck's answer to an unparseable directive is to STOP CHECKING THE REST OF THAT SCRIPT. SC1073's own text says so: "Fix to allow more checks".

**Why this is worth more than its instance.** The sentence was written to emphasise that shellcheck is armed here, and its effect was to disarm it. The general shape, cc's wording: a tool whose own configuration surface accepts prose will read a comment as configuration, and BEING DISARMED IS NOT A STATE IT REPORTS. The failure is a silent loss of checking rather than a red, so nothing distinguishes a script whose checks were skipped from a script that passed them -- which is why it survived in a tracked workflow, in the one project that arms shellcheck as a critic, until an unrelated fleet sweep tripped over it.

**Fixed in this tree already**, at `9d9eb6c52`, by the devbin 0.1.6 sweep that found it. This issue exists for the POPULATION, not the instance.

**The cheap census, not yet run outside devbin and Intent.** `git grep -nE '^[[:space:]]*#[[:space:]]*shellcheck[[:space:]]+'` over a tracked tree, minus the six real keys, names every prose comment sitting in directive position. devbin-cc ran it over devbin's whole tracked tree: devbin is clean, so devbin's ShellCheck leg green is not hollow. No other estate has been swept.

**What is owed:** run that census across the fleet, read-only, and report the estates named rather than fixing them -- the same shape as issue 0498's, where a defect closed as one estate's turned out to be nine more. An estate is only bitten where it BOTH carries such a comment AND arms shellcheck; the census finds the first, and the second is a per-estate question.

**Filed by vc on devbin-vc's measurement and at its request**, so the finding outlives the live channel it was reported in.

## A SECOND, INDEPENDENT INSTANCE OF THE GENERAL FORM, FROM A DIFFERENT TOOL, THE SAME MORNING (devbin-vc, 2026-09-22)

The paragraph above says a tool whose configuration surface accepts prose will read a comment as configuration, and that **being disarmed is not a state it reports**. That sentence acquired a second instance within hours, in a different mechanism entirely, found during the fleet's concurrency audit.

Laksa's workflow carried a `concurrency:` block that was well formed and carried a comment saying it cancels PRs. Its `cancel-in-progress` read `${{ github.event_name == 'pull_request' }}`. So it cancelled pull requests and **never cancelled a push** -- hv's ruling exactly inverted -- and every audit grepping for `concurrency:` counted it compliant. It surfaced only because devbin-vc asked for a literal `true` rather than for the key's presence.

**Present, plausible, disarmed, and reporting nothing about being disarmed.** The shellcheck case and the Laksa case share no tool, no syntax and no author, and they share that property exactly. The pairing is why this issue is worth keeping open for a population rather than closing on its instance: **a census that asks whether a mechanism is PRESENT cannot see a mechanism that is present and inverted**, and the only census that can is one that asks what the mechanism is set TO.

That generalises the census this issue already owes. For the shellcheck class the question is whether a comment sits in directive position; for the wider class it is, for each armed mechanism in a tree, whether its disabled state is distinguishable from its enabled state by inspection. The second question has no cheap grep and is not being proposed as work here; it is recorded because the two instances establish that the class is real rather than theoretical.
