## What

`intent wb ask <to> <body> --node <from>` stores the message as a row of the RECIPIENT's board. `Board.messages` holds "the messages ADDRESSED TO this node" (`native/rust/crates/intentsvcs/src/model.rs:2306`), so the ask rewrites `<to>/board.json`, which is canon, and re-renders `<to>/inbox.<from>.md`. The recipient's `wb clear` writes the same row's handled state into the same file, and the inbox view renders both: the sender's body, and the recipient's `(handled)` (`views.rs:2075`). One canon file and one view carry two nodes' acts, while every node commits only its own paths. So whichever commit the sender makes, committed main is wrong:

- **The sender commits its event and the recipient's inbox view.** This is Molt's practice, reported by molt-vc on 2026-10-22. The view on main shows a message the committed canon cannot render. Every fresh checkout or worktree then fails `intent doctor` with view skew on that inbox until the recipient commits its `board.json`. Molt's builders run doctor at the committed head in worktrees, so their commits are refused for the whole window.
- **The sender commits its event alone.** This is Intent's own rule (`intent/restart.md`: a board commit carries the node's own directory render and the event files its own acts wrote). Doctor is clean, but main carries no message. A fresh store is built from the `board.json` files, and the `wb.ask` event is only the audit record, so a fresh clone's recipient sees nothing. In a team on several clones the recipient can never commit the message, because its clone never had it. The team guide's own example (`docs/concepts/working-in-a-team.md`, "The whiteboard across clones") works only when the sender commits the recipient's `board.json`. That makes the file a two-clone file, and its "both sides moved" refusal the normal case.

## Measured

vc, 2026-10-22, on the installed 3.2.4 pair (f89b8285b), in a scratch project under an isolated HOME with hooks off. Two nodes were registered, `aa` and `bb`, and the baseline committed. Then `intent wb ask bb "hello from aa" --node aa` moved `bb/board.json`, `bb/inbox.aa.md` and one event file (op `wb.ask`, subject node `aa`).

- **Arm M, committing the event and `bb/inbox.aa.md`:** `intent doctor` in a fresh worktree at that commit exits 1 with `residue: view-skew -- 1 finding` and `intent/whiteboard/bb/inbox.aa.md -- generated view differs from the model (222 bytes on disk, 194 rendered)`.
- **Arm I, committing the event alone:** doctor in a fresh worktree exits 0, and `intent wb show bb --all` there prints `messages (0)`. The sender's checkout prints `messages (1)`, with `bb/board.json` and `bb/inbox.aa.md` still uncommitted.

## Why

The placement is deliberate, and `model.rs:2286` states its premise. Messages sit with the recipient so that "one file is a whole readable board and rendering one needs no join across nodes". The same note says "the single-writer invariant is enforced by the API and is not a property of which file the extract lands in". But git commits files, not API calls, so the invariant has to be a property of the file.

## The fix vc recommends (hv rules before any code)

Each canon file and each view has exactly one writer node, and a view renders from its writer's canon alone.

1. **The sender's `board.json` carries the message,** in a list of sent messages that replaces `messages`. It holds the fields only the sender writes: recipient, body, re, fyi, recorded_at, authored_at, edited_at.
2. **The recipient's `board.json` carries the handled state,** as marks that each name one message, written only by `wb clear`. The key must be unique across clones and stable across edits. (sender, recorded_at) is not, because a migration pass stamps every row with one recorded_at. The lane proposes the key, either an id minted at the send or the ordinal within (sender, recipient, recorded_at), and vc rules on it before code.
3. **`<to>/inbox.<from>.md` renders from the sender's canon alone,** so it carries `(edited)` and no `(handled)`. Handled state shows in `wb pickup` and `wb show --all`, which read the store.
4. **The store's `wb_message` table does not change.** The extract splits each row across the two files and the restore joins them. A mark whose message no committed board carries yet is kept rather than dropped, and doctor does not count it.
5. **`board.json` changes shape,** so its schema string and the face version of `board.schema.json` move. A store reads the old shape once, and the next board write re-renders every board and inbox view in the new one: one mechanical commit per estate, at its next sweep.
6. **The commit rule becomes mechanical:** a node commits what its own verbs wrote. That is its own `board.json` and `wip.md`, every `<peer>/inbox.<node>.md`, and its own event files. The in-whiteboard skill, `intent/whiteboard/README.md`, `intent/restart.md` and the team guide say so.

**molt-vc's other two options were weighed and are not recommended:**

- Making `wb ask` report that the recipient's `board.json` is now uncommitted leaves both windows open and depends on memory.
- Rebuilding messages from `wb.ask` events makes the event log a second canon for a row that `board.json` also carries. It also still leaves the view rendering the recipient's uncommitted handled state.
