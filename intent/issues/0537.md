Reported by gtools-vc on 2026-09-23 and driven by gtools-vc on Gtools with Intent 3.2.0 at c5cca7e26. vc read the source at 615d86a8a, and it agrees.

**What happens.** `staged_files()` in intent-cli's render.rs takes the file list from `git diff --cached --name-only --diff-filter=ACM`, so it honours `GIT_INDEX_FILE`. `critic::run` then reads each of those files with `std::fs::read_to_string`, which reads the work tree and not the index. gtools-vc drove one path in a scratch Gtools worktree:

- staged content planted, work tree clean: `ok`, exit 0, so the violation would have been committed;
- staged content clean, work tree planted: CRITICAL and WARNING, exit 1, so a clean commit was refused;
- a staged path missing from the work tree: `cannot read ...: No such file or directory`, exit 2.

A commit made with `git commit --only <paths>` stages the work tree's bytes, so this estate's own commit discipline makes the two agree and hides the defect. With `git add -p`, or any edit after staging, the gate judges bytes other than the ones being committed, and the error can go either way.

**What the fix has to do.** Under `--staged`, each file's content comes from the index that `GIT_INDEX_FILE` names: the staged blob for that path. A path staged for addition or modification is judged by its staged bytes whether or not the work tree still holds it. `--files` keeps reading the named files from disk. The drive covers all three cases above.
