Measured 2026-09-15 on train 6's judge, in a scratch worktree with an isolated HOME: after `intent sync --to-store` with the worktree's own binary (c6445c4c0 plus dc's 0321), staging `intent/.canon` picked up `intent/.canon/st/ST0056.json` and `intent/.canon/st/ST0075.json`, although 0321 changes neither thread's objective or context.

The whole difference, compared byte for byte and then as parsed JSON:

- ST0056: `objective` and `context` end with `\n` in HEAD's canon and in the bank's canon (built from a store whose fields were written through the verbs); the canon the worktree's store produced from the realised tree ends both without it. No other key differs.
- ST0075: `objective` ends with `\n` in HEAD's canon and without it in the worktree's. No other key differs.

So the same field serialises two ways depending on how the store holding it was filled. Which verb put the newline into the live store was not measured; that the tree import does not reproduce it was.

Consequence: canon churn with no content change. Anything that fills a store from the tree (`sync --to-store`, a fresh store, a train judge) rewrites those canon files, and a lander's "the canon moved only by X" check reads the rewrite as movement. It cost the judge that found it a comparison to rule it out.

Remedy: one normalisation for the round-tripped `## Objective` and `## Context` fields, applied at every door that writes them, the tree import included, with the canon written from the normalised value. Which normalisation is the fixer's call; the defect is that there are two.
