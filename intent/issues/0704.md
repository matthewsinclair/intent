Measured on brew 3.4.0 on 2026-11-19, in a scratch repository (vc). Two branches each start a thread, so each appends a `STEELTHREAD` row to `intent/.intentfiles`. When one has merged and the other merges main, git reports a content conflict in `.intentfiles` beside the two aggregate views. `intent sync` lists `.intentfiles` as "unmerged path(s) that are not intent's to resolve", and `intent sync --apply --yes` then stops at rc 1, "could not read the committed canon ... intent/.intentfiles:34 -- conflict-markers", before it regenerates anything.

So the team page's one command after a pull is not enough for the commonest merge there is. A person has to delete the markers, keep both sides' rows, `git add` the file and run the command again. After that it regenerates and stages both views and doctor is clean.

The rows are a set, and the merge's three versions say which rows each side added and removed, as they already do for a thread's work packages (issue 0555). Expected: sync resolves an `.intentfiles` conflict itself when both sides only added or removed rows, and leaves it to a person only when a line is not a row. What the merged manifest is belongs to cc; the plan step is ic's. Found while reproducing the collision behind ST0095.
