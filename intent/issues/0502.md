Raised by ic on 2026-09-22 while building ST0079/01, the explorer's `/outstanding` view. vc routed it: file it as an issue, then fix it in that bank.

**What was seen.** On the installed pair at c3514e151 (`intent 3.2.0 (c3514e151...)`), run `intent explore`, type `/help` and press Enter. With the cursor on the help page's first row, which is a `label`, the hint line reads `OMNI  1/100  ⏎ edit  ↑↓ browse · / menu · ⌫ back · type to find`. Enter on that row edits nothing, because a `label` row is a declared no-op on Enter (`native/rust/crates/intent-cli/src/tui/app.rs:763`: "ENTER ON A `label` IS A DECLARED NO-OP, STATED AFFIRMATIVELY"). This was driven in a pty rendered by pyte, on a scratch project under an isolated HOME.

**What was expected.** On a row where Enter does nothing, the hint names no Enter verb. It already names none for a door-less `button`, and none for a `select`, `text` or `number` row that cannot be edited.

**Where.** `hint_row` in `native/rust/crates/intent-cli/src/tui/run.rs:431-439` maps the focused row's kind to an Enter verb. It has no `label` arm, so a label falls through to `_ => "⏎ edit"`. Every screen with label rows shows it: `/help`, the error row of a settings or projects view that cannot load, and the counts row that ends the new `/outstanding` view.
