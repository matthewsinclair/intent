**WHY NO RESCAN ARRIVES, READ IN THE SOURCE.** FSEvents reports dropped events as `MustScanSubDirs`, with `UserDropped` or `KernelDropped`. `notify` 8.2.0 turns that into `EventKind::Other` with `Flag::Rescan` (`src/fsevent.rs`, `translate_flags`). But `callback_impl` passes an event on only when its path `starts_with` a watched root, so a drop reported against any other path is discarded there, silently, before the debouncer or `intentd` sees it. A rescan handler in `intentd` alone cannot close this.

## Resolved (2026-09-22) -- landed at `2f35e059e`, judged by vc

**THE VERDICT.** The sentinel is LOST, not late. Under file-event churn elsewhere on the volume, `intentd` receives neither the event nor a rescan, because `notify` discards a `MustScanSubDirs` drop whose path is outside the watched root. This is a production defect: a daemon on a busy Mac stops ingesting external edits and says nothing. The arm found it because the whole suite supplies that churn. The body above records the measurements that established it.

**THE FIX.** `native/rust/crates/intentd/src/watch.rs` +109 -5, bank `20969897af1aaccf812fe16dca0a627a8d509d49`, patch-id `6499ea0aa423ccba705fe7321b433f604634c994`. The landed patch-id equals the judged one. Each `Watch` owns a backstop thread that reconciles the whole canon scope every 30 seconds through the watcher's own `files_that_changed`, and ingests only when bytes differ. `on_batch`'s tail became `reconcile()`, the one path from a possible change to publish and ingest, shared by the watcher and the timer. A per-project lock is held across the file-index read and the ingest send. The store's queue is FIFO, so the second reader queues behind the first one's ingest, and a timer pass and a watcher batch cannot ingest one edit twice. A rescan that does arrive reconciles the root. Dropping the `Watch` drops the stop sender and does not join.

**TWO EXPOSURES vc NAMED, BOTH DRIVEN RATHER THAN ARGUED.**

- **An ingest reverting a store write (the 0216 class).** `file_index` records bytes AS LANDED on disk (`record_landed`, facade.rs), not the store's canonical bytes, so in the store-ahead window disk and index agree and nothing ingests. The half-landed window is the one the watcher already meets, and `ingest_from_disk`'s 0216 and 0441 guards cover both paths. Driven in a probe build with a 200ms backstop and every watcher batch IGNORED, so the timer was the only ingest path: 5 rounds of 10 creates, 10 rapid edits of one issue and 1 thread, and every write held. Each round's LAST edit held, which is the exposed write in 0216. That was 63 ticks and 10 timer ingests during the bursts. POSITIVE CONTROL: an external disk edit reached the store through exactly one timer reconcile. LIMIT: in-process CLI writes only, bursts of 21.
- **Drop and join.** The premise that the debouncers already prove the drop site safe was FALSE. `notify-debouncer-full`'s `Drop` sets a flag and returns, and only its `stop()` joins, which `intentd` never calls. So the backstop's first design was the only blocking drop, and it was changed to drop without joining. A `Watch` drops only when the registry does, at shutdown. Driven: 5 SIGTERMs with a 1s backstop and a hold inside each pass, 2 of them with a pass in flight, all exited rc 0 in about 3ms, and no daemon was left over.
