## What

`lib/templates/hooks/staged-format-guard.sh` checks a project's declared `elixir` formatter on staged `*.ex` and `*.exs` files only (`check_elixir`, `staged_files '*.ex' '*.exs'`). It runs `mix format --check-formatted` once per staged file, so every file boots the VM.

A project's `.formatter.exs` declares which files mix formats, and in a Phoenix project that includes `.heex`, through `Phoenix.LiveView.HTMLFormatter`. Laksa's `.formatter.exs` inputs are `*.{heex,ex,exs}`, and Laksa tracks 60 `.heex` files. With `"formatters": [..., "elixir"]` declared, the shipped guard would let an unformatted `.heex` file through the commit gate, and CI's `mix format --check-formatted` would refuse it afterwards.

## The measured case

Laksa's own gate, `bin/.devbin/cmd/precommit`'s `gate_elixir`, reads the extensions out of `.formatter.exs` and runs one `mix format --check-formatted` over every staged probe. Its comment records why: on 2026-08-19, 25 unformatted files under `lib/laksa_web/**` had slipped a hand-written extension list, because the list had been wrong since `.heex` entered the inputs. So in Laksa, swapping its gate for the declared guard would bring that hole back. Laksa therefore declares `markdown` and `rust` only, and keeps `gate_elixir` until this is fixed.

## Expected

The staged-format guard's Elixir check takes the extensions the project's `.formatter.exs` declares, `.heex` included, and refuses rather than guessing when it cannot read them. It runs `mix format --check-formatted` once over every staged probe, with each probe beside its original as now, so the nearest `.formatter.exs` and its plugins still apply. An arm stages an unformatted `.heex` file in a project whose `.formatter.exs` declares it: red on the base, green on the fix.

Severity medium: a declared formatter that skips a file class the project formats is a gate that passes what it was declared to refuse.
