Found in Lamplight on 2026-09-28 under v3.2.3, when critic-prose's mechanical pass returned 15 FMT-03 (unicode-decoration) hits on two files that are pure ASCII, every one a straight quote or apostrophe. FMT-03's Regex at intent/plugins/claude/skills/in-detrope/data/trope-catalog.md:801 is a single character class, and by code point its four quote characters are U+0022 U+0022 U+0027 U+0027: straight quotes where U+201C U+201D U+2018 U+2019 were meant. So the rule matches every straight quote and apostrophe and misses every curly one, which is the inverse of what it is for. Measured with Python's re, the class copied byte for byte from the file: `don't say "yes"` matches; the same text written with U+2019, U+201C and U+201D does not; a string holding U+2192 matches, as the control that the class works at all. Five more rules carry the same flattening in a two-character class `['']` that repeats U+0027 where the second character was evidently meant to be U+2019: TN-04 (:2040), TN-01 (:2176), TN-07 (:2376), TN-05 (:2444) and TN-02 (:2508). So TN-01 matches `Here's the thing` and misses the same phrase typed with U+2019. No curly character has ever been in the file's history (`git log --follow -S` finds none), so it was flattened before it first landed at 88ee47b8a (2026-03-28). The installed copy at ~/.claude/skills/in-detrope/data/trope-catalog.md is byte-identical, so every consumer runs it. Possibly by design rather than the same defect: the other apostrophe-bearing rules use a bare `'?` (ASR-01, ASR-02, ASR-03, CMP-01, NAR-01, NAR-02, SS-01, SS-04) and NAR-04 keys on a straight `"`, so none of them match typeset prose either. Fix direction: restore the four curly characters in FMT-03 and U+2019 in the five classes, written as \u escapes so no quote normaliser can flatten them again, and add a catalogue test that runs each automated regex against a curly-quoted positive and a straight-quoted negative.
