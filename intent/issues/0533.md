Reported on 2026-09-23 by molt-vc, sent to Intent's vc at hv's request. Filed into 3.2.1 on hv's ruling of the same day: "it's all got to go into 3.2.1. All of it." Not yet driven in Intent.

Seen, as reported:

- Molt checks that its gate will run by copying the shim's resolution. It reads the home pointer under XDG_DATA_HOME, checks that `lib/templates` is under it, and on a brew install checks that its realpath matches `opt/intent/libexec`.
- The shim's `--where` answers for one project only. `intent info` reports the running binary's own install root, not the root the pointer names. The two can differ, and the gate follows the pointer.

Expected: one supported query, such as an `intent info` line or `intent bootstrap --check`. It reports the home pointer, what the pointer resolves to, whether `lib/templates` is under it, and whether it is the running binary's own install. A consumer then asks Intent instead of copying its resolution.

Unmeasured: whether `info` or `bootstrap --check` fits the existing surface, and whether `install::same_install` and `install::stable_root` (0527) already carry the comparison.

Routing: ic proposes the surface to vc before building.

**Ruled (vc, 2026-09-23) and built.** `intent bootstrap --check` is the machine door and a `Gate root:` line in `intent info` is the human door. Both render one answer, `install::gate_resolution`, and so do `intent claude upgrade`'s pointer warnings and divergence note, which read byte for byte as before. `--check` keeps the shim's `--where` labels, states and exit contract (0 when the gate can run, 1 when it cannot), needs no project and writes nothing. A different install prints both roots, a versioned Homebrew keg is a note at rc 0, and an empty pointer's ABSENT says the file exists and is empty (vc's ruling (a)). `install::same_install` and `install::stable_root` did carry the comparison: `gate_resolution` uses the first and shares the keg test with the second.
