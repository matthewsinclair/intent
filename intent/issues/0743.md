Found by devbin-dc on ST0095 WP-13's drive (run 2, 2026-11-21) of the new build. It is a miss in ST0095 WP-08 (dc's, done): WP-08 put every record sort onto `id::record_order` (ordinals by number, then hashed records by their origin's creation order), but the two newest-first orders the views draw were left comparing ids as text.

`views::index_order` (threads: `st list`, `steel_threads.md`, the explorer's /threads) sorts each open/closed group by `b.id.cmp(&a.id)`, and `views::issue_index_order` (the explorer's /issues) by `b.number.cmp(&a.number)`. For ordinals that is newest first. For hashed ids it is descending hex, which says nothing about when a record was made. devbin-dc's drive: in a fresh project `st list` showed STf28fb4e, STd7c5f6a, STcbb968f in descending hex, not newest first; in an upgraded one, hashed threads before ordinals, the hashed ones again in hex order.

Remedy wanted: both orders sort each group by `id::record_order` reversed, so they read newest first by creation, with hashed records (all made after the upgrade) above the ordinals, which keep their number order. `st list` and the generated index still call the one function, so they still agree. Proof: a test that mints hashed threads in a known order whose hex order differs, and asserts `st list --status all` lists them newest made first above the ordinals.
