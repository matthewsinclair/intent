`intent set intent:///threads/<ID> acceptance exempt` writes a field that `transitions.rs` declares `Disposition::Immutable`, and that write is the only verb route to the close-gate exemption that the gate's own refusal tells an operator to declare. The two cannot both stand: enforcing the declaration closes the door the remedy points at, and keeping the door leaves the declaration false.

Found by ic on 2026-09-15 while building issue 0334's reading (4), which had `set` refuse the field by reading its Immutable declaration. vc withdrew (4) from 0334's commit on the grounds below and put the conflict to hv. The (4) patch is kept at `refs/bank/ic/0334-4`.

## The two things in conflict

- **The ruling.** hv, 2026-08-17, on vc's recommendation: `Thread.acceptance` is "immutable after creation; no machine, no edge" (`intent/st/ST0056/data-model.md:778`, under "The `Unbuilt` fields -- RULED"), because it is "an attribute of a thread, not a lifecycle: changing it is AUTHORING, not a transition, and it gets no verb" (`data-model.md:782`). `transitions.rs` carries it as the `Thread.acceptance` row: `Disposition::Immutable`, `ruled: "hv 2026-08-17"`.
- **The door.** `Facade::set` has no refusal for the field, so it writes it. `st new` writes no exemption and no rendered view carries the field, so `set` is the one verb that does. The close gate's refusal for an emptied contract names that exemption as the escape (`native/rust/crates/intentsvcs/src/contract.rs:687`): "If this unit is deliberately contract-free, declare 'acceptance: exempt'." `docs/known-defects.md:85` gives users the `set` command as the way to declare it.

## Driven

On a scratch estate with the installed pair, `intent 3.0.3 (465d508cc326917aab9b1fba61880fec9121ad8a)`, under an isolated HOME:

```
  $ intent ac new ST0001 AC-01.1 --text "a criterion"
  ok: AC-01.1 created
  $ intent ac withdraw ST0001 AC-01.1 --reason "dropped from scope"
  ok: AC-01.1 withdrawn
  $ intent st start ST0001
  ok: ST0001 started
  $ intent st done ST0001
  error: ST0001 is not ready to close -- gate: ST0001 BLOCKED -- all 1 in-scope AC(s) are descoped or withdrawn; nothing is left to verify. If this unit is deliberately contract-free, declare 'acceptance: exempt'.
    remedy: satisfy or formally descope the remaining criteria, then close again
  $ intent set intent:///threads/ST0001 acceptance exempt
  ok: intent:///threads/ST0001 acceptance written
  $ intent ac gate ST0001
  gate: ST0001 EXEMPT -- the thread declares 'acceptance: exempt'
```

## Why (4) was not the fix

With (4), `set` refuses the field as immutable, so on any thread that already exists the gate's remedy names a declaration nothing can write: a remedy naming an unreachable route, which is the class the close-out exists to remove. Resolving the conflict changes either hv's ruling or what the gate recommends, and both are hv's call (vc, 2026-09-15).
