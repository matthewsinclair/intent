A project that disables its rules wholesale gets a commit gate that tells it they were enforced.

`CriticReport::exit_code` (native/rust/crates/intentsvcs/src/critic.rs:361) returns 2 -- ABSTAINED -- only when nothing was armed AND nothing was disabled:

    if self.total() == 0 && self.disabled.is_empty() { 2 }

A project with a non-empty `disabled` and no findings falls past that arm and returns 0. That is deliberate and documented at critic.rs:336-341: the opt-out is the project's own committed decision, so the run takes the verdict its findings give and the census names what it disabled.

THE GATE THEN THROWS THE CENSUS AWAY. lib/templates/hooks/pre-commit.sh captures both streams into `$out` and reads `rc=$?`, and its rc 0 arm is exactly:

      0) ;;

`$out` is discarded, and the digest goes on to print "N of N declared language(s) enforced". The critic's own disclosure -- written at intent-cli/src/render.rs:13491 precisely because "a run the project disabled wholesale reads as a clean pass over rules it never put" -- never reaches the committer.

So at the canonical checkpoint, the one line the operator reads says enforced where nothing was. The gate is not wrong about its exit code; it is silent about its denominator, and a denominator nobody prints is a denominator nobody checks.

SIZE. One line. The information is already in `$out` at the moment it is dropped, so printing it -- or just a disabled count -- on rc 0 closes it. Changing the exit code instead would reopen the standing ruling at critic.rs:336-341 and is NOT what this asks for.

## HOW TO DRIVE A FIX TO THIS FILE, because the obvious method silently tests the wrong bytes (vc and dc, 2026-09-22)

**A WORKTREE DOES NOT TEST `lib/templates/hooks/pre-commit.sh`, AND THE HOOK REPORTS A CLEAN PASS WHILE NOT TESTING IT.** `.githooks/pre-commit.intent` is a SHIM, not a copy: it asks the binary where the gate body is and `exec`s that. `$INTENT_HOME` is refused from the environment deliberately (`install.rs`, so a stale export cannot make a v3 binary exec v2's scripts), so the shim resolves the INSTALL ROOT's body every time. vc built the fix in a detached worktree, copied the shim in, staged a file, ran `.githooks/pre-commit` and got the UNMODIFIED line -- a green from a run that could not have gone red, because it never executed the bytes under test.

**THE ONLY SAFE WAY IS TO EXEC THE BODY DIRECTLY**: `bash lib/templates/hooks/pre-commit.sh` from inside the worktree, bypassing the shim's resolution. Repointing the install root is the other route and it is FORBIDDEN -- that is the 2026-09-19 incident where `install::publish_home` wrote a scratch tree's root into `~/.local/share/intent/home` and every estate's gate on this machine resolved its guards from it for hours.

**AND THE DISCRIMINATOR IS ONE COMMAND, which is dc's and is the reusable half.** The shim trap bites exactly when the patch under judgement changes a file the shim resolves FROM THE INSTALL ROOT. A patch touching the estate's own `.githooks/pre-commit`, its config or its tests is read from the repository being committed to, and worktree-plus-shim is sound for it. A patch touching the gate body or a shipped guard is not. So before choosing how to drive a bank: `git cat-file -p <ref> | git apply --numstat | grep -c 'lib/templates/hooks/'`. Zero means the ordinary method works; non-zero means exec the body directly.

Driven against the Half B bank to check the boundary rather than assume it: that patch touches three files and **zero** under `lib/templates/hooks/`, and `git log f6ad0f990..3efed86ff -- lib/templates/hooks/` is **empty**, so the install-root bytes were identical to the worktree's and that verdict stands.
