`Report::unclaimed_digest` (native/rust/crates/intentsvcs/src/organize.rs:1101) hashes each unclaimed path exactly as stored:

    .map(|p| p.to_string_lossy().to_string())

and the stored paths are root-prefixed: `Step.path` is cloned from a walk rooted at `Project::st_dir()` / `Project::issues_view_dir()`, both built from `self.root.join(..)`.

The renderer that prints that digest relativises only the DISPLAY -- `let show = |path: &Path| project.relative(path)` at intent-cli/src/render.rs:6965 -- while the digest is appended to the same summary line untouched (render.rs:7027-7031).

So two values on one line disagree about what a path is, and the digest changes when the project MOVES although the set it summarises has not. A digest whose job is to answer "did this set change" instead answers "did this set change, or did the tree move", and nothing on the line distinguishes the two.

COVERAGE. The one test builds the `Report` directly from relative string literals (intentsvcs/tests/organize_preview_polarity.rs:395), so it never holds a project root and cannot move a tree. It asserts membership-sensitivity and order-insensitivity only. The defect is invisible to it by construction, which is why it survived.

SIZE. `Report` carries no project root, so `unclaimed_digest(&self)` cannot relativise in place. Either a root is threaded in, or `Report` carries project-relative paths from the start so that `show` and the digest stop being two homes for one question. Every recorded digest changes exactly once, whichever is chosen.

NOT THIS, AND THE DISTINCTION IS WHY (cc, 2026-09-22, on vc's instruction, recorded before the fix lands so the next reader does not re-derive it or "fix" it). `organize::observe` hashes `root.join(&entry.path)` at organize.rs:576-587, so the PLAN digest carries the project's location too. Leave it alone. It answers a different question, and three facts in the code's own vocabulary settle it: the variant a mismatch raises is `OrganizeError::TreeMoved`; its guard stands on the APPLY path and nowhere else, by explicit design, because a preview takes no irreversible step for it to protect; and its detail is `format!("planned against {}, found {}", self.digest, now)`, which names both digests. So a project relocated between a plan and its apply yields a DIAGNOSABLE FALSE REFUSAL of an act that cannot be taken back -- never a false pass. That is the opposite disposition from this digest, whose whole job is to answer a question about set membership and which fails by quietly reporting a change that did not happen.

AND THE FIX IS NOT "MAKE `Report` CARRY RELATIVE PATHS", which was the first of the two shapes named above and is the one that looks like the Highlander answer. Census taken 2026-09-22: every DISPLAY consumer already relativises (render.rs:6965, facade.rs:6073-6084, facade.rs:8475-8483, facade.rs:6458-6470, facade.rs:6816-6827, mcp.rs:1455-1461), but two consumers ACT on the paths as real filesystem locations. `prune_emptied` is handed `&report.dehydrated` and `&report.pruned_legacy` directly (organize.rs:1332, 1362) and filters candidates by `d.starts_with(root)` before `remove_dir`, so relative paths there drop every candidate and the directory prune removes nothing AT EXIT 0 -- an `IN-AG-NO-SILENT-001` violation introduced by the fix. And `facade.rs:6472` membership-tests `run.hydrated` / `run.rewritten` against `owned`, which is absolute (`carried()` filters `p.starts_with(&project.thread_dir(id))`, then `retain(|p| p.exists())`), so `wrote` silently empties and 0083's "which files THIS CALL wrote" regresses. Both breakages are `PathBuf` to `PathBuf`: no type change, no compiler help.

So `Report` carries absolute paths CORRECTLY -- it is the record of acts performed on a real filesystem, and this crate consumes it as one. The defect is narrower than the title says: a digest answering a project-relative question was derived from a representation carrying the project's location. The fix threads the root in and hands the work to `project::relative`, documented at project.rs:2211-2218 as the one home for naming a path as Intent names it, so `show` and the digest become two CALLERS OF ONE HOME rather than two homes.
