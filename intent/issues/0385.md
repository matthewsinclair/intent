After a pair change, the first write that re-renders views warns "overwrote bytes that were not the store's render -- an edit to a generated file is gone" for every view whose only difference is the footer's version stamp. Found on Laksa (laksa-vc, on the 4c172d260 pair): `intent wp start ST0112/09` warned for every view whose footer went from "Generated by Intent v3.0.1" to "v3.0.2", and nothing had been hand-edited. A warning that fires on the renderer's own stamp trains its reader to ignore it, which hides the day a real edit is lost.

Cause, read against the source at v3.0.2 (e75708756): `Facade::foreign_bytes` renders the prior estate with the running binary's `render_ctx` and compares each candidate's disk bytes to it exactly, so a view an older Intent rendered differs in the footer's version and is reported as foreign. `doctor` met the same class in issue 0309 and answered it with `views::differs_only_in_banner_version`, asked before skew is decided; the overwrite check never asks it.

Fix: `foreign_bytes` drops a candidate that `differs_only_in_banner_version` from its prior render, using the one predicate rather than a second reading of the footer. It either says nothing about it or names it separately and quietly as a stale render, the way doctor's `StaleRender` does.

Related: issue 0342 (doctor compares the banner, so every cut skews every untouched view), whose doctor half issue 0309 answered, and the release-footers issue in this batch, which removes the footer-only difference at the cut.
