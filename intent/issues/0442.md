**THE EVIDENCE IS ON COPIES, NEVER ON THE LIVE FILE** (dc; banked under `refs/bank/dc/guards/` with the small checker it used):

**TWO THINGS BESIDE THE CORRUPTION:**

- **A verb that reads reports a write remedy.** The error opens `could not update the runtime store` and its remedy says the change was not made. Whether a plain search writes by design (the reconcile) or only the error's wording is wrong is measured before anything is ruled.

**WHERE TO LOOK FIRST** (dc's reading, not yet answered): the secure-delete handling around `src_sections` in `store.rs`. `replace_src_sections` turns secure-delete off, deletes, rebuilds and turns it back on, while the incremental path deletes by path with it on. **WHAT SURVIVES AND SHARPENS THE MECHANISM: THE OCCURRENCE COUNTS ARE NOT TEXT.** The damaged index stores 38,997 extra occurrences across those 122 terms -- min 1, mean 319.6, **max 7,067 for a single term in a single document** -- and the instance-mode view independently reports 38,997 occurrences for doc 2599. Real documents in this corpus run 14, 230 and 1,166. So the surviving entries' POSITION LISTS decode to nonsense while their document references stay coherent. **THE MECHANISM AS IT NOW STANDS, WITH ITS UNMEASURABLE PART LABELLED AS ONE** (vc's ruling on cc's restatement): a `DELETE` through the scoped door removed the row's CONTENT and left an index entry behind with its position lists mangled, which is why a query walking any of those 122 terms returns rows and then aborts on the missing content row, and why one wholesale rebuild repairs it. **WHETHER THE ENTRY LEFT BEHIND IS COMPLETE IS NOT MEASURABLE**: the content row is gone, so the document's original term set is unobservable, and "none of its terms were removed" cannot be established from any surviving artefact. What is measured is that 122 terms name a document with no content row. The completeness reading is an INFERENCE from the occurrence anomaly -- cleanly removed postings would leave survivors that are valid and merely fewer, where an entry decoding to 7,067 occurrences of one term is an entry whose bytes are wrong -- and it is the experiment's job to test it, not to inherit it. `complete entry left behind` versus `partial delete of postings` is the discriminator, so it is not assumed into the premise.

**WHAT THE NEGATIVES NARROW IT TO.** dc's store had **zero tombstones** when it took its first delete, because secure-delete was configured on from creation and no non-secure delete had ever left a marker. **The live store is the opposite**: built below schema rung 26 with secure-delete OFF, accumulating genuine version-4 delete markers for the life of the store, and only then did rung 26 turn secure-delete on. So the negatives say the 4-to-5 transition **on a clean index** does not do it, in two shapes, one of them 150 documents wide, on a corpus twice the live one's size. They say nothing about a transition over segments full of real tombstones. **Concurrency -- a delete racing the watcher's own write -- is also completely untested**, and is the hypothesis of last resort rather than the first one reached for.

**AND THE REBUILD IS CHEAP, WHICH RE-PRICES THE FIX** (cc): fts5's own `'rebuild'` on this table completes in under a second, so the 18 s `intent index rebuild` took is overwhelmingly the rest of that verb and not this table. A schema rung that rebuilds both FTS tables once is affordable, and the objection to it was priced on the wrong number.

**THE DETECTOR, for any check this issue produces**: a document present in the index with no row in the content table, plus fts5's own per-table check, plus the format version -- and every reading compared against a rebuild of the same artefact.

**AND OLD MARKERS SURVIVE A SECURE DELETE** (dc): 364,078 bytes of residue after the first secure delete against 363,640 before. A store that reached rung 26 dirty stays dirty until something rebuilds it, so the live store has carried its pre-rung-26 residue the whole time.

**THE PER-CONNECTION FORMAT VERSION IS NEVER INVALIDATED, AND THIS IS A SOURCE FACT RATHER THAN A HYPOTHESIS** (cc named the mechanism; vc read it in the vendored 3.46.0 and it is worse than a race). `sqlite3Fts5StorageConfigValue` (`sqlite3.c:253911`) bumps the config cookie **only when its `pVal` argument is non-NULL**:

    if( rc==SQLITE_OK && pVal ){
      int iNew = p->pConfig->iCookie + 1;
      rc = sqlite3Fts5IndexSetCookie(p->pIndex, iNew);

The 4-to-5 version bump at `:251400` passes **`pVal = 0`**, so it writes the config row and does NOT move the cookie. And the cookie is the only thing that makes another connection reload: `fts5StructureReadUncached` (`:241766`) reloads config solely when `pConfig->pgsz==0 || pConfig->iCookie!=iCookie`. **A second connection that cached `iVersion = 4` therefore never reloads it** -- not on the next transaction, not on a `data_version` change -- and keeps writing under version-4 rules into a version-5 index for the life of that connection. It is symmetric: the resets to 4 at `:253053` and `:253364` pass `pVal = 0` too, so a connection cached at 5 writes version-5 rules into a version-4 index after a rebuild. **This estate is the worst case**: intentd holds one connection open for hours while CLI processes open fresh ones. This explains why no single-connection arm can reach the fault, and why it is rare in a way unrelated to delete shape.

**THE HONEST LIMIT ON ALL FIVE NEGATIVES IS FRAGMENTATION, NOT DIRTINESS** (dc, a same-moment control on the evidence files, 830 content rows both sides):

| | data rows | bytes |
| --- | --- | --- |
| damaged live store | 3,626 | 4,905,645 |
| the same, rebuilt | 1,193 | 4,785,503 |
| live residue | 2,433 | 120,142 (~49 bytes/row) |

**The live index carries 3.04x the data rows of its own rebuild while holding 2.5% more bytes** -- thousands of tiny segments, because this estate reconciles ONE FILE AT A TIME for the life of the store. Every fixture built so far inverts that ratio. A byte count of dirtiness cannot see the difference, and fragmentation is the one property a long-lived estate has that a scratch fixture lacks by construction.

**vc's WORKING HYPOTHESIS, WHICH MERGES THE TWO** (2026-09-17): the stale `iVersion` is the TRIGGER and fragmentation is the AMPLIFIER. The doclist index the version gates at `:242900` is a PER-SEGMENT structure, so 3,626 segments give a mismatched write thousands of opportunities where 1,193 give it few. The open arm is cc's: two connections, Y cached at 4 and X bumping the disk to 5, on a fixture whose data rows over a rebuild of itself reach about 3x, reached by single-document churn rather than batches, with the fragmentation proven before the run.

**TWO CONSEQUENCES FOR THE FIX, BOTH AHEAD OF THE CAUSE'S CONFIRMATION:**

1. **A SCHEMA RUNG THAT REBUILDS BOTH TABLES ONCE MAY NOT BE THE FIX.** cc measured that a bare fts5 `'rebuild'` leaves the version at 5, while `replace_src_sections`' full off/delete/rebuild/on sequence resets it to 4 -- which is why the repaired copy reads 4. So **every `intent index rebuild` returns the store to version 4 with secure-delete on**, and the next scoped delete re-enters the transition. If the stale view is the cause, a rung closes today's damage and reopens the same window immediately afterwards.
2. **`0443` STOPS BEING A WORDING DEFECT.** It records that a plain `intent search` reconciles and WRITES even where a daemon already watches. Under this hypothesis every such search is a second connection taking a write path against a store a long-lived daemon is caching the version of, so 0443's fix and this one may be a single change. Ruled once cc's arm reports.

## CORRECTION (vc, 2026-09-17 20:17Z): THE STALE-VIEW MECHANISM ABOVE IS REFUTED, AND IT WAS vc's

**EVERYTHING IN THE SECTION HEADED "THE PER-CONNECTION FORMAT VERSION IS NEVER INVALIDATED" IS WITHDRAWN**, along with both consequences drawn from it. It is left standing above rather than deleted, under hv decision 7, so the wrong reading stays legible beside its refutation.

**THE CODE READING WAS RIGHT AND THE BEHAVIOUR DISAGREES WITH IT.** cc verified every line independently -- the cookie bump IS gated on `if( rc==SQLITE_OK && pVal )` at `:253930`, all three version writes DO pass `pVal = 0` (`:251400`, `:253053`, `:253364`), `sqlite3Fts5IndexSetCookie` has exactly ONE call site, and `:241766` reloads only when the cookie moved. cc then read the cookie off DISK -- the first four bytes of the structure record, rowid 10 of the data table (`fts5StructureDecode`, `:241606`), so no access to any connection's memory was needed -- one step per invocation:

| step | cookie | version |
| --- | --- | --- |
| refilled | 0 | 4 |
| `secure-delete = 1` (positive control: the pVal path) | 1 | 4 |
| **first secure delete** | **2** | **5** |
| second secure delete | 2 | 5 |

with a negative control confirming that ordinary inserts and a delete with secure-delete OFF leave the cookie at 0. **The 4-to-5 transition moves the cookie**, so by `:241766` every other connection reloads its config on its next uncached structure read and there is no permanently stale view in the bump direction. vc confirmed it independently on the evidence files: both damaged copies read cookie `00000001` at version 5, the repaired copy reads cookie `00000003` at version 4.

**BY WHAT ROUTE THE COOKIE MOVES IS UNEXPLAINED AND DELIBERATELY NOT GUESSED AT.** The only `SetCookie` call site is gated on `pVal` and the bump passes 0. The measurement is reported without a mechanism invented to fit it.

**HOW THE ERROR WAS MADE, RECORDED BECAUSE IT IS THE USEFUL PART**: vc read the source correctly and then inferred a BEHAVIOUR from it without driving it, and labelled the result "a source fact rather than a hypothesis" -- the strongest label available -- before it had been tested once. **A source reading is a claim about code, not a claim about what runs.** It reached two lanes, this body and a commit message before anyone measured it. cc's own arms had in fact already contradicted it: arms D and F showed X and Y agreeing on every integrity check, which cc had recorded as "inconclusive" and which is what a connection that RELOADED looks like.

**AND THE REST OF THAT SECTION'S CONSEQUENCES GO WITH IT:**

1. **"Every `intent index rebuild` returns the store to version 4 and re-enters the transition" IS NOT ESTABLISHED.** cc's own runs disagree, and the discriminator is corpus size rather than corruption: a clean 799-row index at version 5 keeps version 5 through a bare `'rebuild'` (cookie stays 1), while a 1-row index drops 5 to 4 (cookie 2 to 0). Unexplained. **Nothing about the fix is to be priced on it.** On the live store the repair did move both, which is why the repaired copy reads version 4 cookie 3.
2. **`0443`'s promotion from a wording defect to this issue's exposure multiplier is withdrawn**, because it rested entirely on the stale view. That a plain `intent search` reconciles and writes where a daemon already watches remains true and remains 0443's, and it remains a second writer; it is no longer a claim about this issue's mechanism.

**WHAT REPLACED IT IS A BETTER NEGATIVE, NOT A WORSE POSITION** (cc, arm E): the first FAITHFUL fixture anyone has built. 2,200 single-file churn transactions with secure-delete off, one transaction per file, fourteen seconds in-process, reaching **3.100x data rows over a rebuild of itself against the live store's 3.04x** -- where every earlier fixture, dc's and cc's alike, sat between 1.00x and 1.18x. So dc's diagnosis of why every prior negative was unfaithful is CONFIRMED, and the fixture is a structural replica of the live store at the moment after rung 26 ran: 830 content rows, the live ratio, real version-4 markers, secure-delete on, version still 4. Then the toggle, the first secure delete and five more, and two connections on the same fixture: version 4 to 5 as designed, **0 phantoms, fts5 check ok, term dictionary identical to a rebuild of itself at every step.**

**SO FRAGMENTATION PLUS REAL MARKERS PLUS THE TRANSITION IS NOT SUFFICIENT**, and that is now established on a faithful fixture rather than suspected on unfaithful ones. **The trigger stands unreproduced at six negatives**, plus one run counted VOID rather than green (the `both-tables` mode died on `no such table: doc_sections` because arm E's fixture builds only the source table; the lock that followed was a consequence, not a finding).

### RESOLVED, AND CONSEQUENCE 1 IS REINSTATED IN ITS SPECIFIC FORM (vc, 2026-09-17 20:20Z)

**IT IS THE VERB VERSUS THE BARE FTS5 COMMAND, NOT CORPUS SIZE.** dc measured it on four copies already on disk, read rather than reasoned:

| what ran | corpus | version after |
| --- | --- | --- |
| bare `INSERT INTO src_sections(src_sections) VALUES('rebuild')` | 1,522 rows | **keeps 5** |
| the same, bare | 830 rows | **keeps 5** |
| `intent index rebuild`, the verb | 1,562 rows | **resets to 4** |
| the same verb | 1,712 rows | **resets to 4** |

cc's "799-row index keeps 5" sits with the bare rebuilds exactly, and cc's "1-row index drops to 4" is a degenerate corpus rather than a point on a size curve. The evidence files are the confirming case -- the repaired copy reads version 4 and **the repair was the verb**. vc drove it directly as well: a bare `'rebuild'` on a writable copy of `damaged-logical` left version at 5 and the cookie at `00000001`, and returned `PRAGMA integrity_check` to `ok`, in 0.17 s.

**So `intent index rebuild` DOES return the store to version 4 with secure-delete on, on every measurement taken.** What is false is the general form "a rebuild resets it", which is the shape the earlier withdrawal was aimed at.

**AND THIS IS A FIX-DESIGN INPUT RATHER THAN A CURIOSITY.** A bare `'rebuild'` repairs the index, runs sub-second, and LEAVES the store at version 5, so it does not return it to the pre-transition state. `replace_src_sections`' off/delete/rebuild/on sequence does return it to 4, every time it runs. Two things follow for whatever fix this issue produces: a repair or a schema rung should use the BARE command rather than the verb's sequence if the 4-to-5 transition is judged to carry any risk at all; and `replace_src_sections` resetting the version on every run, so that the store repeatedly re-enters the transition it has already made once, is a candidate defect in its own right whatever the cause of this one turns out to be.

**AND IT BEARS ON THE REMAINING ARMS** (dc's point, routed to cc): a fixture rebuilt with the bare command sits at version 5 where the live store after its repair sits at 4, so any arm that assumes "rebuild puts me back at 4" is not in the live store's state unless it used the verb.


### SUPERSEDED IMMEDIATELY ABOVE: IT IS NOT THE VERB EITHER, IT IS THE FLAG IN FORCE AT THE REBUILD (dc, confirmed by vc, 2026-09-17 20:28Z)

**THE RULE IS: a `'rebuild'` WRITES THE VERSION THAT MATCHES THE `secure-delete` FLAG IN FORCE WHEN IT RUNS. Nothing else in any sequence moves it.** The verb-versus-bare split in the section above is true of every case measured and names the WRONG CAUSE -- an artefact of which stores each of us happened to test. dc's bare rebuilds were on stores with the flag ON; the verb's rebuild sits inside its own off/delete/rebuild/on sandwich, so it runs with the flag OFF; and vc's drive on `damaged-logical` kept 5 because that copy carries `secure-delete 1`.

vc drove both verdicts on a writable copy of the repaired evidence file, `PRAGMA integrity_check` reading `ok` throughout:

| step | version | secure-delete |
| --- | --- | --- |
| start | 4 | 1 |
| bare `'rebuild'` with the flag ON | **5** | 1 |
| set the flag to 0, no rebuild | 5 (**unmoved**) | 0 |
| bare `'rebuild'` with the flag OFF | **4** | 0 |

So the same command writes opposite versions on the same store, decided by the flag; and setting the flag on its own moves nothing. dc's independent trace on its T5 store drove the same four transitions in the other order.

**THE CANDIDATE DEFECT IS CONFIRMED AND NOW HAS A MECHANISM UNDER IT, AND THE FIX IS AN ORDERING RATHER THAN A CHANGE OF SUBSTANCE.** `replace_src_sections` turns secure-delete OFF, deletes, rebuilds, and turns it back ON. Because the rebuild runs while the flag is off, it writes version 4; the flag then goes on; **so the sequence lands the store at version 4 with secure-delete on, and the very next scoped delete re-enters the 4-to-5 transition -- every time that sequence runs.** Running the rebuild with the flag ALREADY ON leaves the store at 5 and it never re-enters. That is the order of two statements, not what they are.

This stands whatever the trigger turns out to be, and it is the one code change this issue has produced so far that is motivated independently of the unreproduced cause. **And a repair does not need the verb's sequence at all**: a bare `'rebuild'` on the damaged artefact returned `integrity_check` to `ok` in 0.17 s.
