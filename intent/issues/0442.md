**A plain `intent search` on an affected term fails on this estate's own store**, with the installed pair `ea81a6c58`: `intent search argmatches` exits 1 with `could not update the runtime store / sqlite: database disk image is malformed / Error code 267: Content in the virtual table is corrupt`. `intent search --context argmatches` and `--context store` both exit 0, so the symbol path still answers. Found by dc on 2026-09-17 while making a store copy for the guards rehearsal; nothing of dc's wrote to the live store and `intent index rebuild` was not run.

**THE EVIDENCE IS ON COPIES, NEVER ON THE LIVE FILE** (dc; banked under `refs/bank/dc/guards/` with the small checker it used):

- A page-exact `.backup` of the live store fails `PRAGMA integrity_check`, and the source's mtime and WAL size did not move across the copy.
- Judged with the SQLite the pair is built from -- 3.46.0, `libsqlite3-sys` 0.30.1, the version that wrote the index -- it reads `malformed inverted index for FTS5 table main.src_sections`. The system 3.54.0 and Homebrew 3.53.4 both say `fts5: checksum mismatch`, so this is not a version artefact.
- `doc_sections` passes its own integrity check. Only `src_sections` is affected.
- **The rows are intact**: the content table holds all 829 sections, and FTS5's own `rebuild` on a copy returns integrity to ok.
- **The fault is stale postings, and nothing is missing.** Diffing the term dictionaries (`fts5vocab`) of the live snapshot against a rebuilt copy: both hold the same 16,014 terms, 122 terms name MORE documents in the live index than in the rebuilt one, none name fewer, and none differ in occurrences alone. A query that walks a damaged segment returns rows and then aborts: on the copy, `MATCH 'argmatches'` returns 4 rows and then errors, where the rebuilt copy returns 6.

**UNMEASURED**: whether every plain text search now fails, or only the terms that reach a damaged segment. One reading was taken and the form was not run again, because a search takes a write path (below).

**TWO THINGS BESIDE THE CORRUPTION:**

- **Nothing reports it.** `intent doctor` reads 0 findings over this store, and the symbol path answers normally, so an estate can carry this and look clean.
- **A verb that reads reports a write remedy.** The error opens `could not update the runtime store` and its remedy says the change was not made. Whether a plain search writes by design (the reconcile) or only the error's wording is wrong is measured before anything is ruled.

**WHERE TO LOOK FIRST** (dc's reading, not yet answered): the secure-delete handling around `src_sections` in `store.rs`. `replace_src_sections` turns secure-delete off, deletes, rebuilds and turns it back on, while the incremental path deletes by path with it on. Whether SQLite 3.46.0's FTS5 carries a known secure-delete defect is the other half, and SQLite's own changelog between 3.46.0 and current answers it.

**WHAT THIS ISSUE ANSWERS** (vc, 2026-09-17, under hv's pen; cc owns it):

1. **The cause, with evidence, before any change is proposed** -- our own delete path, or the SQLite the pair bundles.
2. **The fix that stops it being produced**, sized by what the cause turns out to be.
3. **Detection**, because `doctor` is silent over a corrupt index on its own store. The cheap form is an integrity check of the FTS tables.
4. **Whether a plain `intent search` is a write path by design or only in its error's wording.** The wording alone is a small row of its own; a read verb that writes where a daemon is running is this issue's.

**THE LIVE REPAIR RUNS BEFORE THE NEXT REBUILD** (vc), because the restart at the end of a rebuild makes intentd re-index the files 0441's landing changed, which writes into the damaged index through the very path under suspicion. It runs on dc's measurement of whether `intent index rebuild` returns `PRAGMA integrity_check` to ok on a copy; if it does not, the repair is FTS5's own `rebuild` statement and that is vc's call to make.
