intentd's watcher arms fail inside the release gate right after the full workspace build, and pass alone at the same load.

**Measured 2026-09-19** on the 3.1.0 cut. Six arms went red twice in `dvb build release`'s cargo gate on identical intentd bytes at a one-minute load under 10: `the_daemon_lists_the_project_registry::a_project_added_to_the_registry_is_listed_without_a_restart`, `daemon_watch::one_external_edit_costs_a_bounded_number_of_ingests`, `daemon_watch::a_change_to_a_path_outside_the_sync_scope_drives_no_ingest`, `daemon_watch::an_external_edit_reaches_the_store_with_nobody_running_sync`, `daemon_watch::a_burst_of_edits_is_debounced_into_far_fewer_ingests`, `a_source_edit_reaches_the_index_and_costs_canon_nothing`. Every panic is a watcher wait expiring (ten seconds of polling for the registry arm, `ATTEMPTS` of `PAUSE` for daemon_watch). Alone, in a private worktree at the same HEAD under the gate's environment at load 5, intentd's suite passed 38 of 39, the one red the ruled flake a_daemon_outlives_nobody. The gate runs these arms seconds after building every workspace test target and running intent-cli's suite, and its once-only intentd re-run two minutes later passed on every run where it fired.

**What this is not:** a watcher defect. What it is: arms whose delivery windows assume an FSEvents pipeline that has nothing queued, on a host where a workspace build has just written tens of thousands of files.

**The ask:** either the arms wait for the watcher to acknowledge its first event before the timed wait begins, or the gate runs intentd's suite last, after the filesystem has settled, and the driver's family list (`4da3ca19d`) stops being the thing that decides. M. The records are vc's scratchpad `release-red-1.md` and the gate logs `intent-release-gates.kwRZAG3elO` and `.4sA17TkSWL` of 2026-09-19.



**Landed, not closed** (2026-09-19, in the commit that carries this paragraph, patch-id b654c01e7, test-only). Option (A) as ruled: each of the six arms first writes a sentinel (a thread file, a source file, or a registry entry) and waits up to `ARM_ATTEMPTS` (`ATTEMPTS * 12`, counted in tries, never a clock) for the watcher to act on it, and only then starts its own bounded wait. Two cold gate-shaped runs, each `cargo build -p intentd && cargo test --workspace --no-fail-fast` in a private worktree: with (A), load 14.66 at the start, the workspace 0 failed (intent-cli 321 + 1 + 716, intentd 9 + 5 + 39, intentsvcs 297 + 1510, testkit 9), all six arms green; the CONTROL on the unfixed base, load 70.38, also 0 failed with all six arms green. So that instrument does not reproduce the red, and these runs show (A) breaks nothing, not that it fixes anything. **Closing condition:** the next real `dvb build release` gate passes all six arms first time. The driver's load-sensitive family list stays as it is until then.
