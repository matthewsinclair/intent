## The general form

**A derived artefact is held to its source by a mechanism that FAILS when the two diverge, or it is held by nothing.** Discipline is not a mechanism, and neither is a remedy that a reader has to know to run. This estate already has one worked example of the mechanism done right: the rules index is deliberately duplicated into `CLAUDE.md` and `AGENTS.md`, and a drift test holds the pair byte-identical. The duplication is safe because divergence breaks something, not because anyone is careful.

## The partition

Every generated surface in this project sits in exactly one of two states, and the two are different defects with different fixes:

- **A comparison reaches the surface and reads the wrong source for it.** That is 0495's subject.
- **No comparison reaches the surface at all.** That is this issue's subject.

The partition is exhaustive, which is why these are two issues rather than one: 0495 ends at what the whiteboard comparison reads, and this one ends at whatever holds a surface that `render_all` never enumerates. Neither blocks the other and neither is intelligible only beside the other.

## CORRECTION 1: doctor DOES compare the store against canon, and this issue originally implied otherwise

The first version of this body said of 0495's subject that "both sides of the comparison derive from one source, so a store that has moved on is outside the test entirely". **That is true of `views::skew` and wrong about `doctor`, and the difference matters.**

`doctor` carries a separate store-versus-canon arm: it rebuilds a store from committed canon, diffs it against the runtime store's `derived_dump`, and reports `StoreStale`. cc positive-controlled it in both directions -- hand-edit a thread's title in canon so it disagrees with the store and it fires; restore the file and it goes quiet. **So a check does look. It works. Its dump simply does not carry whiteboard items.** That is a gap in what an existing comparison COVERS, not the absence of a comparison, and the original wording overgeneralised from one function to the whole command.

**And the bound on this correction, so it does not become the next overreach (cc's wording):** a store that has moved on is outside `views::skew`, and INSIDE doctor's store-versus-canon arm for every family whose rows reach `derived_dump`. Threads demonstrably reach it; whiteboard items demonstrably do not. **Which other families the dump carries is established by nobody**, 0495 does not claim it, and neither does this issue.

**Two properties of that arm belong beside it, both cc's.** Where it fires it is an ADVISORY and is not counted in the verdict, deliberately, because on a shared tree a store ahead of canon is the normal state during another node's write. So `doctor: 0 finding(s)` can print with a store-stale advisory directly above it, and a reader who checks the count instead of reading the output learns nothing in either case.

## CORRECTION 2: the prediction that this extends to threads and issues is DISCONFIRMED

The first version predicted that any canon file a verb fails to write after the store commits would have the same property, threads and issues included, since they pass through the same `ingest::read`. **cc drove it instead of extending on it, and it does not hold.**

The control: with `intent/.canon/st` refusing writes, `intent st start ST0001` lands the row and warns that writing the views did not, naming the refused temp file. Canon on disk does not move, so the store is ahead of it in exactly the shape the board case has. `doctor` then prints `residue: view-skew -- 1 finding`, `advisory: store-stale -- 1 finding`, and a verdict of `1 finding(s)`. **Same shape, same direction, same refusal mechanism -- reported for a thread, silent for a board.**

So 0495's scope is whiteboard items rather than `ingest::read`, and the partition above survives both outcomes, which is some evidence that the split between these two issues is a real one rather than a convenient one.

## What `doctor`'s skew reach actually is

`doctor::file_checks` calls `views::skew`, which iterates `views::render_all` and byte-compares each rendered view against the file on disk. Where it applies the check is strong -- a live render against the bytes, not a heuristic. So the reach of skew detection is exactly what `render_all` enumerates, and that is four families:

- thread views, per canon thread
- issue views, every issue, open or closed
- whiteboard boards and inboxes, one per ordered node pair
- the two aggregate views, `intent/st/steel_threads.md` and `intent/todo.md`

**Anything generated that is not in those four families is a surface `doctor` cannot report skew on, by construction rather than by oversight.**

## The worked instance: AGENTS.md

`AGENTS.md` is generated from project state by `intent agents sync`. It is not in `render_all`. `crates/intentsvcs/src/doctor.rs` contains zero occurrences of `agents` or `AGENTS`; `views.rs` names the file once, in a comment about the banner convention, and nowhere in the enumeration. So it can drift arbitrarily from the state it is generated from with `doctor` reading clean, and the only signal that would say so lives in a separate command, `intent agents validate`.

**Its consequence is worse than a board's, for a reason the estate has already written down.** `AGENTS.md` is the primary tool-agnostic contract, the file every agent is told to read first -- and `CLAUDE.md` records that it is the one file the Claude Code agent never receives. So drift in it is invisible to `doctor` AND to the reader it most affects. That combination is what the `CLAUDE.md` duplication plus its byte-identity test was built to answer for one section of it; the rest of the file has no such thing.

## The question this issue is actually asking

Not *where else can a view go stale silently*, which invites a list that rots. Instead:

**Which generated surfaces are outside `render_all`, and what holds each of them to its source instead?**

That has a per-surface answer, and where the answer is "nothing" it names the missing mechanism rather than adding a row to a list.

## Closed 2026-09-21: landed at 2aceb6060

**The ruling.** hv put 0496 in the 3.2.0 cut ("Definitely in", 2026-09-21, relayed through cc and vc). The mechanism is the one dc's walk proposed: a `doctor` advisory that asks `canon::apply` in report mode. `canon::apply` is the path `intent claude upgrade` without `--apply` already takes, so the comparison and the write cannot disagree, and no second renderer and no view are added (`root_files_generated.rs:302`). Patch-id `115808741`, identical to the judged bank `refs/bank/dc/0496/patch`.

**A premise the walk and the ruling both carried, corrected by the drive (2026-09-21).** The walk said the templates are compiled into the pair, and vc's ruling repeated it as the reason the class is uncounted. It is false. `canon::template` (canon.rs:363) and `rootfiles::render` (rootfiles.rs:214) read `<install root>/lib/templates` from disk at run time, and only the footer's version is compiled in. The advisory stays uncounted on two facts that were driven instead. First, a newer Intent install reads every project behind until `claude upgrade --apply` runs there: the footer version, plus whatever the templates changed. Second, in this repository the install is the working copy, so a template edit puts the tree's own root files behind on save, and a counted class would refuse the commit that changes a template.

**What report mode needs, driven on the 46131238e pair in scratch projects under an isolated HOME.** It needs the install root, which `install::home()` resolves from the running binary's own path, not HOME. The git hooks directory is optional: with no repository, `canon::hooks_dir` is `None` and the gate steps are skipped. Report mode writes nothing. Before the change, a line appended to `CLAUDE.md` and to `.git/hooks/post-merge.intent` after an `--apply` left `doctor` at `0 finding(s)` while the dry `claude upgrade` listed both. With the worktree build, `doctor` names both under `advisory: root-file-behind -- 2 findings, not counted in the verdict` at rc 0, and `--format json` carries `"class":"root-file-behind"` per file.

**As landed.** A new `FindingClass::RootFileBehind` (`root-file-behind`, rank 6 beside `stale-render`) is in `is_actionable`'s exempt set, so never counted, and in `is_shown_by_default` for `StoreStale`'s reason: a `doctor` reading 0 while `CLAUDE.md` is behind was the defect. `doctor::root_file_findings` reports one finding per `Applied.written` path that EXISTS, project-relative. On a fresh `intent init`, report mode lists ten absent seeds and hooks of twelve, and reporting them would put a permanent advisory on every project that never ran `claude upgrade`. A held or preserved file is the project's and is never listed as written. The remedy names `intent claude upgrade --apply --skip-settings`, or `intent claude upgrade --apply` for `.claude/settings.json` and `.mcp.json`, which `--skip-settings` leaves alone. **The pre-commit carrier is left to `hook_findings`**, which already reports it behind its template (a hidden `advisory`) and knows whether the shim or the gate is its comparand, so the new class does not report one fact twice. When the install root cannot be resolved, or `canon::apply` refuses, the arm reports an `advisory` naming the cause rather than nothing.

**The test**, `intentsvcs/tests/doctor_reports_a_root_file_behind_its_template.rs`, first asserts that `install::home()` under `cargo test` equals `testkit::repo_root()`. The test binary sits in the in-tree target, so the first ancestor carrying `lib/templates` is the repository. That is where a fixture differs from an installed project, and a target moved out of the tree fails there by name. Then come three states on one fixture. Quiet after `canon::apply`. `CLAUDE.md` and `.claude/settings.json` moved off their templates are both named, each with its own door, with `actionable()` and `exit_code()` unchanged. Quiet again after `canon::apply`. **With the arm's call removed from `examine`, it fails at :83**, finding `[]` where it expected the two files.
