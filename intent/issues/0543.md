Found by ic on 2026-09-23 while re-reading 0520's CHANGELOG entry, every link read in the source at HEAD. It is not yet driven on screen: ic drives it in a pty after the tail run ends, and the fix's arms drive it through run.rs's test Source.

**What happens.** 0520 made the explorer follow the store. The omnibox matches and jumps against `app.index` (tui/app.rs:545-546, :953). That index is rebuilt in two places only: at startup (tui/run.rs:638), and on the idle tick's follow_the_store (run.rs:591-593), which rebuilds it only when `index_owed` is set. `index_owed` is set in one place: when `source.moved()` answers true (run.rs:579). `source.moved()` is Live's catch_up (render.rs:6264-6265), and it answers true ONCE per store change, because `Facade::catch_up` records the change as seen (facade.rs:4203-4211).

`Live::rows()` also calls catch_up before every read (render.rs:6211), and discards its `Ok(true)`. So whichever read catches a change first consumes it. When that read is a key-driven one, the next idle tick sees `moved() == false`, `index_owed` stays false, and the omnibox keeps the entities from before the change. A key-driven read comes first:

- after every `/` command, which runs in-process (tui/edit.rs:317-322) and is followed at once by a re-read (run.rs:849). So `/st new "X"` puts X in the list on screen, and the omnibox cannot find X;
- after every editor hand-off, whose re-read is at run.rs:865. A title changed there keeps its old spelling in the omnibox;
- after any key that re-reads rows before the 500 ms idle tick fires, so an outside write can be lost to the omnibox too.

The index recovers only at the next store change that an idle tick sees first, or at a restart.

**What the fix has to do.** The moved signal survives whichever read takes it: Live records that catch_up answered true on any path, and the loop reads that record to set `index_owed`. The existing may_reindex gate still holds the dropdown steady under a typed query. The arms: a `/` command's new entity is found in the omnibox, and a key-driven read that catches an outside write still reindexes.
