**AN intentd STARTED WITHOUT `CLAUDE_CONFIG_DIR` SEES NO CLAUDE SESSION, AND THE ESTATE PAGE MARKS EVERY RUNNING SLOT ORPHANED.**

**Observed by devbin-vc on rhadamanth on 2026-11-01, and relayed to intent-vc the same morning.** The estate page, which intentd serves, marked every running slot ORPHANED, while the CLI's census, `intent estate status`, saw every session. devbin-vc's reading: intentd "runs without CLAUDE_CONFIG_DIR and so sees no Claude sessions".

**Measured by intent-vc on rhadamanth on 2026-11-01.** The running intentd was pid 62625, `/opt/homebrew/bin/intentd` (brew 3.2.8), up 2:19:08 at 08:37:36Z by date -u, so started near 06:18Z. Its environment carried `HOME` and no `CLAUDE_CONFIG_DIR`. On this machine `CLAUDE_CONFIG_DIR` is `~/.config/claude` and `~/.claude` does not exist. At 08:39:21Z the CLI's census listed 24 sessions. `intent estate status --daemon` refuses, because no daemon answers that verb, so the daemon's own view was read only through the page.

**Where it comes from.** `userstate::claude_dir` (`native/rust/crates/intentsvcs/src/userstate.rs`) takes the Claude directory from the process's own `CLAUDE_CONFIG_DIR` and falls back to `$HOME/.claude` (issue 0604), and intentd inherits whatever environment started it. The LaunchAgent plist that `intent daemon start --at-login` writes (`launchagent::write_plist`) sets `ProgramArguments` and no `EnvironmentVariables`, so a daemon that launchd starts at login has the same blind spot on any machine that sets `CLAUDE_CONFIG_DIR`. devbin-vc's words: "decision 98's at-login enrolment must carry that variable".

The menubar app that was running (pid 8368, a Debug build from `~/.local/state/intent/build/macos`, up since 2026-10-31 21:32Z) carried none either. It starts, stops and restarts the daemon through `IntentCLI`, whose `environment()` takes `PATH` from the login shell but not `CLAUDE_CONFIG_DIR` (`native/macos/Intent/Intent/Services/IntentCLI.swift`, `DaemonService.swift`).
