## 2026-07-29 — v2.17.4 (issues 0005 + 0006 + 0007 + 0008)

- **Four issues fixed + closed as a patch, no ST (standing hv fix-under-issue ruling), in two pairs that each shared one root cause.**
- **0006 + 0007 (high, `bin/intent_acceptance`) — a `sed` non-match is invisible, in both directions.** READ side: the field extractors were bare `sed -E 's/.../\1/'`, and sed prints the input unchanged when a substitution does not fire, so each was total BY ACCIDENT and its failure value was a plausible-looking one — `status: **green` came back as the entire AT line, compared false against `green`, and gated a green test as unsatisfied in silence (eleven rows on one live Lamplight thread understated it by half, and the understated gate is what routed the thread for triage). WRITE side: `ac satisfy` substituted into a ` -- evidence:` segment a non-test AC need not carry; sed exits 0 on zero substitutions, so a no-op write was indistinguishable from a real one and the `ok:` printed regardless — the tool that records verified state reporting success having written nothing. Fixes: `extract_field`, THE extraction seam (match before substitute, one pattern for both uses so they cannot drift, empty on non-match); `assert_written`, post-state verification on every mutation (verifies the RESULT not the mechanism, so it survives pattern drift and also catches a write that fired but wrote the wrong value); `ac satisfy` made total over bare and tailed rows by rewriting the tail rather than substituting into one that may not exist.
- **New diagnostics that WARN and do not block.** Out-of-vocabulary AT statuses and unclosed `(non-test` markers are now named on stderr by every reader, quoting the required form. Deliberately not a new block: unlike a malformed id — which vanishes from the count and lets the gate go VACUOUS, hence ST0044's F1 block — these leave their criterion uncredited, so the gate already failed closed. It failed closed SILENTLY, and the voice is the whole fix. `at green` and `ac satisfy` now diagnose the row rather than reporting the conclusion the parser reached ("is test-backed") in place of the cause the author can act on.
- **0007's fix 3 (tolerate markdown emphasis on read) deliberately NOT implemented.** The vocabulary is documented in every contract's own preamble, so emphasis in a controlled field is author error, not a dialect; and tolerance would not stop at stripping `*` — the live reproduction carries trailing prose after a `;`, with no principled stopping point. hv's own caution in the issue decides it: leniency without a diagnostic just moves the silence. Consequence: the Lamplight rows do not flip on upgrade and need rewriting, but the tool now names every one.
- **0005 + 0008 (medium) — a generator asserting into a consumer repo something true only where the tool lives.** 0005: `intent lang init` wrote ``rule pack at `intent/plugins/claude/rules/<lang>/` `` into the consumer's RULES.md, where `lang init` never vendors that tree, so it dangled by construction in every project — inside a tool-managed block no project could correct locally. Now names the command (`intent claude rules list --lang <lang>`). **Widened beyond the report, because as specified the fix would have healed nothing:** the writer skipped any language already present, so every affected project — which is every project that had run `lang init`, by definition — would have kept the stale text for good. Made an upsert. The needle identifying an entry existed in three hard-coded copies; unified into one matching ANY revision of the wording, which is what lets the upsert recognise a pre-fix entry. The third copy was found by TESTING, not reading: `lang remove` had silently stopped removing entries. Both patterns begin with `- `, so every grep against them needs `--` or grep parses them as an option bundle.

## 2026-07-24 — v2.17.3 (issue 0004: the close-gate's own vacuous pass)

- **The acceptance close-gate reported a pass for a target it never evaluated — fixed + closed as a patch, no ST (standing hv fix-under-issue ruling from 0002/0003).** Surfaced by hv in Lamplight while closing ST0290/WP-04: `intent ac gate` returned exit 0 with no output, which is also exactly what a genuine pass looks like, so the close had to be verified via `ac status` instead. Root cause: an unresolvable target degraded to an EMPTY acceptance-criterion set, and each command in the `ac`/`at` family then reported its own flavour of vacuous success over that emptiness — the gate found nothing unsatisfied and exited 0, `ac status` printed `0/0 satisfied`, `ac list` printed no rows. "This target does not exist" and "this target has nothing unsatisfied" were the same internal state, and only the second was ever reported. The irony is the point: this is the precise failure mode the close-gate exists to prevent (ST0044/ST0048), reproduced inside the gate itself.
- **Fix — resolution as a distinct, failable step.** `resolve_target` in `bin/intent_acceptance` is now THE target resolver for the whole family: it normalises the ST id, zero-pads the WP, resolves the thread, and — new — resolves the `/NN` segment, which nothing validated anywhere before. `ac list` / `ac status` / `ac satisfy` / `at list` / `at red|green|na` resolve through it (error + exit 1); `ac gate` resolves through the same call and renders BLOCKED + exit 1. Only the presentation differs — the gate is read by machines through `$?`, the readers by humans through stdout. `acc_path`, which each reader re-entered separately and the gate never called at all (the asymmetry that left the gate without even the steel-thread check its own sibling `status` had), is retired in favour of `acc_file` over the already-resolved target. New `resolve_wp_dir` in `bin/intent_helpers` — the WP analogue of `resolve_st_dir`, composing with it; the three `bin/intent_wp` sites that resolve an existing WP now share it (the fourth, `wp new`, builds the path of a WP that does not exist yet, so it correctly keeps its own concatenation).
- **Every verdict is announced, PASS included.** Silence-on-success was the gate's own camouflage: a verified 23/23 and an evaluated-nothing were byte-identical on stdout, which is why the hole survived three releases of daily dogfooding. `PASS` lines now join `EXEMPT` and `BLOCKED`. The ST0044 WP-lenient rollup is preserved but granted only to a work package that EXISTS, and announced when taken rather than inferred from a zero count — a typo'd `<st>/99` matches zero ACs for the same arithmetic reason a genuinely AC-free WP does, so only a directory probe separates them.
- **Companion fix:** `parse_wp_specifier` fed the `/NN` segment to a bare `10#` expansion, so `intent wp show|start|done <st>/abc` aborted with raw bash noise (`10#abc: value too great for base`) rather than an Intent error — an unhandled failure wearing the mask of one. Guarded once in the shared helper, fixing the `ac`/`at` family and the `wp` verbs together. Zero-padding tolerance unchanged (`ST0055/3` and `ST0055/03` both resolve).
- **hv's proposed fix item 4 deliberately NOT actioned** — uniform non-zero exit on a BLOCKED `ac status`. The reported inconsistency does not reproduce: `ac status` exits 0 on BOTH BLOCKED shapes here (`cmd_ac_status` has no `exit` on any path), and `intent_acceptance_cli.bats:111` asserts exactly that with `assert_success` on a `0/3 BLOCKED`. The encoded design looks deliberate and worth keeping — `status` is the human-facing REPORTER whose verdict is its stdout, `gate` is the machine-facing GATE whose verdict is its exit code, which is why `gate` exists as a separate command. The `ST0290/99` observation behind the item is fixed regardless, by resolution: that target no longer reaches the point of printing a misleading `0/0 satisfied -- BLOCKED`. Left for an hv ruling as its own issue if wanted.
- Six guards added to `acceptance_close_gate.bats`, each verified RED against the pre-fix binary before going green — the file's own subject matter makes a vacuous test the standing hazard, and one of the six guards the OPPOSITE failure (that the legitimate WP-lenient rollup is not over-tightened). Full suite green (matts, external); critic-shell clean on all three changed files. Canon: `working-with-llms.md` D11 records that the rollup requires an existing WP and that every verdict is reported. Tag `v2.17.3` (`2828f89`), wrap `5793d7d`, both remotes + GitHub release. CHANGELOG `[2.17.3]` is the release note (patch precedent).
