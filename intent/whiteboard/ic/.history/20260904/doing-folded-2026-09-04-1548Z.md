## DOING 1 -- `0234` / `WP-18`: the store growth defect -- **FIXED, AND MY FILING WAS WRONG TWICE**

**BOTH MECHANISMS FIXED, TESTED AND POSITIVE-CONTROLLED. UNCOMMITTED.** The corrected account lives in the issue body itself (`intent issues show 234`), not here -- **a filing whose premise is wrong sends the next reader down the same path, so it was corrected at the source rather than annotated on a board only I read.**

**WHAT I GOT WRONG, KEPT BECAUSE THE ERROR IS THE REUSABLE PART.** I filed _the `DELETE` never runs_, on the evidence that rowids stay contiguous `1..N`. **The `DELETE` is fine.** FTS5 keeps its content in an ordinary rowid table, so after a wholesale delete the next insert starts at 1 again -- **contiguous rowids are exactly as consistent with a working delete as with a broken one, so the evidence never discriminated between the two hypotheses it was offered as proof of.** I also banked `INSERT INTO doc_sections(doc_sections) VALUES('delete-all')` as the obvious fix. **SQLite refuses it here** -- _"'delete-all' may only be used with a contentless or external content fts5 table"_ -- so it would have failed at runtime. Driving it rather than assuming it (W14) is the only reason that is not in the tree.

**MECHANISM 1 -- three derivations of the prose index, disagreeing.** `ingest::read` was correct; the restore path in `facade.rs` was correct; **the mutation path dropped only `work-package`** while `collect_wp_text` also emits two kinds of `thread` section -- so every mutation left one more copy of every thread's prose, forever. **The same path never derived issue prose at all**, so an `issues add --body` body reached the FTS index only at the next full ingest: the same defect in the opposite direction, one code block, one cause. **Now `ingest::sections_of` is the only derivation and all three callers use it**; `collect_wp_text` is `collect_thread_prose`, because a filter written against the old name was a reasonable mistake to make.

**MECHANISM 2 -- the inverted index is tombstoned, never truncated, and THIS is where the gigabytes were.** `DELETE FROM` an FTS5 table writes a delete marker per term rather than removing it. **Nothing reports it**: rows correct, content table the right size, searches correct, and `VACUUM` reclaims none of it because tombstones are live data. Laksa _after_ mechanism 1's rows were repaired: 859 sections, 5 MB of content, **589 MB of `doc_sections_data`**. `write_doc_sections` now follows its `DELETE` with the fts5 `'rebuild'` idiom, against an already-empty content table.

**REPAIRING THE ESTATE NEEDS NO TOOLING -- ONE ORDINARY `intent sync --to-store`.** Measured on a copy of Laksa with the fixed binary: rows 48,524 -> 859; `doc_sections_data` 589 MB -> 1 MB; `intent st list` 1536 ms warm / 6807 ms cold -> **54 ms**. **The file stays 2.3 GB and that turns out not to matter**: a `VACUUM` takes it to 14.8 MB and the timings come back 54-60 ms, ie unchanged. **Reclaiming the file is a disk question, not a speed one, and the two must not be sold together.**
