**SHARED-CHECKOUT MECHANICS.**

- **`git commit --only` PLUS A STAGING HOOK LEAVES THE FILE STAGED BEHIND HEAD, AND THE RESIDUE ACCUMULATES.** Measured 2026-08-28 in a scratch repo with a control, on Conflab's hook shape (prettier/`mix format` reformat, then `git add`). The COMMITTED CONTENT is always correct -- that half of the rule works and it never sweeps a foreign staged entry. What breaks is the INDEX: one stale pre-format entry per file committed, monotonically, so **`git diff --cached --name-only` is EMPTY stops being usable** -- and that is the cheap check that detects a peer mid-write before you `git add`. **A commit discipline adopted to stop foreign entries being swept slowly manufactures the very condition that makes sweeping likely, and it cannot be relaxed later because the index is dirtier by then.** Remedy, measured: append **`&& git reset -q -- <paths>`**; index returns to baseline, committed bytes identical. **It is the hook+`--only` INTERACTION, not `--only` alone** -- an estate whose hook does not stage is unaffected.
- **I SUSPECTED THE REFORMAT WAS LOST AND IT IS NOT.** Committed blob was identical under plain and `--only` in every arm. **Recorded because a killed hypothesis that reached nobody is the cheapest kind, and this one was one message away from three nodes carrying it.** Its neighbour died the same morning: inherited bad stamps CANNOT wedge a post-hop board -- all three clock-guard checks are add-only by construction (`git diff --cached --unified=0 | grep '^+'` at `:218`, check C gating on `f_added` at `:457`).
- **A TRUNCATED `git status` IS A CONFIDENT WRONG NUMBER ABOUT A REAL PROPERTY.** `git status --short | head -10` showed me 7 lines of 159 and hid 152 staged deletions a peer had already counted. **`| head -N` on the thing you are about to measure is the same defect as `| tail -N`, and I have it written down one section up.**

- **A green over a shared tree is about whoever's files are in it -- verify in a detached worktree at HEAD carrying your files and nothing else.** **AND THE REDS HALF IS THE ONE THAT COSTS AN EVENING: a red is INHERITED until a clean HEAD worktree says otherwise**, and the instinct is to make it pass. - **VERIFY THE COMMIT THE ARTEFACT NAMES, NOT HEAD.** A green at HEAD is a true statement about a tree the binary is not made of.
- **`git commit --only` is PATH-scoped, not hunk-scoped.** **A LOST COMMIT RACE LEAVES YOUR FILES STAGED IN THE SHARED INDEX** and the next node to commit by path sweeps them into a message claiming work they did not do -- check `git diff --cached --name-only` is EMPTY before `git add`, and wait if it is not. `git checkout -- <file>` in a dirty tree is a REVERT. `.git/index.lock` means a peer is mid-commit -- wait, never clear it. **`git status` here is a snapshot of whoever is mid-write, not a state, and it names PATHS, not AUTHORS.** **A PEER'S HALF-FINISHED EDIT REDS YOUR RUN IN A FILE YOU NEVER TOUCHED, THEN REPAIRS ITSELF** -- ask the owner before diagnosing. **Verify a repair out of the COMMITTED BLOB.** Never amend once a peer has committed on top.
- **THE INSTALLED PAIR IS A SHARED ARTEFACT TOO** -- a peer's rebuild swaps it under a run in progress, so read the sha at BOTH ENDS and discard on a differing OR FAILED read. **A build marker differing from HEAD is not a finding**; the question is whether a COMPILED input moved, and a doc-only edit to a `.rs` file still moves it.

**THE BACKTICK DEFECT IS UNQUOTABLE IN THE MEDIUM THAT CARRIES THE REPORT.** A plain `'` is correct in board prose; the never-escape rule is about the HEADER block ONLY. **The odd-count check has a FALSE-POSITIVE arm to match its false-negative one** -- awk sets NF=0 on an empty record, so guard with a non-zero length test.
