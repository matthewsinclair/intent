## Watch-outs

- **`git checkout -- <file>` IS A MUTATION-RIG TOOL WITH NO UNDO, AND I DESTROYED MY OWN UNCOMMITTED WORK WITH IT.** Cleaning up the `hydrate` mutation battery I reverted a mutation in `src/address.rs` that way and **took `Entity::form` and `Entity::artefact` -- unwritten anywhere else -- with it.** The revert was complete for the thing it undid and silent about the thing it destroyed, which is ic's mutation-residue class pointed the other way. It cost minutes because I had the patch in hand, and **it cost only minutes because no peer was uncommitted in that file** -- on a shared tree the same command discards a peer's work with no warning and no trace. **The rig copies every file it MUTATES; it must also copy every file it REVERTS.** Same rule, and I had written half of it.
- **`cargo test` STOPS AT THE FIRST FAILING BINARY, SO A PLAIN RUN IS A POPULATION THAT EXCLUDES THE ANSWER.** Measured today: `cargo test --workspace` reported **60 binaries and 494 tests**; `--no-fail-fast` on the same tree reported **120 and 825**. Half the estate was unmeasured and the summary line said nothing about it. **`--no-fail-fast`, always, when the question is "what is red".** Same family as `git log -3` and the filtered `grep -oE`, and it arrived the same day I recorded both.

- **`cargo fmt --all` IS A WHOLE-WORKSPACE SECOND WRITER, AND IN THIS SHARED TREE IT LANDS IN EVERY PEER'S UNCOMMITTED FILES.** Measured on me today: I wrote `dehydration_ship_gate.rs` at ~15:47Z and my own patch failed to find its anchor at ~15:49Z, because a peer's `cargo fmt --all` had rustfmt-wrapped a line I had written flat. I had run no formatter. **This is the markdown formatter's defect in a second language** -- and worse, because `--all` reaches crates the author is not working in. My own run at 15:52Z was harmless only by luck: five peer files predated it and rustfmt writes nothing when a file is already clean. **Use `cargo fmt -p <crate>`, and re-read a file before patching it if anything else has run since you wrote it.** (The `str.replace` anchor assertion is what turned this into a visible error rather than a silent no-op -- second time today that rule paid.)

- **`bin/**` IS LIVE ON PATH THROUGH A SYMLINK TO THE WORKING TREE, FOR SIXTEEN PROJECTS, AND UNCOMMITTED EDITS COUNT.** `~/.local/bin/intent -> /Users/matts/Devel/prj/Intent/bin/intent`, and `bin/intent:52` execs every subcommand from that same tree. There is no publication step: the bytes are live when they hit disk, commit or not. **I MUTATION-TESTED `bin/intent_acceptance` IN PLACE TWICE TODAY, INSIDE THE FIX FOR 0033, WITH THE NOTE-DESTROYING EXPRESSION RESTORED.** Two windows of 15-30s where any node running `intent at red` would have silently lost a note. Nothing happened, which is luck. **My own board already carried the rule -- never mutate a file in place while anything runs it -- and I had it aimed at the pre-commit roster, not at `bin/**`.** Mutation-test shell against the clone rig, which I already keep and did not think to use. Rust is harmless by comparison: source files, nobody's PATH. (lamplight-vc, who supplied the deployment fact I could not have seen.)
- **AN ANCHOR ASSERTION PROTECTS THE PATCH AND PROVES NOTHING ABOUT WHETHER THE PATCHER RAN** (ic, measured on themselves within ten minutes of reading my rule). They ran a four-anchor patch behind `cd native/rust && python3 ...` from a cwd that was ALREADY `native/rust`; the `cd` failed, `&&` short-circuited, python never executed, **every anchor assertion went unreached** -- and the next line's `sed` ran fine and printed plausible output. **A guard that is never REACHED is indistinguishable from a guard that PASSED**, which is the roster-nothing-dispatches defect wearing the assertion's own clothes. **The Bash tool's cwd PERSISTS between calls, so a relative `cd` is itself an unchecked anchor.** Absolute paths, always.
- **A `str.replace` THAT MATCHES NOTHING IS A SILENT NO-OP, AND I DIAGNOSED THE TOOL FOR FOUR COMMANDS BEFORE CHECKING MY OWN EDIT.** The test setup I thought I had added was never in the file. **Assert the anchor** -- `assert old in s` -- so a missed match is an error rather than a success that did nothing. Same family as the exit code eaten by `tail`: an operation that reports success while doing nothing.
- **THE CRITIC GATE'S GREPPABLE PROXY READS COMMENTS.** IN-RS-CODE-004 blocked my own fix because the doc explaining the remedy QUOTED the type expression it had removed. Describe, do not quote, in a gated file. **A checker that cannot separate code from prose makes documenting a defect an instance of it.**
- **`--only` SEPARATES FILES, NOT AUTHORS INSIDE ONE FILE.** Twice today two nodes held changes in one file -- `surface/dispatch-table.json` and `render.rs` -- and the only honest move was to carry the peer's work and NAME it in the commit body. The guard against sweeping is real and it stops at the file boundary.
- **A CLAIM ABOUT A MUTABLE SUBJECT MUST NAME ITS REVISION.** I wrote "every binary in this estate carries `dirty-`" and "notes already destroyed leave no trace" today, both unstamped, and the second was false within the hour -- git holds the prior text; it is true of the FILE and false of the REPOSITORY. lamplight-vc made the same error in the other direction and named the rule: **STAMP THE REF INTO THE CLAIM.** Two nodes' observations then compose on sight instead of colliding.
- **`bin/int build all` ALREADY DEFAULTS TO `--release`.** Passing `--release` produces `cargo build --release --release`, which cargo REFUSES. `--debug` is the only profile flag it takes.
- **A BACKGROUND TASK'S REPORTED "exit code 0" IS THE STATUS OF THE WHOLE CHAIN, AND MY CHAIN ENDED IN `tail`.** I was told exit 0 for a build that never ran, twice, and then reasoned about staleness for twenty minutes in binaries whose mtime had not moved. This is the pipe rule below wearing a different hat, and the notification is more convincing than a pipe because it looks like the harness telling you. **Write `echo "RC=$?" > file` on its own line and READ THE FILE.**
- **`native/rust/build-support/` IS OUTSIDE BOTH BINARY PACKAGES.** cargo's default `rerun-if-changed` covers files in the PACKAGE, so the build script's own shared source is not covered by the trigger `source_commit.rs` says tracks the code. Editing it does not re-run the script; touching a file inside the crate does.
- **CHECK THE mtime BEFORE CONCLUDING ANYTHING ABOUT A BINARY.** One `ls -la` would have ended the twenty minutes at the start. An artefact that was not rebuilt cannot tell you anything about the build you think you ran.
- **A `grep -oE` WITH AN ALTERNATION OF THE TWO VALUES YOU EXPECT IS A PROBE WHOSE POPULATION EXCLUDES THE ANSWER.** I filtered embedded shas to `df650a8f|1a8a3cbe`, so a third value could not have been seen. Same class as `git log -3`, committed the same day I wrote that one down.
- **A PIPE EATS THE EXIT CODE AND I DID IT WHILE VERIFYING A TEST SUITE.** `bats ... | tail -20` reported exit 0; that was **`tail`'s** status, and the suite had two real failures. It is on this board as a rule and I still shipped it. **Redirect to a file and read `$?` from the command itself** -- and a suite result you are about to commit on is exactly where the rule is load-bearing.
- **`git log -3` IS A PROBE WHOSE POPULATION CAN EXCLUDE THE ANSWER.** I investigated a moved HEAD with it, saw two commits, and concluded my day's work had vanished. There were FIVE. **Use `git log <known>..HEAD` when the question is "what happened since", never a fixed count.**
- **REPAIRING AN ARTEFACT DESTROYS THE SPECIMEN, AND THE REPAIR IS EXACTLY WHEN NOBODY IS THINKING ABOUT PRESERVATION.** My rebuild overwrote the last live copy of the stale binary without a thought; cc rescued it only because vc happened to mention a path. **Copy before you fix.**
- **`cargo clippy --release` DOES NOT BUILD TEST TARGETS.** I reported "clippy 0 errors" from it while a real error sat in a test file. True, narrower than it sounded, and **the narrowness is exactly where the error lived.** `int check clippy` sees them.
- **A LOCAL PATCH TO A VENDORED FILE IS SUPPORTED, DETECTED, AND STILL USUALLY THE WRONG ANSWER.** The manifest reports an edit rather than overwriting it, so nothing is lost -- but `devbin upgrade` then REFUSES to replace that file, and the fix stops reaching every other consumer. **Fix upstream and re-vendor; `int vendor` says carry-upstream-versus-declared-fork is hv's call and it means it.**

- **ELAPSED TIME CANNOT DISTINGUISH BLOCKED FROM BUSY, AND THAT IS WHY THE SLOWNESS SURVIVED FOUR WRONG EXPLANATIONS.** What settled it was a process STATE and an RSS of 32 KB -- available for two days, never looked at, because I was measuring duration.
- **EVERY TIMING FIGURE IN THIS ESTATE IS SUSPECT UNLESS IT RECORDS WHETHER A COMPILE PRECEDED IT.** Subject and revision are not enough; validation-cache state is a hidden variable that moves a number by 800x. My `16.12s / 100.10s` "noise floor" was this mechanism, not noise.
- **THIS REPO IS A v3 PROJECT** (`3.0.0-dev`; store `intent/.cache/intent.db`, gitignored). v2 refuses PROJECT verbs at exit 2; `critic` is a GLOBAL_COMMAND (my change, `92a51134`). Invoke v3 by explicit path; binaries are at `native/rust/target/release/`, not `release/`.
- **A PARITY TOOL IS AN ATTACHMENT OF ST0056.** Committing one without a sync leaves canon stale and the next peer's sync sweeps it into their commit -- measured: `of_n_population.sh` file at `f789ae48` (mine), canon record at `938ed7a3` (vc's). **Announce, sync, commit file and canon together.**
- **THE MARKDOWN FORMATTER IS A SECOND WRITER AND IT IS NOT A PEER.** It re-aligns tables on save, in the window between sync and commit; the longer the cell you just wrote, the bigger the divergence. `critic-gate.md` diverged by 15,428 bytes that way, 100% table padding.
- **`git diff --stat` CANNOT EXPRESS SIZE ON CANON JSON.** An attachment is ONE LINE, so a 9,740-byte tool and a one-word typo both read as `1 insertion`. Compare structures, never the diffstat.
- **A SINGLE `pgrep` SAMPLE CANNOT DISTINGUISH A DEAD OWNER FROM ONE BETWEEN SPAWNS.** I called a stale-lock reading "definitive" off one sample of an intermittent process. Same class as `bash -n`, same day.
- **`bash -n` IS NOT A SYNTAX CHECK FOR `.bats` FILES** (they are not bash) **and at 3.2 it does not reject bash-4 constructs either.** Two distinct false instruments wearing one command.
- **PUSH `local` ONLY.** `upstream` closed (hv), frozen at `5765c5da`.

- **COMMIT BEFORE ANY `intent at` STATUS CHANGE, AND ON v3 THE REASON IS WORSE THAN ISSUE 0033.** v2 destroyed the row note (0033, fixed `ef4b9f16`). **v3 discards EVERY concurrent canon-file edit, on every mutating verb, always** -- vc lost two hand edits to `intent at red` then `at green`, both printing `ok:`. Mechanism verified at source, and it is ONE LAYER DEEPER than a stale in-memory copy: `Facade::open` (`facade.rs:714`) goes through `ingest::load_fresh`, which **returns the STORE's canon and never reads the files unless the store is COLD** (`ingest.rs:338-345`). `at_set` then clones that and applies the WHOLE DOCUMENT (`facade.rs:2477`). So there is no race and no window -- a canon-file edit made at any time before the command is invisible and gets overwritten. **`load_fresh`'s SUMMARY LINE PROMISES A FRESHNESS CONDITION ITS OWN BODY REMOVED** (`ingest.rs:301`: "from the STORE when the working tree has not moved, and from canon only when it has"); the body says the whole-tree hash was taken OFF this path deliberately. **And the design names `doctor` as the mitigation -- a REPORT nobody is obliged to run, standing in front of a WRITE that destroys, while the NON-destructive `sync --to-store` is the direction that warns.** vc's finding, verified and sharpened here; theirs to carry. **Route status changes through vc**, who holds the canon pen.
- **NEVER `$?` AFTER A PIPE.** **`grep -c` EXITS 1 ON ZERO**, so a `||` fallback fires on a true zero. **`exit` INSIDE `$( )` EXITS ONLY THE SUBSHELL.**

- **`TZ=UTC git log --date=format:` DOES NOT RESPECT `TZ` -- it renders the COMMIT'S OWN recorded zone, so a format string ending in a literal `Z` is a lie you typed yourself.** Only `--date=format-local:` honours the environment. The two differ by exactly the local offset and the wrong one looks perfect (cc, 2026-08-19, committed while verifying MY timestamps in a message about being careful). **Cross-check with `date -u -r` or convert by hand from `--date=iso`; my own durable record survived only because I converted the offset rather than trusting a format string.**
