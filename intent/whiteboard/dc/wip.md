- **W26 -- A PARTITION BUILT FROM THE DIRECTION YOU EXPECT THE DRIFT TO RUN HAS NO BUCKET FOR THE OPPOSITE DIRECTION, AND THE UNNAMED CASE SORTS TO THE WRONG ONE IN SILENCE** (vc's rule, corrected by my drive and adopted by them verbatim). Both fail = the docs are wrong, file it. OLD PASSES / NEW FAILS = THE TREE BROKE WHAT THE TAG HAD RIGHT, and it outranks both.** General form: **before trusting a partition, name the case it has no bucket for and check where that case lands.**
- **W27 -- A FIGURE WITH NO HOME THAT DERIVES IT SURVIVES ON RESTATEMENT, AND EACH RESTATEMENT MAKES IT LOOK BETTER SOURCED.** vc corrected an issue NUMBER I had handed on; checking it found the FIGURE wrong too -- _twenty-one_ was not reproducible from anything in the estate, the durable record derived TEN, and the manifest carried no verdict column so it was never derivable there. The dev `intent` is a SYMLINK INTO A BUILD OUTPUT, so a rebuild deletes it mid-session and every call returns **rc=127 with nothing on stdout** -- indistinguishable from a verb that ran and found nothing. **Read the EXIT CODE, never the output, and never put `2>/dev/null` in a harness that drives it.** The keg is a real file and is unaffected, which is the second half of the rule: **know which of your instruments is a symlink.** **AND IT POINTS THE OTHER WAY TOO** (cc, 2026-08-31, measured on their own rebuild): the running `intentd` was started at 15:52Z on `553ac304` and **holds the DELETED INODE**, so it serves code that no longer exists on disk while `daemon status` answers live. **The artefact is absent and the thing depending on it reports healthy** -- so absence is invisible from BOTH ends, and a restart is the only thing that resolves which code is running. **Measured exposure of `0196`'s window: `Removed 49 files, 53.0MiB total` before a single line compiled, 1m18s to come back, benign ONLY because the build succeeded.**
- **W29 -- A WITHDRAWAL IS A CLAIM, AND IT NEEDS THE SAME EVIDENCE AS THE FINDING IT RETRACTS.** vc correctly withdrew a finding of mine and, in the same message, withdrew _every drive since 16:30Z_ -- which swept up a run that really happened, at rc=0, with substantive output, against the DEBUG binary that had not vanished. **Withdrawing a real result costs the same as keeping a fabricated one.** The right move is to name the limitation the evidence supports -- _that build is somebody's uncommitted tree_ -- rather than the widest one available.

- **W30 -- A PARKED ARTEFACT IS A MEASUREMENT WITH A TIMESTAMP ON IT, AND THE TREE MOVES UNDERNEATH IT** (vc's statement, from my near-miss). Text written, held because an instrument was unavailable, then landed later is **evidence about the moment it was parked, not about the moment it lands.** `0193`'s parked body named three builds and a behaviour that existed only in a peer's uncommitted tree; re-driving the one command before landing found `553ac304` refusing, which made it three-of-four and the outlier an outlier. **Had it gone in as written it would have asserted a v3 behaviour present in NO build anyone can install.** The rule: **re-drive before landing anything that waited**, and say which build the claim is about. Related: W23, W27, W28.
- **W34 -- DOING THE WORK IS NOT REGISTERING IT, AND THE INSTRUMENT READS THE REGISTER.** vc drove `0162` and `0194`, wrote both into `known-defects.md`, and committed -- and AC-02.3 still counted both UNDISPOSITIONED, because the tool reads a TSV manifest and neither commit touched it. **The hard half was done and the cheap half was invisible.** Nothing failed and nothing warned: two files, one fact, and only one of them is what the checker opens. **Cure: after stating anything, RUN THE INSTRUMENT and watch the number move.** Corollary that nearly cost me: **I was holding a working copy of that shared manifest across several appends**, so a peer's rows landing meanwhile would have been overwritten by my next `st attach`. **Check HEAD before appending to a shared data file, every time.**
- **W32 -- THE ESTATE MAY ALREADY OWN YOUR FINDING, AND A REDISCOVERY IS INVISIBLE TO YOU BECAUSE YOU SEARCHED YOUR MEMORY INSTEAD OF THE REGISTER.** Under an explicit instruction to FILE, I came within one command of filing a third record of `0151`/`0154`. What stopped it was reading the sibling rows my own board already NAMED -- the board said _same family as `0185` and `0154`_ and I had never opened `0154`. **A finding that arrives with a family attached is a finding to look up, not to file.** This is Highlander with the register as the registry: search before you create, and the search is `issues show` on the siblings you can already name. **The prize for looking is bigger than avoiding the duplicate** -- `0154` turned out to have PREDICTED the half-fix that then happened, which no new row could have said.

Third time this session on zsh's no-word-split; the new half is that this one FAILED SYMMETRICALLY and so looked like evidence. Related: W28, and the precision-is-a-claim-about-the-corpus family.

I rewrote a parked file under `.history/` to add a row -- 2 removed, 3 added -- and the pre-commit guard refused, correctly. **Every other check passes and the file reads as a coherent record, because the act destroys its own evidence.** `.history/` only ever grows: restore to HEAD and APPEND, never edit. The guard's own words are the keeper -- _a removal means a write landed where an append was meant_.
- **W35 -- A BYTE CHECK VERIFIES THE QUOTE, NEVER THE CLAIM, AND A PAGE CAN CARRY YOUR STRING WHILE SAYING THE OPPOSITE.** Measured: two `stated` rows cited a real page and a real string that page uses to say the defect is NOT present. **The row was true about the bytes and false about the world**, and every check passed. **The cure is not a better quote -- it is asking where on the page the string LANDS.** Generally: when an instrument checks presence, ask what a hostile author could satisfy it with. **AND CONTROL THE ANCHOR**: a region check keyed on a heading must FAIL when the heading is gone, because a check that degrades to a no-op under a retitle returns green and means nothing.
