# WP-06: The hashed family

## Objective

Every new thread, work package and issue is minted as a hashed id derived from its creation event, the canon and the store carry it, and no verb mints an ordinal again.

Seat: cc. Size: L.

## Scope

- The mint: the event envelope first, then the id as its marker plus the front of `sha256_hex(origin)`: 16 hex for a thread and an issue, 8 for a work package. It refuses an id this clone can see (the store, the canon directory, the realised directory, and the ids taken in a plan), and it draws a new event id when the new short form equals that of a visible record of its own kind. The draw is inside the one mint, happens before anything is written, and is bounded: after its last draw the mint refuses loudly. Its test uses a real pair of ULIDs whose hashes share a short form, found by search and kept as a fixture.
- Canon: `number` and `seq` become `id`; `origin` goes on a thread, a work package and an issue, written for hashed records only; the thread and issue schemas take a new version.
- The store goes from schema 35 to 36 with two table rebuilds: `issues.number` is the rowid (`store.rs:332-333`), and `wps.seq` is an integer (`:255-275`).
- `intent upgrade` gains the canon format migration: byte-deterministic, over every issue file and every thread file with a work package, with no id changed.
- The stored-form reader refuses a canon name of neither family by name. That ends the silent skip (`project.rs:2645-2661`, inherited at `migrate.rs:358-373` and `ingest.rs:370`).
- The faces and the export bundle take their new versions with ic. WP-10 carries the GraphQL side.
- The tests whose subject is the ordinal scheme are rewritten here: `facade_st_wp.rs`, and the two-clone test, which becomes the proof.
