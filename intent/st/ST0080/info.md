# ST0080: Scheduled store backups that actually fire

## Objective

A project's configured backup cadence takes a snapshot when one is due, without anyone running `intent backup` by hand, and keeps only as many snapshots as the project says.

Concretely:

1. The existing `backup.schedule` in `intent/.config/config.json` fires. The "is a backup due" question already has one home, `intentsvcs::backup::due()`, which reads the per-machine store. Today only intentd's sweep calls it with a cycle. `intent explore` calls the same door before it does anything else, and intentd's start or a session hook can call it later, so a project nobody opens in the explorer is not left without backups. There is no second "is it due" function.
2. `backup.keep: <N>` joins the same nested `backup` block and keeps the newest N snapshots. It is ONE pruning rule: it replaces the existing `backup.retain.{daily,weekly,monthly}` retention (defaults 7/4/12), or is ranked against it in a way the design states. It is never a second rule beside it. No new flat keys.
3. The cadence format is settled: words (`daily`, `weekly`) or durations (`12h`, `7d`). The off value is the existing `backup.enabled`, which gates only the scheduled path, so a stale backup still reports.
4. A backup that is due and fails is never silent. The recommendation is a loud warning, with the explorer still opening.

## Context

hv's idea, 2026-09-25, relayed by gtools-vc with hv's approval of gtools-vc's plan ("I like your additions. We should use your plan."): a backup cadence in the project's Intent config; `intent explore` checks the cadence and the last backup and, if one is due, takes it first; a keep-count prunes to the newest N.

WHAT IS ALREADY THERE, measured on 3.2.2:
- `intent backup` snapshots this machine's store to `intent/.backup/db/`, lists with `--list`, and prunes expired snapshots on each run.
- `backup.schedule` exists in project config (`"daily"` in Intent, Gtools and Lamplight), and NOTHING HONOURS IT for most projects.

WHY IT IS INERT (lamplight-vc, read from source, 2026-09-25): intentd's 5-minute sweep (`BACKUP_SWEEP`, intentd/src/main.rs) and its on-open `consider_backup` (intentd/src/store.rs) reach only projects intentd holds open, and a project is opened only when something reaches it through `--daemon` or MCP. A CLI that runs in-process never opens it, so the schedule reads as honoured and nothing runs. Measured: Lamplight's newest snapshot was 433h old, Anvil's 429h, Gtools' four days, each against a daily schedule. Nothing says so until doctor's backup-stale advisory, which only `-v` shows.

THE CONSTRAINT THE DESIGN MUST STATE: the cadence is checked-in project config, shared by every machine and clone, while snapshots are per machine (`intent/.backup/` is never in git). "Due" is therefore a per-machine question asked against a shared rule.
