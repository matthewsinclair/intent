# ST0086 design draft: the estate view

Written on 2026-10-24 from the rubber-duck between hv and vc. What is marked measured was measured; the rest is design to be measured before it is built.

## What it is

The estate is the host (rhadamanth, kovacs, gyges each its own). The estate view is a live top-styled table of every Claude session on the host: who it is, which project and node it stands in, whether it is busy, idle, in a heavy run or paused, its one-line WIP, its claims, and the host's load with a census of the process classes its controller declares. Three readers render one source of truth: intentd at /estate/status, the intent explore TUI at /estate, and `intent estate status --json` for Claudes.

## The source of truth

Presence and liveness are Claude Code's own session files, read and never written (hv's ruling, 2026-10-24). Claude Code writes `<config dir>/sessions/<pid>.json` for every session, where the config dir is `CLAUDE_CONFIG_DIR` or else `~/.claude` (measured on 2.1.310): `pid`, `procStart`, `sessionId`, `cwd`, `name` (the cross-session name), `status` (busy or idle), `startedAt`, `updatedAt` and `statusUpdatedAt` (epoch milliseconds), `messagingSocketPath`, `kind`, `entrypoint` and `version`. The format is not a published contract, so a reader test pins exactly the fields the reader relies on (pid, procStart, sessionId, cwd, name, status, startedAt, updatedAt), and a file that lacks one is shown as unreadable with the field named, never dropped. The reader lists `<pid>.json` only: Claude Code writes a `<pid>.<64 hex>.key` beside each session file (measured by cc on 2026-10-25, one pair per session), which the reader never opens or names, and an arm pins that it skips them by suffix. intentd runs today as a detached process whose parent is pid 1, not as a launchd job, and carries `CLAUDE_CONFIG_DIR` in its environment (measured 2026-10-24), so the reader takes the config dir as a parameter and the daemon passes its own; a LaunchAgent intentd would not carry that variable, so its plist sets `CLAUDE_CONFIG_DIR` under `EnvironmentVariables` to the value the sessions run with: without it the daemon reads `~/.claude/sessions` and asks the Keychain for the bare service name, which are another config's (WP-02).

Intent adds only what that file lacks, and joins most of it rather than storing it. Project root is the Intent project whose tree holds the session's cwd. Node, focus and claims come from the board whose recorded session id matches (`wb pickup` records it), read narrowly from that board's rendered `intent/whiteboard/<node>/board.json` header, under board schema 3.0 and 4.0 alike; the reader opens no store, since a read-write open of a peer project's store writes into it (cc's reading at WP-01, vc's ruling at its landing, 2026-10-24), and the header is the store's own tool-written render of those keys, so one fact keeps one home. Paused is a board's paused status. Heavy is a running slot the session holds in any lane, a light lane included (see Slots and lanes), and gone is a dead pid (see Cleanup); neither is written by anyone (vc's ruling, 2026-10-24). Intent writes per session only what nothing else holds, in `~/.local/state/intent/estate/<session-id>.json`: a schema version (pinned from day one, since the dev, opt and brew switch lets two intents share a host), the session id, a WIP line for a session with no board, the statusline's latest `rate_limits` where that fallback is in use (see Readers), and no stamp: the file's own mtime is its stamp, set by the atomic rename that writes it, so nothing asks a clock (D42). It is written whole by atomic rename by that session alone, with no locking; it is state, not config (intentd's socket already lives under `~/.local/state/intent/run`, measured).

## Writers

Presence needs no Intent hook: Claude Code keeps its own session file current. The explicit verbs: `intent estate wip "<line>"` (a session with no board), `intent estate prune` (Intent's own WIP records only), and the slot verbs below. MCP exposes `status` and `wip` because a repeat changes nothing; the slot verbs accumulate and stay CLI.

## Readers

One reader function in intentsvcs returns the joined table from the directory plus the stores it points at; the page, the TUI pane and the verb are renderers of it (PFIC, thin coordinator). The daemon adds the host census it measures itself, which retires vc's census script: the load, and a count of the running processes of each declared class, attributed to the project whose tree holds each process's working directory (a process in no known project counts as unattributed). The tool knows no process names, as it knows no lane names: the controller declares the classes, each a name and a pattern matched against the process's command line, with `intent estate watch <class> <pattern>` (and `intent estate unwatch <class>`), written as `census/watches/<class>.json` beside the slots. The verbs are flat, not `estate census watch`, because the spine builds a family and its verbs with no third level, and the subcommand-values idiom that would give one is the one the daemon family was moved off, because it puts two recoverabilities on one row (vc decision 75, 2026-10-25). `intent estate init` seeds the classes this host ran on 2026-10-24 (cargo and rustc, bats, mix and beam.smp, swift-build and xcodebuild); a project building with anything else adds its own. The page lists every declared class, those running with their count by project and those idle on one line, so a declared class never drops off the page (hv asked for this on 2026-10-24).

The page is not a second document (vc's ruling, 2026-10-24): under D56 the daemon serves one shell document, so /estate/status is a route in `shell.html`, fed by `/op` with the reader's JSON, and the daemon renders no HTML for it. The mockup attached as `estate-status-mockup.html` shows the page's layout and the raw record shapes it reads (census, controller, lanes, requests with one key per file present, sessions, and the boards the reader joins), from an inline sample that re-renders on a timer. hv approved its layout on 2026-10-24: one band across the top (the host block, the last hour as sparklines of the 1-minute load and the running slots, and plan usage), then the queue as its own panel, oldest first, then the lanes, then the sessions. Every panel is collapsible as a native `<details>`, with no script and no stored state, and a collapsed panel's summary line keeps a live one-line reading (the queue's waiting count and oldest age, usage percentages and whether the fallback is in use, the session tally), so folding a panel never hides activity; collapse all and expand all sit at the top. Rearranging panels is not in the mockup: if wanted, it is a per-viewer order kept in the browser, for WP-02 and WP-03 to decide. The sparklines need the daemon to keep a short in-memory ring of census samples (a minute apart, an hour long); it is not a record on disk and a restart starts it empty.

The pipeline strip (hv's ruling, 2026-10-25, vc decision 83, AC-04.7) sits under the band and above the queue, so the graphs and then the jobs are the at-a-glance view and the panels below are the drill-down. It is one horizontal line of cells that scrolls off the page both ways, never wrapping, read left to right as time: the requests that ended in the last hour (ended, revoked or denied, the same window as the sparklines) on the left and faded, each with its requester, how long it ran and how long ago it finished, a revoked or denied one tagged in red; a now marker; the running requests, highlighted, each with its requester, lane and age, an orphaned one in red; then the requests yet to run, dashed, granted before asked and oldest ask first. The strip opens with now near its left edge, so the running cells are in view and the finished ones a scroll away; a scroll the viewer made holds through every re-render; a centre button beside the heading, an icon of two chevrons pointing at a bar, centres the running cells, or the now marker when nothing runs. The summary line reads how many finished in the last hour, are running and are yet to run. The mockup draws it from its sample.

The reader's answer is `intent/estate-status@1`, and every key is present from WP-01, so a renderer never branches on a missing one; until the WP that fills a key lands, it carries the empty value of its declared shape, which is a valid instance of that shape, so filling it needs no schema bump (vc's ruling, 2026-10-24, since @1 has shipped nowhere). The keys: `schema`; `host` (null when `uname` fails); `version`; `taken_at`; `sessions`, each row carrying `session_id`, `name`, `pid`, `project` (`{root, name}` or null), `worktree`, `node`, `claude_status` (Claude Code's value verbatim), `state` (gone, paused, heavy, busy or idle), `started_at`, `updated_at`, `slots`, `claims`, `line`, `line_is_wip` and `line_at`; `unreadable`, each `{path, why, pid?}`; `census`, `{load, procs, history}`, empty arrays until WP-02, where `load` is the 1, 5 and 15 minute load averages, `procs` is one row per declared class, idle classes included so none drops off the page, `{class, count, projects: [{project, count}]}` with `project` the project's name or null for a process in no known project, and `history` is the in-memory ring, `[{at, load1, slots_running}]`, oldest first; `usage`, `{source, error, read_at, five_hour, seven_day, models}`, all null until WP-02, normalised by the reader so the page derives nothing: `source` is null when there is none, else `{kind, session_id}` with `kind` endpoint or statusline and `session_id` the reporting session's for the statusline, null for the endpoint; `error` names why the primary failed (the Keychain read, a status other than 200, an answer that will not parse), null when it did not; `read_at` is when the source was read; `five_hour` and `seven_day` are each `{percent, resets_at}` or null; and `models` is `[{name, percent, resets_at}]` from the endpoint's per-model caps, null when unavailable, which the statusline always is; and from WP-04 the slot keys. `controller` is null when no session holds control, else `{session_id, name, pid, node, taken_at, predecessor}`, `node` null when the take named none and `predecessor` `{session_id, name, node}` for the controller this take handed over from, or null. `holds` is `[{id, scope, lane, condition, node, held_at}]`, every hold standing, oldest first, `scope` `desk` or `lane` and `lane` null for a desk hold. `lanes` is `[{name, type, capacity, load_under, granted, running}]`, the last two counts of the requests granted and running in that lane, a request granted into several lanes counting in each, and `load_under` null when the lane has no load admission. `queue` is `[{id, type, what, state, lanes, named, tags, gates, asked_at, started_at, ended_at, relayed, by}]`, every request not yet ended, denied or revoked, oldest first by its sort key (`asked_at`, or the `--place-of` request's), where `id` is a ULID, `state` is the fold of its files (asked, granted or running), `lanes` is every lane its grant names and empty until a grant, `named` is the booking's key=value strings, `tags` its display tags, `gates` `[{kind, text, ref}]` with `kind` `not-before` (`ref` a request id) or `hold` (`ref` null), `started_at` and `ended_at` null until the start and end files exist, `relayed` true when either stamp is a relay's time, and `by` is the requester's session id. One fact keeps one home, so a row carries `lanes` and no `lane` (ic, 2026-10-25). `recent` has the same row shape and holds the requests that ended, were denied or were revoked in the last hour, oldest end first, so the pipeline strip draws its finished cells from the reader rather than keeping history of its own; `queue` stays as above. Every stamp is ISO-8601 UTC with a `Z`.

Plan usage comes from two sources, the second a fallback (hv's ruling, 2026-10-24: "1 is the fallback. But I think 2 is worth it."):

- Primary, the account's usage endpoint, as the claudecodeusage menubar app reads it (measured from its source). intentd reads Claude Code's OAuth access token from the macOS Keychain with `/usr/bin/security find-generic-password -s <service> -w`, whose service is `Claude Code-credentials`, suffixed with `-` and the first eight hex digits of the SHA-256 of the config dir when `CLAUDE_CONFIG_DIR` is set and the bare name when it is not, which is Claude Code's own condition, with no fallback from one to the other: a fallback would read another config's token, and a test daemon run without the variable would reach the real Keychain; the value is JSON and the token is `claudeAiOauth.accessToken`. It then sends `GET https://api.anthropic.com/api/oauth/usage` with `Authorization: Bearer <token>` and `anthropic-beta: oauth-2025-04-20`, by spawning `/usr/bin/curl -sS --fail-with-body --max-time 10 -K -` at its absolute path with the URL and both headers in a config on its stdin, so the token is in no process's argv, and capturing the status and the body; intentd carries no TLS crate (vc decision 73). The answer carries `five_hour` and `seven_day` (`utilization`, `resets_at`), `seven_day_sonnet`, the per-model weekly caps in a `limits` array (`scope.model.display_name`, `percent`, `resets_at`) and `extra_usage`. intentd reads it at most once a census tick, never per page read, and only once a page has asked (the first ask wakes the tick), so a daemon nobody reads never touches the Keychain or the network; it keeps the last answer in memory. The token is never written, logged or sent anywhere but that endpoint. intentd reads the token by spawning `/usr/bin/security`, never through the Security framework itself: `/usr/bin/security` is on the item's access list, and that is the read measured silent (2026-10-24, the suffixed item, rc 0 in about a second with the token present and no dialog on screen, both as a detached process whose parent is launchd, which is how intentd runs today, and as a gui-domain LaunchAgent). A direct Security framework call from the intentd binary was not measured and would most likely prompt.
- Fallback, the statusline's `rate_limits` (measured on Claude Code 2.1.310): the JSON a session hands its statusline command carries an optional `rate_limits` with `five_hour` and `seven_day`, each `{used_percentage, resets_at}` in epoch seconds, for subscribers after the first API response, and no per-model figure. It is stdin to that command, not a file, so it reaches the estate only through a statusline step that writes the latest copy into the session's Intent record. The step (WP-02, vc decision 75): the statusline script pipes the JSON it was handed to `intent estate statusline`, with stdout untouched and the exit code ignored, `printf '%s' "$input" | intent estate statusline || :`, so a missing or broken intent never blanks the status bar. The verb prints its `wrote:` line on stderr and nothing on stdout, which is the status line; an input with no `rate_limits` writes and prints nothing.
- The failure path is named, never silent. When the Keychain read fails (no entry, access denied, a locked keychain), the endpoint answers anything but 200, or the answer will not parse, the page says which, shows the fallback's 5-hour and 7-day figures with their source and age, and marks per-model "unavailable" with the reason. With neither source it says "no source" and why. `usage.error` names each failure: no curl at `/usr/bin/curl`, the Keychain read, the endpoint unreached, a status other than 200 (with the status), and an answer that will not parse; a reading taken outside intentd names that the endpoint was not asked. The Keychain is macOS only: elsewhere the fallback is the source until another platform's credential store is measured.

## Cleanup

A session file whose pid is dead, or whose pid now belongs to a process started at a different time than its `procStart`, renders as gone. `procStart`'s form differs by OS (measured on both on 2026-10-24, Claude Code 2.1.310): on macOS it is UTC ctime, compared with `ps -o pid=,lstart=` under `LC_ALL=C` and `TZ=UTC` in one call for every pid; on Linux it is the kernel's start time in clock ticks since boot, compared with field 22 of `/proc/<pid>/stat`, an absent entry being gone. A failed liveness read is listed as unreadable and calls nobody gone. A session in another pid namespace, such as one in a container (its `pidDomain` names the namespace), reads as gone, since the reader does not cross namespaces. Claude Code's files are never deleted by Intent; the daemon reaps only Intent's own WIP record for a gone session on its next tick, and `intent estate prune` does the same where no daemon runs. A live pid with an old `updatedAt` renders as idle with its age and is never reaped. A slot whose holder is gone renders as orphaned until its controller revokes it; a controller whose pid is dead leaves its record orphaned, and the next `control take` succeeds it. Readers never write.

## Slots and lanes

A generic way for one session to control how much of something runs at once and for others to ask for a share. Nothing in the tool knows what a lane is for; the names below (heavy, cargo, bats, light, launchsvc) are the ones the host's desk runs on and are examples, not a fixed set. The tool enforces capacity and records; which request goes first is the controller's judgement (vc decision 88, 2026-10-25, amended on molt-vc's read). The verbs are three entries, because the spine builds three levels and no fourth: `intent estate control <take|release|hold|unhold>`, `intent estate lane <open|close|hold|unhold> <lane>` and `intent estate slots <ask|grant|deny|revoke|start|release>`, each refusing by name a flag foreign to the verb chosen. A flag takes one value, so the flags that name several things take a comma list.

- **A lane is a scarce resource, and a run holds every lane it uses.** `intent estate lane open <lane> --type <type> --capacity <n> [--load-under <n>]` writes `lanes/<lane>.json`; the same verb changes the capacity, and `lane close <lane>` removes the file and refuses while anything is granted or running in it. The type is the class the controller names (heavy, light, negligible), nothing being built in. `heavy` is a lane of capacity one in itself, and a heavy grant names `heavy` plus every resource the run uses: a judge that runs cargo and bats is granted into `heavy`, `cargo` and `bats`, and a kovacs cargo run into `cargo` like any other, so one lane of capacity one is one cargo run machine-wide. A `launchsvc` lane of capacity one keeps a Launch Services light from running beside a Launch Services run. `--load-under <n>` admits a grant into the lane only while the census's 1-minute load is under n, and the refusal names the reading; the desk's `light` lane is capacity one with `--load-under 60`.
- **A negligible run takes no lane and still shows**: `ask --lane none` asks for none, and `grant <id> --lane none` grants it into no lane, counting against no capacity, with `start` and `release` as usual. Its row carries `lanes: []` in a granted or running state.
- **A request asks by type**: `intent estate slots ask <type> "<what>" [--lane <lane>] [--named <k>=<v>,...] [--tag <tag>,...] [--not-before <id>,...] [--hold "<condition>"] [--place-of <id>]` writes `ask.json` and prints the id, a ULID from the crate's one minter. Queued is per type.
  - `--named` records what the booking will run (eg `tip=`, `patch_id=`, `bank=`, `script_sha256=`); `start` must name the same set, so a START on other bytes than the booking named is not covered by its grant.
  - `--tag` is shown on the row and orders nothing (eg `security`, which the controller weighs on a tie).
  - `--not-before <id>` is a gate the tool enforces: a grant is refused, naming the gate, until that request has an end file.
  - `--hold "<condition>"` is a gate the controller judges: it is shown on the row, and nothing the tool can read says when it is met.
  - `--place-of <id>` is a hand-back keeping its place: the request sorts by that request's `asked_at`. It is refused unless that request was granted and ended without starting, and its `named` set equals this ask's.
  - A fresh booking after a red run or a refusal is a plain new ask, and so is a booking whose named set changed.
- **The controller**: `grant <id> --lane <lane>,<lane>,...`, `deny <id> "<why>"`, `revoke <id> "<why>"`. `revoke` works on an asked, granted or running request, so a dead or quiet holder's slot is freed with the reason recorded; the tool never kills a process. A grant is refused, naming the count, when it would put any lane it names over its capacity, counting granted and running; the controller raises the capacity if it means it. It is refused too while a `--not-before` gate is unmet, while a named lane's `--load-under` is not met, or while a hold stands.
- **Holds**: `control hold "<condition>"` holds the whole desk and `lane hold <lane> "<condition>"` one lane, each printing the hold's id; `control unhold <id>` and `lane unhold <lane> <id>` release them. While a desk hold stands every grant is refused, and while a lane hold stands every grant naming that lane, each refusal naming the hold. A desk hold is today's "no GOs until hv says continue".
- **The holder**: `start <id> [--named <k>=<v>,...] [--relayed]` and `release <id> [--result "<text>"] [--relayed]`. The write stamps both, so START and END are never typed; `--relayed` marks a stamp as the relay's time rather than the run's own clock, for a run on another host whose holder relays it (kovacs, through kovacs-sysadm), and the row says so; `--result` carries the run's legs as the holder writes them. A `release` before `start` ends the request unrun, which is what `--place-of` re-asks from.
- **The caller is `CLAUDE_CODE_SESSION_ID`**, as for `estate wip`: `by` on an ask is it, and `start` and `release` are accepted from the asking session only. **Only the controller grants, and the tool enforces it**: grant, deny, revoke, lane and hold writes are refused, by name, from any session but the one `controller.json` records. Every write records the writer's `--node` when given, and the page shows the controller's node on its control line. The caller's name is the one its own Claude Code session file records, found by `CLAUDE_CODE_SESSION_ID` (measured on 2026-10-25: the file carries `"name"`, the name peers address the session by), never `--node`, which is self-declared.
- **The files are the protocol**, under `~/.local/state/intent/estate/slots/`, beside the session records, each carrying `schema` `intent/estate-slots`: `controller.json` (`session_id`, `name`, `pid`, `node`, `predecessor` as `{session_id, name, node}` or null, `hv`, `released`), replaced atomically by each take and by `control release`, which sets `released` rather than deleting it, so the reader shows NO CONTROLLER from a record and not from an absence; `holds/<id>.json` (`id`, `scope`, `lane`, `condition`, `node`) and `holds/<id>.unheld.json` (`node`), a hold standing while its unheld file is absent; `lanes/<lane>.json` (`name`, `type`, `capacity`, `load_under`, `node`) written by the controller; and each request a directory `requests/<id>/` holding `ask.json` (`id`, `type`, `what`, `lane`, `named`, `tags`, `gates`, `place_of`, `by`, `node`) from the requester, `grant.json` (`lanes`, `node`) or `deny.json` (`why`, `node`) from the controller, `start.json` (`named`, `relayed`) and `end.json` (`result`, `relayed`) from the holder, and `revoke.json` (`why`, `node`) from the controller. A request belongs to no lane until granted. Each file is written once by its one writer, and no lock exists.
- **No record carries a clock reading** (ST0056's D42, as the WIP record's `wip_at`): every stamp is the file's own mtime, set by the atomic rename that wrote it, and the reader reads each file's mtime, never its directory's. So `taken_at` is `controller.json`'s, `held_at` the hold file's, `asked_at` `ask.json`'s, `started_at` `start.json`'s, and `ended_at` that of whichever of `end.json`, `deny.json` and `revoke.json` finished the request.
- **A request's state is the fold of the files present**: revoked if `revoke.json` is there; else denied with `deny.json`; else ended with `end.json`; else running with `start.json`; else granted with `grant.json`; else asked. The readers read it like the session files.
- Learning without polling: `wait` for the requester; for a controller, the UserPromptSubmit hook names the pending asks on the lane types its session controls, the way it injects project context today.
- Out of the first cut: priorities and any ordering in the tool, and any policy beyond capacity, the named-set match, the not-before gate, the holds and the load admission. Succession is by pid liveness only (see The coordinator).

## The coordinator

The controller is whichever session hv assigns to manage the workload: a dedicated session that stands in no Intent project, or a node inside one. The protocol treats both the same and names the role by a record instead of relying on a volunteer, which is what 2026-10-24 did.

- Control is a record: `intent estate control take` writes `controller.json` beside the lanes, one per host, with the session, its cross-session name and pid; `control release` ends it. **A take is a handover** (vc decision 88, amended on molt-vc's read): a fresh session has a fresh session id, so `take` succeeds when there is no controller, or when the recorded controller's session is gone by the test the page's ORPHANED uses (its session file absent, its pid dead, or its pid now a process started at a different time than its `procStart`), and the new `controller.json` records the predecessor's session, name and node. While the recorded controller is live, `take` is refused, naming it. `control release` hands over cleanly. **A take keeps the controller's name unless hv says otherwise** (vc decision 88, on molt-vc's point that any peer could otherwise take a dead desk and grant itself): the caller's name is read from its own Claude Code session file, and a take over a recorded controller under any other name, released or gone, needs `--hv "<hv's words>"`, recorded verbatim on the take and shown on the control line. A first take, with no controller ever recorded, needs no words. There is no force flag: a dead controller is the only case a take passes over, and the tool can see it. Lane, grant, deny and revoke writes are accepted from the controller session only.
- The page and `status` show the controller at the top, or NO CONTROLLER, in which case asks queue and nothing is granted.
- Waking it: `intent estate slots watch` blocks and emits one line per state change under `slots/requests/` (asked, started, released), the shape a Monitor consumes, and the coordinator's contract arms it at session start. Requesters have `wait`, the coordinator has `watch`, and the UserPromptSubmit hook injects the pending asks on top.
- A dedicated coordinator stands in no project and has no node, so its WIP line is set directly; a project node that takes control keeps its project and node, and the reader joins its focus as for any node.
- All of it inside Intent, nothing else needed: `intent estate init [<dir>]` renders a dedicated coordinator's working directory from Intent's own templates (`lib/templates/estate/`, through the same token expander as every root file): its AGENTS.md and CLAUDE.md carrying the coordinator contract (take control at session start, arm `slots watch` under a monitor, judge asks against lane capacity and the estate view, release control at session end), and `.claude/settings.json` wiring the same `intent claude hook` lifecycle hooks a project gets. A Claude Code session started in that directory is the coordinator with only Intent installed. A project node that is assigned control follows the same contract, carried to it by the hook injection.

## Work packages

- WP-02 the page: intentd answers the reader over `/op estate_status`, which the page polls; there is no watcher in WP-02, so D20 keeps its two events, and the census tick reaps gone sessions' WIP records (vc decision 73); /estate/status is a route in the one shell document (D56), live, top-styled, with the census and its ring, laid out as `estate-status-mockup.html`; plan usage from the endpoint with the statusline fallback and the named failure path.

## Out of scope

Cross-project announce; federation of estates across hosts (kovacs on rhadamanth's page); slot policy beyond capacity; anything a sleeve or dotfiles framework would add on top, since the coordinator runs on Intent alone.

## To measure before the design is final

- What happens to a session's file when the session is killed rather than ended. **Measured by cc on 2026-10-25 on hv's yes** (Claude Code 2.1.310, the real config dir, an empty scratch cwd outside every project, read by `ls` and `cat`, stamps from `date -u`):
  - At the trust prompt a session has written `<pid>.<64hex>.key` and no `<pid>.json`; the json appeared within a second of the prompt being accepted (18:02:33Z, 18:02:46Z).
