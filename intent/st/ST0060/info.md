# ST0060: Add 'intent vault' as a way for intent projects to manage local credentials

## Objective

Ship `intent vault`: a local credential store -- **per-machine identity, per-project store** -- that lets an Intent project's config files carry a REFERENCE (`vault:<project>/<profile>/<name>`) rather than material, so that reading a config, diffing a profile, or pasting one into a bug report cannot disclose a credential. Built once in Intent for the whole estate, against twelve requirements supplied by Lamplight (ST0358) as a measured requirements provider. **No new crypto and no new auth lane** (hv's constraint): `age` for the encryption, the OS keychain as a passphrase CACHE, the environment as the CI path.

## Context

**The defect is the habit, not the incident.** On 2026-08-25 a session ran `cat ~/.lamplight/config.toml` to find out which port a plane listened on and printed two live API keys, one of them production, into a transcript. One field was wanted; the whole file was printed. hv ruled the exposure low-risk in context and **the habit the defect** -- because no amount of care at the call site fixes it: the care has to be perfect every time, and the file gives no signal that any is needed.

**The exposure is entirely in user-level, untracked stores that no in-repo fence can see.** Lamplight measured its own repository at zero real credentials -- four `ll_key_`-shaped hits, all fixtures -- so a sweep that only greps the repo reports clean and is useless. The material is in `~/.lamplight/config.toml` at **mode 644**, three profiles, while the Wrighter instance file beside it is **600**: the correct posture already exists in that estate and the credential file is the one that lacks it.

**hv's direction collided with two of the twelve requirements, and both collisions dissolve by separating the KEY from the STORE.** hv asked for the vault in `intentd` with a master password in an OS-specific store; R3 requires no daemon and headless safety (SSH, containers, CI), and R2 requires ONE code path across macOS and Linux, where there is no universal Keychain equivalent -- `secret-tool` needs a D-Bus keyring daemon, absent exactly where servers live. The design's answer: **the store is age ciphertext, identical everywhere and daemon-free; the identity is a file; and the only platform-conditional code is a passphrase CACHE with a null implementation.** The keychain holds the passphrase that decrypts the identity and never holds a secret. `intentd` becomes an accelerator under ST0056 WP-08's already-ratified routing rule (_socket present -> daemon; absent -> in-process; never two engines_) rather than a dependency -- which matters because **WP-08 is Not Started, XL, and a 49-line stub**, so a vault that required it could not ship until an XL work package did.

**Status: SPECCED, NOT STARTED, post-3.0.0 by hv's ruling.** The design is at `design.md` and its traceability table is the ratification instrument. **Intent specced this against someone else's measured requirements, so Intent does not get to ratify it** -- AC-00.16 carries the provider's ruling on the one deviation (age Rust crate rather than shelled binary) and the two strengthenings (S1: the posture check must name the IDENTITY, which R12 omits; S2: material must not reach a `Debug` or `Display` rendering, which R11 does not cover).
