# WP-07: intent:// addressing and read resolution

## Objective

Give every hydratable artefact a durable address that does not depend on whether it is currently on disk, and one resolver serving both faces.

## Why (D57-8)

Hydration makes a file path a statement about a moment. **Measured at `ce532a97`: 80 citations of `intent/st/ST####/<file>.md` in tracked estate prose**, the most-cited single artefact being `ST0034/design.md` at 23 -- a COMPLETED thread, and therefore among the first to dehydrate. Three AT rows also point inside `intent/`; the other 87 point at `native/rust` code and are unaffected.

## The scheme

```
intent:///threads/{stid}
intent:///threads/{stid}/wp/{wpid}
intent:///threads/{stid}/ac/{acid}
intent:///threads/{stid}/at/{atid}
intent:///threads/{stid}/attachments/{path}
intent:///issues/{issueid}
intent:///nodes/{moniker}
intent:///nodes/{moniker}/inbox/{sender}/{stamp}
intent:///events/{id}
```

**Empty authority means THIS project.** Cross-project references carry the slug and resolve against intentd's registry.

**VIEWS GET NO URL.** A view is derivable from its entity, so a reference to a view is a reference to its source. Giving views addresses re-creates, inside the scheme, the conditionality the scheme exists to remove. `?format=` selects a REPRESENTATION; a path segment would name a separate thing.

## One resolver, two faces

Resolution lives in `intentsvcs`. The CLI calls it in-process; intentd calls **the same function** and serves it over GraphQL. **The failure mode to guard is intentd growing its own resolver because GraphQL wants different shapes** -- two resolvers agreeing exactly until one moves, with nothing watching.

## `?format=md` needs no new renderer

`views::render_all` already returns `Vec<View { path, content }>` with three callers -- `facade.rs:1236` (what `sync` writes), `doctor.rs:737` (skew), `migrate.rs:293`. Serving `View.content` makes **"the served markdown byte-matches the file `organize` would hydrate" true BY CONSTRUCTION**, because `View.path` is where it would land. `views::skew()` is already the gate's render-and-compare.

## Four outcomes, and two of them must not look alike

hydrated -> content; **dehydrated -> content from the store, and SAY SO**; never-existed -> refuse; withdrawn -> refuse DISTINGUISHABLY. _"Not on disk"_ must never be reported as _"does not exist"_ -- a class this estate has paid for four times.

## AC to write

**No daemon may be required to read your own project.** If reading a dehydrated thread came to need a running intentd, the disk model would have made the estate LESS accessible than a pile of markdown.
