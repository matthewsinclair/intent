# WP-09: The event log records the model and not the disk

## Objective

**Every op that changes the MODEL is recorded; no op that changes the DISK is.** `intent/events.jsonl` is the one table that cannot be re-derived from anything else on disk, and the acts it does not witness are the destructive ones. Close the gap at the boundary, not by widening the chokepoint that is already right.

## The chokepoint exists and it is good

**`Facade::apply` (`facade.rs:3504`) is the single door for model mutation, and it earns the name.** It does not trust a caller-supplied list of what changed -- it DIFFS `next` against the loaded canon, because the declared-list version made *the mutation did not persist* reachable by naming the wrong id, with the database and the return value both reporting success. Comparing against loaded canon cannot forget, and it generalised to issues for free.

Everything reaching it is logged: `ac.put`, `at.put`, `at.set`, `issues.add`, `st.new`, `wp.new`, `wp.rescope`, and the whole `set_thread_status` family -- `st.triage`, `st.start`, `st.hold`, `st.resume`, `st.done`, `st.reopen`, `st.reinstate`, `st.cancel`.

## And the realisation verbs do not reach it

**`grep -c 'apply(' organize.rs` returns 0.** `Facade::organize`, `sync_to_disk`, `sync_from_disk` and `hydrate` each write the filesystem without passing the door. The one other caller of `Store::append_event` is the text-backup path at `facade.rs:1913`, and it is there to obtain the database's stamp rather than to witness an act.

**Measured consequence, 2026-08-19: `organize --apply` removed 423 files from this estate and the log recorded nothing.** The log's 55 events at that moment were 31 `at.set`, 9 `wp.new`, 6 `wp.rescope`, 6 `wp.start`, and one each of `st.new`, `st.triage`, `st.start`. **The only act all evening that destroyed anything is the only class of act absent from the record.**

## Why this is the log's problem rather than organize's

`sync_to_disk` states the log's standing itself: *history travels only if something writes it out; every other entity in this set can be re-derived from a file that is already there, this one cannot.* **A record that is unrecoverable by design and silent about deletion is answering the wrong question.** A reader asking *what happened to ST0001* gets `st.new` and nothing since, while the thread's files left the tree an hour ago.

## Two things NOT to do

**Do not route `organize` through `apply`.** `apply` diffs canon; `organize` changes no canon at all -- disk is the subject. Forcing it through would make the diff a no-op and the event a lie about its own mechanism. The realisation ops need their own emission against the same `Store::append_event`, with the subject being the PATH SET rather than an artefact id.

**Do not add a pruner.** Growth is not the problem and a retention policy on the one unrecoverable table trades a real loss for an imaginary one. Measured: 55 events in the first 35 hours, ~229 bytes each, on the heaviest four-node day this project will see. At that rate a year is ~17k events and under 4MB.

## What IS worth deciding at the same time

**Concurrent append.** It is a tracked, append-only file written by four sessions committing minutes apart, so every concurrent write is a same-line git conflict waiting to happen. Seven commits have touched it without one, which is luck at 55 rows rather than a property. **Decide it while there are 55 rows to migrate, not 17,000** -- per-node event files that merge, or a store-side sequence that the file is projected from.
