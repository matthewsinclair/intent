# WP-01: Canon relocation to intent/.canon/

## Objective

Move per-artefact canon out of `intent/st/<ID>/` and into `intent/.canon/st/<ID>.json`, so that `intent/st` can empty. Foundational: every other WP in this thread assumes the layout.

## Deliverables

- Canon at `intent/.canon/st/<ID>.json` and `intent/.canon/issues/<n>.json`, still ONE FILE PER ARTEFACT.
- Migration of existing canon, with the conservation verdict green over a pinned subject before anything is removed.
- `intent/.canon/` explicitly NOT gitignored, asserted by a test rather than by inspection.

## Why C, and why not A or B (D57-1)

**A -- canon in place.** Bytes fall ~60% but `intent/st` still lists 56 entries, so it does not meet the requirement.

**B -- one consolidated `threads.jsonl`.** Rejected: four concurrent writers make a single canon file a merge-conflict generator, and this estate has four nodes.

**C -- ruled.** The only option that empties `intent/st`, keeps a clone complete, and keeps a per-artefact diff so two nodes editing two threads never conflict. It is a path change, not a model change.

## The constraint that must not be lost

**D29: a gitignored path is never canon.** Canon is the layer that TRAVELS -- if `intent/.canon/` were ignored, an unrealised artefact would exist only inside a gitignored database, absent from a fresh clone and destroyed by `rm -rf intent/.cache`. That single rule is what makes every deletion in this thread safe rather than careful.

## Done when

`intent/st` holds `steel_threads.md` and the realised threads, nothing else; a fresh clone reads every thread whether realised or not.
