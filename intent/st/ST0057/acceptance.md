# ST0057: Disk as a sparse projection of the store -- Acceptance

> Canonical acceptance contract. Acceptance Criteria (AC) are the ratified completeness boundary; Acceptance Tests (AT) are the small red-to-green tests that prove them.
>
> Done = every AC is covered by a GREEN AT, or (for a non-test AC) its named evidence is satisfied, AND the AC set is the ratified full boundary. Done is read from this map, never from a hand-ticked box.
>
> Test-backed satisfaction is COMPUTED from covering green ATs and never stored -- storing it would be double truth. An AC has four states, not two: beyond satisfied and unsatisfied, a requirement can be **descoped** to a named thread or **withdrawn** with its reason on the record. Both are non-blocking and both are reported separately, so a thread that descoped half its contract looks like one.

### WP-03 -- Attachment canon: opaque as file, and the naming gate (status: Not Started)

- AC-03.1 **An opaque attachment's bytes live in canon as a file at `intent/.canon/st/<ID>/<path>`, and hydration reproduces the working copy byte-identically from it.** Denominator printed over every opaque attachment in the estate. - AC-03.2 **Form follows content, both ways: no opaque attachment is stored inline and no text attachment is stored as a sibling file.** One rule, checked in both directions -- a check that only catches one direction passes an estate that has drifted the other way. -- satisfied: no (computed)
- AC-03.3 **The naming gate rejects, at ingest, any attachment path that cannot be given both a canon path and a URL -- and rejection is NOT retroactive.** An existing violator (the estate already carries a `.webloc` with spaces in its name) is reported by `organize` as UNCLAIMED under its fifth row and never silently removed. -- satisfied: no (computed)
- AC-03.4 **`sha256` in canon detects a working-copy edit by COMPARISON rather than inference**: an attachment modified on disk without the store knowing is reported by `doctor` as divergence, and the report names the path. -- satisfied: no (computed)
- AC-03.5 **`sync --to-store` REPORTS an attachment whose on-disk bytes differ from what the INDEX holds for that path** (dc 2026-08-18, from a live instance). The ingest path reads the WORKTREE, so an uncommitted edit sitting in the tree is carried into canon by whoever syncs next -- and canon then records an artefact whose bytes exist in NO COMMIT, indistinguishable on inspection from a correct one. **That is AC-11.5(c) of ST0056 arriving in canon rather than in vendored files, and the ratified remedy is NOT applied on this path**: arm 1 of `self_provenance_check.sh` reads `git cat-file blob :$rel` precisely to avoid it, but it validates the manifest and never an attachment, so it passes. **The rule currently exists only as an instruction between nodes -- commit yours first -- and a rule that lives in a peer message is followed until someone is mid-task**, which happened twice in one afternoon, once to the node who wrote the rule. -- satisfied: no (computed)
- AC-03.6 **A COMMIT MUST NOT CONTAIN CANON THAT NAMES BYTES NOT IN THAT SAME COMMIT.** (dc 2026-08-18, answering vc's refuse-or-report question with neither option as framed.) **AC-03.5's report is correct and insufficient, and the reason is WHO it reaches**: when this fired, the uncommitted file was dc's and the syncer was vc, so a report names a path to a node that CANNOT act on it -- staging a peer's file sweeps their work into your commit, which is the hazard being avoided. **And the harm is not at sync.** Canon holding uncommitted bytes in a working tree is a dirty tree: normal, reversible, nobody's problem. **It becomes permanent and inspectable-but-wrong at the COMMIT** -- the moment a reader can later check out that revision, read an attachment, and be unable to obtain the bytes it names. **Both halves of the justification are already ratified**: ST0056 AC-11.1 puts the control where the HARM is, and the whiteboard clock guard blocks only on what the commit ADDS and never on inherited breakage. The check is cheap because both sides are already to hand for every attachment -- the `text` in canon, and `git cat-file blob :$path` for the file it came from -- **which is arm 1's comparison one population over.** **THE INHERITED-BREAKAGE CLAUSE IS LOAD-BEARING AND MUST BE BUILT, NOT ASSUMED (dc 2026-08-18, measured over the FULL population after retracting a 14-commit window that flattered this argument): of 46 commits carrying canon with attachments, 23 DISAGREE AT ALL -- 50%, not the 14% the window suggested -- and only 5 ADD a new divergence.** **A naive refuse-at-commit would block half of all commits, which is precisely the guard nobody keeps, so vc's original objection applies at the commit boundary too.** What rescues it is the clock guard's ratified rule: **block only on what the commit ADDS, never on inherited breakage** -- and that turns 23 into 5. **Divergences are EPISODES, not events: a file diverges and stays divergent for every subsequent commit until someone syncs** (`estate_corpus.sh` ran divergent across NINE consecutive commits). **If this criterion is implemented without the inherited-breakage clause it will be built as the 23 version and abandoned within a week.** The five episodes, each named by the commit introducing it: `d980e5b5`, `aa220755`, `7ee3019b`, `31f2dce4`, `c4f9bcbe`. **THE PROPERTY IS SYMMETRIC AND THE REASONING MUST NOT NAME ONLY ONE DIRECTION (dc 2026-08-18, from a live catch at HEAD by the checker's first whole-tree run).** At `c4f9bcbe` CANON RAN AHEAD of the commit -- a sync ingested worktree bytes nobody had committed. At `3f10b1ee` THE FILE RAN AHEAD AND CANON STAYED BEHIND -- an attachment was edited and committed with no re-sync, so canon named bytes that existed neither in the commit nor on disk, with a clean worktree. **Both satisfy _canon names bytes this commit does not contain_ and both are caught by the same comparison, but a criterion worded as _a sync must not ingest uncommitted bytes_ describes only the first and misses the second entirely.** The second half is the one that was live. **Stated as the invariant rather than as a prohibition on one operation: at every commit, every attachment's recorded bytes are obtainable from that commit.** **AND IT IS A PROPERTY OF EVERY COMMIT, NOT OF HEAD (dc 2026-08-18, giving the reason the remedy text needed).** Committing the file first and syncing afterwards leaves THAT COMMIT DIVERGENT IN HISTORY PERMANENTLY: a later sync repairs the NEXT commit and can never reach the one already made. **So the compliant order is sync canon FIRST -- because sync reads the worktree -- then commit the file and canon together**, and the obvious order is wrong independently of any gate. **WHAT A CHECKER CAN ESTABLISH SPLITS THREE WAYS, NOT TWO (dc 2026-08-18, correcting vc's too-strong form): NARROWED says this revision ADDS nothing; EXHAUSTIVE at a revision says THE PROPERTY HOLDS THERE, since every attachment matching the bytes that commit holds IS the property evaluated at that point; and NEITHER establishes the property ITSELF, because it is a claim about EVERY commit.** Only a history mode speaks to that, and only over the range it was handed. **A green at HEAD is compatible with a history full of divergences, and a gate cannot repair the past and must not claim to** -- which is why the inherited-versus-adds split is structural rather than a convenience. -- satisfied: no (computed)
