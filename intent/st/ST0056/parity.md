# Parity contract - ST0056: v2 conformance for the v3 CLI (WP-01 spec)

## The contract

**The v3 binary is certified by the incumbent**: the v2 BATS estate runs against it via an `INTENT_BIN` override, and v3 is green when v2's own suite cannot tell the difference -- except where this contract says so, in advance.

- **In scope (parity holds)**: stdout shape, stderr voice (`ok:`/`error:` lowercase, 0023), exit codes, command/subcommand/flag grammar, behavioural semantics.
- **Ratified deviation classes (decided here, never discovered in triage)**:
  - **File layout** -- structured canon appears (`thread.json`, `issues/<n>.json`); `info.md`/`acceptance.md` become generated views; frontmatter conventions on structured data retire (D01-D04). Tests asserting bytes-in-files that are now views retire with the layout.
  - **Issues directories** -- `OPEN/`/`CLOSED/` stop encoding status (status is data); index views replace directory browsing.
  - **Generated-view banners** -- views carry a generated footer; tests asserting their absence retire.
  - **Manual-edit workflows** -- tests that hand-edit structured md and expect the tool to honour it convert to mutation-based equivalents or retire (authored-once, D02).
  - **Corrected** (proposed by ic, hv-ratified at the bounce 2026-08-14) -- a v2 behaviour that is simply wrong and is fixed rather than faithfully reproduced. Distinct from **deviate**: deviate is a design consequence of v3; corrected is a bug fix. Both carry a ratification reference per register row. Known members from ic's census, one per line so each can carry the machine-read `covers:` clause that binds it to the units it ratifies (format adopted by vc 2026-08-15 on ic's proposal: spaced `--` separator, comma-separated ids, nothing fused; checked by `parity/tools/corrected_check.sh`):
    - unknown flags accepted silently with exit 0 (`info`/`config`/`version` -- clap exits 2, so v3 diverges on day one whether or not anyone decides to) -- covers: INV-08, info, version
    - `--help` reporting failure on 10 of 27 commands -- covers: INV-07, st, wp, ac, at, todo, fileindex
    - the stderr/stdout misroute census (45 stderr-only / 12 stdout-only / 2 both on failing invocations -- larger than the three sites in cc's hv queue) -- covers: INV-06
  - **Undefined** (vc ruling 2026-08-14, **hv-RATIFIED 2026-08-16** -- opened on `intent config`, its first and only member) -- v2 exhibits NO behaviour to be faithful to (0 bytes on both streams, exit 0), so v3 is DESIGNING rather than porting or correcting. **Distinct from Corrected, which needs a v2 antecedent to correct: silence is not an antecedent.** Folding it into `corrected` would hide a design decision inside a bug-fix class, and design decisions need a different reviewer. **The class is grounded rather than notional: `class_vocab_check.sh` reads this list and is green, and `intent config` is `disposition: pending`, so `undefined` is the only marker distinguishing "the blank is because v2 was SILENT" from "the blank is because nobody looked yet."**
- **Explicitly out of parity scope**: `bin/release` and the test harness itself (repo dev tooling, not shipped surface); and **`new-surface` entries -- a v3 command with no v2 antecedent has nothing to be faithful to, so this contract is silent about it by construction and its coverage is governed by WP-06 rather than here** (vc 2026-08-15, provisional pending hv, on ic's finding that 18 rows carried the state and no decision recorded it).

## Parity properties (beyond output equality)

Output-equality across implementations cannot catch v3 faithfully reproducing a v2 bug -- the two would agree and the suite would go green. Properties asserted directly, per scoped verb:

- **Scope-honouring (issue 0024):** an instrument that accepts a narrowing argument answers the narrowed question, and its output names the resolved scope. Found in v2: `at lint <ID>/NN` and `ac gate <ID>/NN` silently dropped the WP scope, and a scoped `--fix` rewrote rows OUTSIDE the scope; an equality-only suite would have carried that into v3 as certified behaviour.

## The keep/retire/deviate register

One row per BATS test file (finer-grained per-test rows where a file mixes classes), maintained from WP-05 and complete at WP-06 close:

```
| tests/<file>.bats | <tests> | <burn> | keep · retire · deviate | <deviation class> | <ratification ref> | <exposure> | <notes> |
```

The `<command(s)>` column this schema previously specified is **struck, not owed** (vc, 2026-08-15, on ic's ask). The register is file-level; the file-to-command mapping lives in `coverage_map.sh`, where it is **measured** rather than transcribed. A transcribed copy of a measured mapping is a divergent copy that drifts from the thing it copies, and the register is the last artefact that should carry one. ic was right to raise it rather than quietly diverge a second time -- a contract document naming a column nobody implements is the same defect as an implementation nobody contracted.

- **keep** -- asserts command surface; runs unmodified against `INTENT_BIN`.
- **retire** -- asserts the old layout or a v2 implementation detail; retired with a named class from the list above.
- **deviate** -- asserts surface we are deliberately changing; each carries a D-number ratified in design.md before the port lands.

The register is the honest ledger of everything the rewrite changes. An unclassified failing test is a defect, not a candidate for reclassification-in-the-moment.

## The IC handoff (deep pass)

Two deliverables, design-neutral, v2-side, feeding WP-05:

Flag any test that fits no class -- that is a contract gap for vc, not a judgement call for the classifier.

Working rules: sacrificial worktree for anything touching `bin/**` or helpers; mutation-check any harness change (a retargeted suite that cannot fail proves nothing -- point `INTENT_BIN` at `/usr/bin/false` and watch it burn before trusting a green). A mutation canary must come from the same fixture and branch the test drives -- **applied is not reached** (cc, 2026-08-14: a substitution can apply on a branch the test never walks and read as "does not discriminate").

## Measurement rules

### THE SHAPE THE REST ARE INSTANCES OF: the measurement's subject and the report's subject are different, and the output cannot tell them apart

**Consolidated 2026-08-17 (vc), after seven variants were observed in one day across four nodes.** Each was previously read as its own mistake. They are one: **an instrument measured something, the report named something else, and nothing in the output distinguishes the two.** The failure is never in the measuring step and always in the reporting step, which is why care at the point of measurement does not prevent it.

**The last row is the one this estate is structurally most exposed to, and it is ic's** (2026-08-17, naming it in their own work after the third instance): **a surface is all declarations**, so any question asked of the command surface can be answered from what is declared while the report speaks about what runs. Four of the seven instances below were about the surface for exactly that reason.

**Two properties make the class expensive.** Every one of these returns a well-formed result rather than an error, so nothing prompts a second look. And a wrong subject usually makes the finding STRONGER -- an empty corpus reads as "no violations", a truncated population reads as "all green", a missing `cd` reads as a defect found -- which is the asymmetry rule below, arriving one level up.

**AND THE TOOLING BUILT TO CATCH THE SIX HAD THE SEVENTH** (ic, 2026-08-17, in the mutation harness proving the `self_loop` binding). Its restore ran on relative paths while a helper had changed directory, so the trap meant to undo each mutant never fired and the mutations sat on disk unnoticed. **"A guard that does not run looks exactly like a guard that found nothing."** That is the whole class in one sentence, and the null result is the dangerous half: a harness reporting no findings and a harness that never executed are the same output, so the arm most worth canarying is the one that is supposed to stay silent. Recorded in the file rather than fixed quietly, which is what makes it worth more than the fix.

**The lesson is NOT "use absolute paths"** (ic's own correction of it). It is that **a cleanup step produces no output when it works, so success and never-having-run are byte-identical at the observation point.** That is what makes it a member of this class rather than a scripting slip: the restore's report and the restore's subject came apart, and there was nothing available to read that would tell them apart.

**AND THIS DOCUMENT IS ITSELF A HAZARD TO THE INSTRUMENTS IT TEACHES YOU TO BUILD.** vc, 2026-08-17: a sweep for stamped artefacts returned a third revision, unbackticked and therefore invisible to `provenance_check.sh`'s parser -- a finding, until it turned out to be `gen_register.sh:34`, a header comment narrating that very incident. **The artefact recording the lesson became a false instance of the lesson.** The hazard is specific and it grows: **the more carefully this canon quotes the strings it is about, the more of them it contains for the next grep to find.** Same shape as counting the `rusqlite` doc comment -- which asserts the thin-skin invariant -- as a violation of it. When sweeping the estate for a pattern, the documents that discuss the pattern are the first place it will falsely appear, and they are also the documents most likely to be read as authoritative.

**The operational form is not "was the measurement right".** It is **"what was this measurement ABOUT, recorded in the artefact"** (ic's framing, 2026-08-17): which tree, which process, which corpus, which layer, which population. A result that names its own subject is self-identifying when it goes stale; a result that does not needs somebody to remember, and a rule depending on its author remembering it at the moment of use is not a control. That is why the fix for 0049 is a `measured:` line and not a resolution to be careful.

**Calibrate an instrument against a known-good case before believing its output -- especially a zero.** A measuring instrument reporting zero is indistinguishable from a broken one until it has been shown to report non-zero somewhere it should. Two harness lies crossed nodes in one afternoon from a single root: zsh does not word-split unquoted parameters, so `intent $probe` with `probe="wp list"` passes ONE argument and the dispatcher correctly reports a command it does not know -- inventing a defect in `intent wp list` that does not exist. The control costs one command. Applied within the hour to the next instrument built: before believing `intent config` had zero test coverage, the same needle was run against `doctor` and returned 3.

**A broken instrument that strengthens your finding does not get questioned; one that weakens it does.** The calibration rule above catches the first kind of error -- a zero you cannot distinguish from a dead instrument. This catches the second, and it is the more dangerous kind because nothing about it feels wrong at the time. Measured on this thread in one afternoon: a probe loop that passed one argument instead of two invented a defect in `intent wp list` that does not exist; a verb-extraction grep that omitted `sync` produced a divergence between two artefacts that in fact agree exactly; a `grep -c` for list items returned 0 against a section written as bolded paragraphs and nearly reported it empty. **All three would have made the finding stronger, and none was questioned until someone read the underlying thing instead of the count.** The asymmetry is not luck: an instrument whose error costs you a finding gets debugged; one whose error hands you a better story gets believed. Suspect your instrument hardest exactly when it agrees with what you were hoping to show.

**Success is reported by the mechanism; the property has to be checked by something else.** An edit that removes something is not verified by the edit succeeding -- two successful `Edit` calls during a board tidy silently deleted this thread's biggest finding, and it survived only because someone grepped for it afterwards. Four routes reached this shape in one day and they are one shape: a mutation that applies on a branch the test never walks; a guard scoped to what is already clean; a file clean by luck rather than by construction; and an edit whose success says nothing about what it left behind. In every case the operation returns success and the property is absent.

**A file clean by luck and a file clean by construction look identical in a diff, and only one of them stays clean.** Record what an artefact is NOT protected against, not only what it currently passes -- a green check that cannot say which kind it is has told you less than it appears to. Three routes reached this idea in one day, which is usually the sign it is load-bearing: a mutation that applies on a branch the test never walks; a guard scoped to what is already clean, which certifies the status quo; and a generated view that is formatter-stable only because nobody happened to write emphasis into it yet.

**Classifying by the shape of a failure is a guess that looks like a finding** (cc, 2026-08-14, caught in their own delivered work). A red assertion tells you a test failed; it does not tell you why, and the two readings lead opposite ways -- a genuine parity break, or a test that hand-builds a v2 estate in its own body and is therefore a ratified retire under the manual-edit-workflows class. cc classified 35 rows from failure shape, then re-read the tests and found most were the second: 26 of 54 and 23 of 30 were building the old estate inline. **The register's classes are about what a test IS, not about whether it passed**, and a classification derived from a failure is the register recording the harness's state instead of the estate's. Read the test.

**`cmd | head; echo $?` reports the PAGER's exit status, never the command's** (vc, 2026-08-14, three times in one session). Exit codes are half of what this thread's parity contract is about -- D17 carries v2's codes over, INV-02 forces an override of clap's default, and the pre-commit gate reads one -- so an exit code read through a pipe is the single most load-bearing number the harness produces, and a pipeline reports the LAST stage. It manufactured two clean defects that do not exist: `intent search` with no arguments "exiting 0 on a usage error", which reads as a No Silent Errors violation and is actually exit 1; and `intent ac gate` "printing BLOCKED and exiting 0", which reads as a broken close-gate and is actually exit 1. Both were about to be reported to the node that wrote the code. Redirect to a file and read `$?` before anything else touches it, or use `${PIPESTATUS[0]}` -- and note the direction one more time: **all three artefacts handed back a finding rather than a dull result**, which is why the asymmetry rule below is the one worth re-reading before believing an instrument.

**A guard verified in one harness is not verified; it is verified in that harness** (ic, 2026-08-14, found by their own guard failing silently in the caller that mattered). The corpus guard tested green under `gen_register.sh` (`set -uo pipefail`) and was DEAD under `coverage_map.sh` (`set -euo pipefail`): the bare command substitution inside `corpus_require` aborts the shell the instant the diff reports a disagreement, so the tool exited 1 with an EMPTY stderr against a baseline known to be four files short. **A guard that dies silently in strict mode is worse than no guard -- it reads as a clean tool failure rather than as a finding.** The general shape is that shell options are part of the harness, not part of the script: `set -e` changes what a non-zero return DOES, so the same guard body has two behaviours and only one was ever exercised. Test each caller, each with its own canary, and confirm the guard names the real defect rather than merely refusing.

**Two consumers of one artefact grow two different wrong behaviours around the same missing check** (ic, 2026-08-14). `coverage_map.sh` did not merely read a stale baseline -- `[ -n "$row" ] || continue` **skipped** any file absent from it, so three files left the arithmetic entirely under a verdict that printed with full confidence, while the register's own generator went wrong a different way on the same gap. The fix is not two fixes: the comparison moved into `lib_corpus.sh` once and both callers refuse on it. **A missing check does not produce one bug; it produces one bug per consumer, and they do not look alike, so finding the first teaches you nothing about the second.**

**A count is not a diagnosis, and a record is complete only against the revision it names** (vc, 2026-08-14, caught in vc's own reported finding). A register carrying 97 rows against 98 files on disk was read as a dropped row and reported to its author as a hole in their sweep. The count was right; the cause was invented. At `309d01d` -- the revision the register names -- there were exactly 97 files, and the 98th landed at `ddac6ba`, which `git merge-base --is-ancestor` shows is not an ancestor of it. Nothing was dropped: the estate grew after the measurement, which is the record working as designed rather than failing. Two checks settle it and neither is arithmetic -- ancestry, and a set difference in **both** directions, since a phantom row and a missing one are different defects that one total conceals equally well. The generalisation is the expensive half: **any point-in-time register is falsified by the next test that lands**, and here the falsifying commit was itself a guard test written six minutes before the register was regenerated. An artefact measured at a revision must name it, and a contract consuming such an artefact must say which revision it means -- or it silently demands an estate-wide re-sweep every time anyone writes a test, which is a standard nobody can hold and everybody stops trying to.

**A file named after a command that does not test that command is worse than no file.** It answers "is this covered?" wrongly and confidently. `tests/unit/config.bats` exists, burns 5 of 7, tests configuration LOADING via `intent info` / `intent doctor` / `intent st list`, and never invokes `intent config` once -- so the command has zero coverage while the file listing implies otherwise.

**File-level classification is structurally blind to command-level coverage.** This is a stated limitation of the register, not an oversight in it: a `split` row is silent about whether any command family is exercised by nothing, because it classifies files and the question is about commands. `parity/tools/coverage_map.sh` answers that question instead, by joining the dispatch table's families against `burn-baseline.tsv` -- and the join is the method, since a naive grep reports `treeindex` as one of the best-covered families in the estate when all 53 of its tests exec the binary directly and the dispatcher sees none of them.

**A command family with zero burning coverage is a parity hole**: v3 can change it freely and the conformance suite stays green. Condition on AC-00.1; the work lives at AC-06.1.

**The burn ratio is BLIND TO NEGATIVE-ASSERTION TESTS, and the blindness is one-directional.** A test that asserts a _failure_ passes under both bindings, because `/usr/bin/false` fails too. `intent_upgrade_orchestrator.bats` runs `run "$INTENT_BIN" upgrade; assert_failure` -- it genuinely exercises the CLI and burns zero. Measured 2026-08-15: six such tests across three files, surfaced by the per-test pass as `UNCLASSIFIED / invokes CLI, zero burn` rather than found by inspection.

Two consequences worth separating. **The error direction is safe**: the method UNDER-counts CLI reach and never over-counts, so a burn figure is a floor on conformance coverage rather than an estimate of it. And **the blind spot is detectable rather than silent**: a zero-burn test that nonetheless calls the CLI is exactly the combination `classify_no_burn` refuses to classify, so these arrive as named rows wanting adjudication instead of quietly joining `out-of-scope`. A method with a known hole that reports into the hole is worth more than one whose hole is invisible.

**A fixture built to have "no git" was inside a git repository** (vc, 2026-08-15). The scratch directory this thread works in sits under `/Users/matts/.claude`, which is itself a repo, and git resolves a repository **at or above** -- correctly. So a fixture with no `.git` of its own still inherited that repo's ignore rules, and a measurement of "what happens outside git" measured something else entirely and reported it into the contract as fact. **Assert the environment you think you are in before measuring in it**: `git rev-parse --show-toplevel` costs nothing and is the difference between a fixture and a belief. Give a fixture its own `git init`, or place it where no repo is above it, and say in the record which of the two you did.

**A paired control tells you the INSTRUMENT changed, not just that the fix failed** (vc, 2026-08-15). Re-running a two-arm probe after cc's fix, both arms went silent -- including the arm that had reported before and had no reason to stop. One arm alone would have read as "the fix did not take" and been sent as such. Both arms silent is not a result about the subject at all; it is a result about the instrument, and the correct next question is what changed underneath rather than what the change proves. The discriminating pair earns its cost twice: once for the verdict, once for knowing when there is no verdict.

**Test data placed in a generated artefact is destroyed by the mechanism under test** (vc, 2026-08-15). Appending a unique phrase to `info.md` and then searching for it measured nothing: `info.md` is a generated view under D22, so `sync` regenerated it and discarded the edit -- correctly, and silently, and the subsequent empty search read exactly like a broken index. **Put test data where the truth lives**, which under D01/D02 means the canon, never a view. The general form: when the system under test owns an artefact, that artefact cannot also be your input.

**A stated cost is a claim, and it gets re-run like any other** (ic and vc, 2026-08-15, both wrong on the same number). The register sweep was described as multi-hour and not parallel-safe; that description was written into a tool's justification, quoted across nodes, and used by the verifier to REFUSE a re-sweep. Timed once, it takes **7 minutes 52 seconds**. The multi-hour figure came from a single file hanging, and a defect had been generalised into a property of the tool. Nobody had timed it. **The verifier's whole function is to re-run claims rather than read them, and a claim about cost was exempted purely because it arrived as a constraint rather than as a finding** -- constraints are the claims most worth checking, because they are the ones that stop work happening. Corollary: a deferral justified by an unmeasured cost is not a trade-off, it is a guess with a schedule attached; fix the stale row instead of noting it.

**A test written from the same misreading as the code cannot catch the misreading** (cc, 2026-08-15). A test named `both_spellings_of_sync_are_wired_and_agree` asserted the two produced identical bytes, passed, and was read as confirmation -- when all it confirmed was that a wrong model was internally consistent. `intent st sync` and `intent sync` are different commands. The incumbent's behaviour caught it, not the suite. This is the deeper form of the calibration rule: an instrument built from the hypothesis it is testing cannot falsify it, so the discriminating evidence has to come from OUTSIDE the model under test -- the v2 binary, the committed artefact, the thing that existed before the belief did.

**A check that answers confidently about a set it never looked at** (cc, 2026-08-15, naming the class the three of us hit independently in one night). Not a wrong answer -- **an answer to a different question, wearing the right answer's clothes.** Four instances, none of which announced itself: a `covers` regex written `([^-]+)` stopped dead at the hyphen in `AC-06.2`, matched zero rows, and printed a clean "nothing outstanding"; a corpus fixture keyed on `*.sql` passed identically whether or not the config under test was loaded, because the pattern was in the real global too; an ignore-needle matched `$INTENT_BIN` as a search string rather than a call site; and a green-transition check tested a file's EXISTENCE where the property wanted was that it is committed. The shared defect is that each returned a well-formed result for a population it had not established it could see. **Assert the needle matched something, and print the size of what it matched, before reporting on it** -- a count you can see is a needle you can argue with, and a zero from an unproven needle is indistinguishable from a genuinely empty result.

**Writing a rule down does not stop the author breaking it, and the evidence is this thread** (vc and cc, 2026-08-15, independently and repeatedly). vc fabricated FOUR whiteboard timestamps in one session -- while writing the clock rule, enforcing it on a peer, and citing it in the message that carried the fourth. cc read a corpus through `| head`, lost the eleventh of eleven rows, and published "ten spellings" into a source comment and a commit message -- with `| head` already on their own board as a watch-out, three lines from the pipeline-exit-code note, added in that same session. Neither failure was ignorance of the rule; in both cases the author had written it that day.

**So a rule that depends on the author remembering it at the moment of use is not a control, it is a hope with good phrasing.** The two remedies that actually worked here were both mechanical and neither required anyone to remember anything: the pre-commit clock guard REFUSED a bad stamp, and `lib_corpus.sh` REFUSED a register generated against an incomplete baseline. The two that failed were both documentation. This is the general form of D30's timestamp argument and of the guard-rather-than-a-promise choice made throughout this thread -- **when a rule matters, spend the effort on the mechanism that enforces it rather than on the sentence that states it**, and treat a rule you can only obey by concentrating as an unfixed defect rather than a solved problem.

**A generated artefact that cannot be re-derived from committed state has no cheap check, and its stamp is the only guard it has** (vc, proposed 2026-08-15; ic, evidenced the same day). Not a theoretical class. The 26 `cmd-*.md` command inventories are generated by `gen_inventory.sh` from `probes/toplevel.tsv` -- a file the script only ever READS, which lives in a throwaway scratch directory, has **never been tracked**, and is no longer on disk anywhere. So the input behind the committed measurement at `69d42a7` is gone, and those 26 artefacts can be checked for provenance (do they all name one revision?) and not for content. **That is a materially weaker claim than the drift check has been assumed to rest on**, because the inventory is the measurement half of the comparison the table is checked against: the authored side is fully checked and the side it is compared to is not.

**CORRECTION, 2026-08-15 (ic): "gone" was wrong -- it was UNTRACKED, which is a different thing, and looking is cheaper than reasoning about it.** The paragraph above concluded the input no longer existed anywhere on disk. It was still sitting in the originating session's scratch directory, along with the ad-hoc driver that produced it, the fake HOME it ran under, and the sandbox. `git log --all` was the right query for "was this ever committed" and the wrong one for "does this exist"; nothing had been run against the filesystem. **The TSV is now recovered and COMMITTED at `parity/probes/toplevel.tsv`**, which is what the rule asked for all along, and the driver is committed beside it as `tools/probe_toplevel.sh` -- it had never existed as a file.

**With the real input back, the 26 inventories were checked for content and are exactly faithful to it: 26 of 26 reproduce, modulo table padding.** So the weaker claim was true of the record and not of the artefacts. Three further findings from the same run, all measured:

- **Exit codes reproduce 26 of 26 at the same revision; first lines 26 of 26 in behaviour.** Byte counts reproduce 20 of 26 -- the six that move (`bootstrap`, `doctor`, `ext`, `help`, `info`, `todo`) embed the sandbox's ABSOLUTE PATH in their output, and `ext` differs by exactly the path-length delta, 55 bytes against 55 characters. **The byte column is a property of the path the probe ran under, and that path was never recorded.** Exit codes and first lines are the portable half.
- **`probe.sh` isolated `INTENT_HOME` and not `HOME`, and got away with it because the uncommitted driver did `export HOME="$SP/fakehome"` before sourcing it.** When that driver went, the isolation went with it: a re-probe written against the committed file alone read the developer's real `~/.intent/ext` and took a different code path. This is this document's own mechanism-over-sentence rule turned on itself -- **the isolation that was written down survived and the one that lived in someone's shell history did not.** Now in `probe.sh` where a caller cannot forget it.
- **The probe matrix MUTATES ITS OWN SANDBOX and is therefore not idempotent.** `intent todo` bare generates `intent/todo.md` when absent, so run one records `no intent/todo.md yet -- generating...` and run two records the read path -- two runs of one script at one revision disagreeing on a first line, with nothing in the output saying which run it was. The driver now rebuilds the sandbox rather than reusing it. Same command, same reason its dispatch-table row is classified `mutate`.
- **The provenance's "108-probe matrix" is right and the inventory renders 104 of them.** The 27th unit is `version`: probed on 2026-08-14, never given a `cmd-version.md`, because `gen_inventory.sh`'s spec list has no entry for it. Measured data exists for a command the inventory does not carry.

**Worse, the artefact instructs the reader to destroy it.** Every generated header says _"re-run it rather than editing this file"_ -- correct advice that, once the input vanished, would have overwritten 26 good measurements with empty probe fields carrying the revision stamp of the good data. Measured rather than assumed: `awk` against a missing file exits 2 and produces **nothing**, so the dash fallback never runs, and the script's `set -uo pipefail` without `-e` does not stop it. The remedy is the one this section keeps arriving at -- `gen_inventory.sh` now REFUSES on a missing or empty TSV, because **a missing measurement must present as a refusal to measure, never as a measurement of nothing.** The general rule for anyone adding a generator here: if the input is not committed, the output is stamp-only, and saying so in the record is part of producing it.

**RE-DERIVABILITY IS NOT COMPLETENESS, and a lossy generator is a perfect fixed point with itself** (ic, 2026-08-15). The skew check asks whether a committed view matches what its generator PRODUCES. A generator that silently drops a field satisfies that for ever: regenerate, compare, identical, green. Measured on `dispatch-table.md` -- the canon carried **20 distinct `target` sub-fields and the renderer named 5**, so 15 were written, committed and invisible in the human-readable face, including config keys another node was blocked on. **The check was not wrong; it was answering a different question faithfully**, which is the hardest kind to notice because nothing ever contradicts it. Two properties, two checks: skew for re-derivability, and a completeness refusal comparing the canon's own keys against the rendered text. The corollary for this toolchain: **every generator wants to be asked "does the view carry everything the canon holds?", separately from "does the view match the generator?"** -- and the second cannot answer the first.

**ENUMERATE THE POPULATION; DO NOT SNIFF FOR A MARKER** (ic, 2026-08-15). A needle reports on the set it MATCHED, never the set it was aimed at -- so before building a check on one, count what it matches and print the count. Measured: a backstop planned around detecting a `GENERATED` banner would have covered **1 file in 30**, because 29 generated views carry no banner; enumerating the apparatus directories instead covered all 30. The same shape twice more the same day -- a `jq '.families[].entries[]'` audit reported a canon clean while every offending string sat in a top-level array that path does not traverse, and a mutation run went red from a **different guard entirely** because the fixture never reached the branch under test. **A structured query is a needle too**, and it reports on the subtree it walked. The discipline is cheap and mechanical: derive the population from something that must be complete (a directory listing, the canon's own keys, a declared roster), never from a property the members happen to carry, and **assert the fixture reached the branch before reading its verdict**.
