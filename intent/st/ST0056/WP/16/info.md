# WP-16: Contract drift: a shipped field with no model row is refused

## Objective

Make the schema and `data-model.md` mechanically agree, so a field cannot ship without a contract row and a row cannot describe a field that does not exist. Two instances have now been found by hand, one of them after it cost 434KB.

## The class

**Nothing mechanical connects a shipped field to its model entry.** The generated faces are drift-checked against the Rust types; the PROSE contract that humans read is not checked against anything. So a field can exist in `schema/*.json` and be absent from `data-model.md`, or the reverse, and both states read as normal.

**It is found only when somebody happens to edit the row next to it**, which is how both known instances surfaced.

## Two instances, both measured

**1. `steel_thread.body` shipped without a contract row.** Found while adding `preamble`. The gap has two ends -- cc landed the field, vc owns the table -- and nothing joined them.

**2. `issue.body` and `issue.reporter`, 2026-08-18, and this one had a cost.** `schema/issue.schema.json` declared `body`; `data-model.md`'s issue table carried neither `body` nor `reporter`; and the heading specified a sibling `issues/<n>.md` that has never existed in the flat layout. **Two specifications disagreeing and NEITHER implemented, so 434,357 bytes of authored issue text across all 40 issues lived only in `intent/.cache/intent.db`** -- gitignored, therefore never canon under D29, therefore never travelling under D34, therefore absent from every clone since the hoist. It surfaced only when `sync --to-store` replaced the store from an extract that had never carried it.

## What to build

A check that joins **the schema's property set** to **`data-model.md`'s table rows**, per entity, and REFUSES on either direction:

- a property with no row -- a field shipped with no contract
- a row with no property -- a contract describing something that does not exist

**Both directions, because they fail differently.** The first ships undocumented behaviour; the second documents behaviour nobody implemented, which is the more dangerous half -- it is what made the issue body look specified while it was homeless.

**It runs over ALL entities**, not the one that prompted it: `Thread`, `WorkPackage`, `Criterion`, `AcceptanceTest`, `Attachment`, `Legacy`, `Related`, `Issue`, and the event envelope.

## Design notes for whoever takes it

- **The denominator goes in the output.** `N of N entities checked, M properties` -- a check that silently skipped an entity and a check that found nothing produce the same line otherwise. This thread's standing class.
- **Demonstrate it RED before trusting a green.** Delete a row from a table and watch the right entity fail; add a row for a field that does not exist and watch the other direction fail. A check whose positive case has never been observed is not evidence.
- **Parsing `data-model.md` is the whole difficulty.** The tables are hand-authored markdown with prose between them. The parse must FAIL LOUDLY on a table it cannot read rather than skipping it -- a skipped entity is an unchecked entity reported as checked, which is the defect one level up.
- **Sibling, not an arm of an existing check.** `drift_check.sh` compares generated faces to the Rust types; this compares a prose document to a schema. Different inputs, different failure meanings, and folding them would put two questions behind one exit code.
