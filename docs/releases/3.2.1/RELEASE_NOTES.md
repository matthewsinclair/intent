# Intent v3.2.1

**v3.2.1 answers "what is open?" with one command, lets a node correct what it wrote on a board, and closes a run of places where Intent's own checks passed over work they never examined.** `intent outstanding` lists every open thread, work package and issue in one table, and the explorer shows it as `/outstanding`. `intent wb edit` changes the text of a board item or a sent message, and the change is marked `(edited)`. A board can claim an issue. Around that, this is a release of repairs: a `brew upgrade` no longer leaves every gated commit refused, a fresh clone takes its whiteboard on its first open instead of offering remedies that emptied every board, the pre-commit chain block refuses a commit it cannot gate instead of letting it through in silence, the shell critic reaches a script by its shebang and judges the bytes being committed, and `intent --version` says whether the build is a release. The documentation was re-measured page by page against this release: it gains a guide to the explorer, and the team guide becomes a walkthrough of a team working on GitHub. **Upgrading migrates each project's store to schema 30, and v3.2.0 cannot open it afterwards, so read Upgrading before the first command.**

## Provenance

**These notes were written before the cut, which is the only way they can ship inside it.** Every claim below was verified against the tree the release is being cut from, by reading the code that produces the behaviour, by naming the test arm that holds it, or by reading the closed issue's own landing. A commit message is never the source. Anything ruled but not yet landed is deliberately absent rather than described in advance.

**The section headings follow the CHANGELOG's 3.2.1 section, which is what the release publishes**; this page carries the same entries with the reasoning a reader upgrading needs.

## Added

**`intent outstanding`, alias `intent outs`, shows everything open and in progress in one table** (ST0079). A snapshot of what was open took `intent st list`, `intent issues`, and `intent wp list` once per thread. Now one table carries a row for each thread bare `intent st list` shows, each followed by its work packages in progress, then a row for each issue bare `intent issues` shows, with the kind in the leftmost column. A package in progress under a thread `st list` hides brings that thread in as its parent, so a package is never listed apart from its thread unless `--show` leaves threads out. `--show` takes `st`, `wp`, `is` and `all`, and a closing line counts each kind shown against how many exist, so an empty result reads as none of N. **What counts as open now has one definition**: bare `intent st list` and bare `intent issues` read their defaults from the same place, on the CLI and on MCP, so neither can disagree with `intent outstanding`. It is offered on MCP as a read.

**The explorer's `/outstanding` shows the same table as a view** (ST0079 WP-01), reached by `/outs` too. Its rows are the verb's own, from the same facade call. Enter opens the thread, work package or issue on a row, and Backspace returns to the table. A work package's row now carries its thread and sequence as fields, on MCP as well, so no face has to read them back out of the rendered ID.

**`intent wb edit <kind> <id> <text> --node <moniker>` changes the text of one of your own board items, live or archived** (issue 0523), and `intent wb edit message <anchor> <text> --to <recipient> --node <moniker>` does the same for a message you sent. No verb could change an item's text, so text that must not be committed, such as a client's name, stayed on the board and in the event that recorded it. The edit takes the old text out of the board, and where the event that carried it is not yet committed and the edit can tell which event that was, it amends that event in place. Otherwise a `wb.edit` event records the new text and git history keeps what was committed: rewriting history is the repository's business, never the verb's. **The answer names every file under `intent/` that still holds the old text**, at HEAD and in what the next commit would or could carry, found by reading the repository rather than assumed, and it says no file holds it only when both searches found nothing; in a project with no git it says neither search ran (issue 0545). Like `wb add` and `wb ask`, it is one-way and is not offered on MCP.

**An edited board item or message renders `(edited)`** (issue 0525), at the end of an item's first line, and on a message after `(handled)` in its inbox heading and after the route in `wb show` and `wb pickup`. It says the text changed and never what it said: an edit of an uncommitted draft leaves no trace in the event log by design, so the mark is how a peer who acted on the text can tell. `board.json` carries the stamp as `edited_at`, omitted when there is none, and schema rung 30 adds the column; that rung is the migration Upgrading describes. A restore also updates an edited message in place, keeping its id and so its `#<n>`, where it used to remove and re-add it (issue 0529).

**A board can claim an issue, as `ISSUE:<NNNN>`** (issues 0511 and 0519). `intent wb claim` admitted only a thread or a work package, so two sessions working one issue could not see each other on their boards. The form is the one `intent/.intentfiles` already carries for an open issue; a bare number and free text are refused. `intent issues renumber` now rewrites a board's claim to the issue's new number, as `intent st renumber` does for a thread.

**The pre-commit gate checks staged bytes against the formatters a project declares, and rewrites nothing** (issue 0505). A project that lists `markdown`, `elixir` or `rust` under `formatters` in `intent/.config/config.json` gets a shipped guard that runs each formatter's check over the STAGED bytes of every matching file, and refuses the commit naming the files and the command that formats them; a declared formatter whose tool is missing is reported as unenforced and blocks nothing. Estates had each wired a formatter into their own hook, and a hook that formats the work tree and re-stages it commits bytes nobody staged. `intent/docs/pre-commit-hook.md` describes the declaration.

**`intent bootstrap --check` says where this machine's pre-commit gate resolves and whether it can run, and writes nothing** (issue 0533). It prints the pointer, the root, its state and the gate, and exits 0 when the gate can run and 1 when it cannot, with no project needed. When the pointer names a versioned Homebrew keg, which the next `brew upgrade` deletes, it says so. `intent info` prints the same answer on a new `Gate root:` line.

**A guide to the explorer, [`docs/explorer.md`](../../explorer.md), teaches `intent explore` by task, with screenshots taken from the explorer itself.** It is organised by what you want to do: open it, find and read a thread, change a field, run a command, see what is outstanding, search, keep up with changes made elsewhere, and switch projects. It leaves the keys and commands to the explorer's own `/help`, which is built from the keymap and the command table of the build it runs in, so the page never carries a key table that could fall behind. The generator that takes the screenshots is committed beside the reference generator, so each release re-takes them from the build it ships.

## Changed

**The documentation is re-measured against this release, page by page.** Every claim a page makes about a verb, a flag, a path, an output line or an exit code was checked against the code, and every page that shows commands was run in a scratch project. Where a page and the code disagreed, the page moved to the code. Where the code was wrong, the defect is filed as an issue and the page describes what the build does rather than what it should. `docs/getting-started.md` teaches `intent set` for a thread's objective and context, the route that cannot lose an edit. `docs/concepts/working-in-a-team.md` becomes a walkthrough of a team on GitHub: clones, pull requests under each of GitHub's three merge buttons, the id collisions two clones can make, the whiteboard across clones, and `intent doctor` as a required check. The docs index links the explorer guide and the team guide from Start here.

**Command help and the reference pages say what each command does, without the maintainers' notes.** Over the v3 port, argument notes and help texts had gathered rulings, internal paths and design argument that no reader of `--help` could use. They are rewritten for a reader of `--help`, of `docs/reference` and of the MCP tool descriptions.

**Intent's hooks need `jq`, and `docs/install.md` now says so.** Without it the Claude Code session gate blocks every prompt, `/in-session` included, and the pre-commit gate runs no language critic, which it says on each commit. The requirement is not new; the install page had not said it.

**A correction to the 3.1.0 entry.** It said v3 embeds the rule library in the binary. It does not: Intent reads the library from its install at run time, as `docs/install.md` describes, which is why an install missing the library lists no rules.

## Fixed

**A `brew upgrade` no longer leaves every gated commit refused** (issues 0527 and 0540). `intent bootstrap` recorded the install root it resolved, which on a Homebrew install is the versioned keg, and `brew upgrade` deletes that keg, so the project shim refused every commit in a gated project until `intent bootstrap` ran again. It now records Homebrew's `opt` link, which survives every upgrade. A machine coming from 3.2.0 or earlier still holds the old pointer, and the formula's caveat tells it to run `intent bootstrap` once, whether or not the old keg is still on disk, and names `intent bootstrap --check`.

**A fresh clone takes its whiteboard on its first open, and no remedy empties a board** (issue 0535). A clone's store was filled with every thread and issue and no board, so `intent wb status` said no nodes were registered, and following its remedies, `intent sync --to-disk` or `intent wb migrate` wrote an empty board over every node's `board.json`, each at rc 0. The first open now takes the boards in the same transaction as the threads and issues. Where a store lacks a board that a `board.json` records as migrated, `wb register`, `wb migrate` and `sync --to-disk` refuse before they write anything, and `wb status`, `wb show` and `intent doctor` name `intent sync --to-store`.

**The pre-commit chain block refuses a commit it cannot gate** (issue 0538). The block `intent claude upgrade` writes into each hook ran that hook's carrier when it was executable and otherwise did nothing, so with the carrier absent (it is never committed, so every clone lacks it, and so does every worktree reached through `core.hooksPath`) a commit went ahead with no guard, no critic and no doctor, and nothing said so. The pre-commit block now refuses and names the path and the remedy; the post-merge, post-checkout and post-rewrite blocks say so on stderr, in a checkout that holds an Intent store, and still exit 0, because git has already changed the tree. `intent claude upgrade --apply` now brings an existing block to this form in place, which is why Upgrading asks for it in every project.

**The shell critic reaches a script by its shebang, and a clean verdict counts only the files a rule was asked of** (issue 0536). Each shell rule selects files by its `applies_to` globs, so a script with no extension was asked nothing unless it sat directly inside a directory named `bin`, and the run still counted it and printed `ok`. A file whose shebang names sh, bash or zsh is now tested against each rule's own globs as though it carried that shell's extension, so each rule keeps the dialect it declares. The verdict counts only the files some rule was asked of and names the rest, and where nothing was asked it says so instead of `ok`. A bash library that is sourced rather than run carries no shebang, and it is reached by the `# shellcheck shell=` directive it declares its dialect with, which shellcheck also reads and ranks above a shebang (issue 0544). In Intent's own tree it now reaches every tracked `.githooks/` hook, the shebang scripts under `bin/.devbin/` and the libraries beside them.

**`intent critic --staged` judges the bytes being committed** (issue 0537). It listed the staged paths from the index and read each file from the work tree, so after `git add -p`, or an edit made after staging, the gate judged other bytes: a staged violation under a clean work tree passed, and a clean stage under a dirty work tree was refused. Each staged file is now judged by the blob the index holds for it, and shellcheck reads a copy of that blob under the file's own name. A file renamed and edited in the commit is judged at its new path, where rename detection used to drop it unexamined.

**The gate's other counts say what they counted.** A guard that can tell whether it applies only once it runs is counted as skipped rather than as run (issue 0506), `--list-guards` reports such a guard as `self-classifying` (issue 0515), and the gate's summary line ends with how many critic rules the project has disabled, a count it used to discard whenever the critic passed (issue 0510).

**`intent --version` and `intentd --version` say whether the build is a release or a dev build** (issue 0534). A brew-installed release and a dev-tree build printed the same shape, so telling them apart meant knowing which commit a tag names. The line now ends in `release` for a clean build of a commit tagged `v<version>`, and in `dev` for every other build: `intent 3.2.1 (<sha>) release`. The commit in the parentheses does not move, and neither does anything that reads it.

**A multi-line board item stays one item** (issues 0532 and 0539). A board view printed an item's later lines at column 0, so a sub-bullet read as a sibling item and a fenced block could turn every section below it into code. They are now set in under the item, in the view and under `wb show` and `wb pickup`. A board an older Intent wrote is an uncounted stale render in `intent doctor` until the next write re-renders it, and that re-render is not reported as a lost edit.

**Every refusal that sends someone to register a node prints the whole command** (issues 0522 and 0541): `intent wb register <moniker> --name "<display name>" --role <role>`, with the moniker filled in where one was typed. The bare form, which registers nothing where no hand-authored board header exists, is named only for boards that are still hand-authored. `intent wb register --help` now says what each part is.

**`intent/todo.md` opens with its generator marker again** (issue 0528), v2's `generator: intent todo` frontmatter, byte for byte, so a tool that keeps its own `todo.md` can tell Intent's view apart. Utilz's `todo` rewrote the view without it. A view an older v3 wrote is an advisory stale render in `intent doctor` until `intent todo update` rewrites it.

**The explorer (`intent explore`) shows what changed under it** (issue 0520). It read every view as the model stood when it opened, so another terminal's write, another node's, or intentd's ingest of a hand edit never reached it, and an edit to a record somebody else had changed was refused every time until a restart. It now catches up with the store before it reads, and while nothing is being edited it re-reads the view on screen within half a second of a change once the keys are idle; the search pane re-runs when it is entered, as before. The omnibox follows the store too, so something a `/` command or another node has just made can be found in it by name (issue 0543). Its hint line no longer offers `⏎ edit` on a row where Enter does nothing (issue 0502).

**Closing and dating a thread refuse what they should.** `intent st done --date` and `intent st cancel --date` on a thread already closed answer the stated date instead of dropping it at rc 0 (issue 0503); `intent set <ST> completed` refuses a malformed date and a date on a thread that is not Completed or Cancelled (issue 0504); and a close refused under an empty contract names every step out of it, including satisfying the criterion afterwards, and its `remedy:` line is the refusal's own (issue 0526).

**intentd ingests an edit made outside Intent even when the file events for it are dropped** (issue 0516). Under heavy file activity elsewhere on the volume, a watched project's events could be lost and a hand edit under `intent/` never ingested. A backstop now compares the canon files with what intentd last read every 30 seconds and ingests only what changed.

**`intent sync --to-disk` runs beside an intentd that is watching the project** (issue 0500). It only writes the extract from the store, as every other writing verb does beside the daemon; `sync --to-store`, which replaces the store and would race the daemon's ingest, still refuses.

**Smaller corrections**: `intent wb show --all` and `intent wb pickup --all` mark a handled message's line `(handled)` (issue 0531); `intent wb claim --help` and `intent wb unclaim --help` name the three forms an `<id>` can take (issue 0530); `intent wb migrate` labels its `.history` count as documents carried and names each pre-migration copy it keeps (issue 0499); `intent organize`'s digest of unclaimed paths no longer changes when the project is moved or cloned (issue 0509); the MCP `organize` tool reports project-relative paths (issue 0513); and `intent edit` on an issue's address names `intent issues show` and `intent set ... body --from` (issue 0514).

**A project made by Intent 3.0 is told that git tracks its store, and how to stop it** (issue 0551). Intent 3.0's `init` wrote no `.gitignore`, so a project's first commit took `intent/.cache/intent.db`, and the ignore rule a later run writes does not take it back out of the index. `intent upgrade` now prints the command that does, `git rm --cached intent/.cache/intent.db`, and `intent doctor` reports a tracked store until it is run.

**A pull no longer deletes a teammate's whiteboard message, and a teammate's edit to a thread's Objective or Context survives the pull** (issues 0554, 0556 and 0559). The hooks' pass after a pull rewrote each pulled board file and each edited thread cover from this clone's store, and said nothing. A pulled board the store holds differently is now kept and named, with `intent sync --to-store` to carry it, and board writes refuse until it is carried; a pulled cover edit is taken into the store and the thread named. `intent doctor` names `intent sync --to-store` for a hand edit it can carry. `docs/concepts/working-in-a-team.md` walks through both.

**`intent doctor` says what a broken pre-commit gate does to a commit, and the verb that repairs it** (issue 0570). It said commits were going through ungated and that nothing repaired the gate; most broken states in fact refuse every commit, and `intent claude upgrade --apply` or `intent bootstrap` repairs each one.

**`.intent_critic.yml` is seeded as valid YAML** (issue 0564), **the explorer's `/help`, its address handling and `intent app status` are corrected** (issues 0550, 0552, 0553 and 0560), and **the pull-request workflow no longer runs a pull request's description as code** (issue 0585).

## Upgrading

The order matters, because the first command the new version runs in a project migrates its store.

```
  $ intent backup                  # in each project, still on 3.2.0
  $ intent daemon stop             # or brew services stop intent, if it runs there
  $ brew upgrade matthewsinclair/intent/intent
  $ intent --version
  $ intent bootstrap               # once per machine
  $ intent daemon start            # or brew services start intent, if it ran there
  $ intent claude upgrade --apply  # in each project
```

**The first command in each project migrates its store to schema 30, and v3.2.0 cannot open it afterwards.** Schema rung 30 adds the `edited_at` stamp behind `(edited)` to the whiteboard's item and message tables. A v3.2.0 binary meeting a migrated store refuses it, saying it was written by a newer Intent. No restore verb ships, so the way back is a snapshot from `intent/.backup/db/`, restored by hand, and `intent backup`, run before upgrading, is what makes sure one exists.

**Stop intentd before the upgrade and start it after, through the door that started it.** intentd checks a store's schema when it opens it and not again, so a daemon left running would go on serving a store migrated under it, with the old code, and `brew upgrade` does not restart a service. If intentd runs under `brew services`, use `brew services stop intent` before and `brew services start intent` after: that service keeps its process alive, so it would restart a daemon that `intent daemon stop` had stopped. If it was started with `intent daemon start`, with or without `--at-login`, use `intent daemon stop` and `intent daemon start`: Intent's own login agent does not restart a stopped daemon. `intent daemon status` names the build a running daemon was started from.

**Restart every running Claude Code session once the upgrade is done.** Each session runs an `intent mcp` server started with the old binary, which checks the schema on every open, so once a store migrates, that session's Intent tools refuse with the same newer-Intent message until its MCP server restarts. The CLI works meanwhile, and nothing is written.

**Run `intent bootstrap` once on each machine that ran 3.2.0 or earlier from Homebrew**, whether or not the old keg is still on disk: its pointer names the versioned keg, and every gated commit is refused once `brew cleanup` removes it. `intent bootstrap --check` shows which case a machine is in.

**Put `jq` on `PATH` on every machine that commits.** macOS 15 and later ship it at `/usr/bin/jq`; elsewhere, install it. Without it the Claude Code session gate blocks every prompt and the pre-commit gate runs no language critic. This is not new in 3.2.1, and [`docs/install.md`](../../install.md) now says it.

**Refresh each project with `intent claude upgrade --apply`, and commit what it writes.** It rewrites the chain block in each git hook in place, so a commit in a clone or worktree without the carrier is refused by name rather than let through ungated; a checkout that should gate runs `intent claude upgrade --apply` there to install the carrier. A project that keeps `.claude/settings.json` by hand adds `--skip-settings`, which leaves that file and `.mcp.json` as they are and applies the rest.

**Some views re-render on their next write.** A board or a `todo.md` an older Intent wrote is reported by `intent doctor` as a stale render that blocks no commit, until the next write re-renders it; `intent todo update` rewrites `todo.md` at once.

**A script that matches `intent --version` whole now meets a trailing `release` or `dev`.** Anything reading the version token or the commit in the parentheses reads them as before.

**In a project first made with Intent 3.0, read `intent upgrade`'s output for an `untrack:` line.** If it prints one, run the `git rm --cached` command it names and commit it with the upgrade, so the store leaves the index and stays on disk.
