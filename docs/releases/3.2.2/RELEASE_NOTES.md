# Intent v3.2.2

**v3.2.2 is a patch of repairs, most of them to what happens when two clones of one project meet, and to the checks that tell you something is wrong.** A pull now takes a teammate's whiteboard into the store, two clones that each add a work package to one thread no longer have to choose between them, and a hand edit to a thread's Objective or Context is no longer rendered over by the next write. The search index repairs itself when a refresh leaves it damaged, and says so. The pre-commit gate's shim and `intent bootstrap --check` stop reporting a gate that cannot run as healthy, and the Claude Code session gate no longer blocks every prompt on a machine without `jq`. `intent explore <view>` opens the explorer where you want it. **The store's schema does not change, so v3.2.1 still opens a store v3.2.2 has used; but the gate fixes reach a project only when `intent claude upgrade --apply` runs in it, so read Upgrading.**

## Provenance

**These notes were written before the cut, which is the only way they can ship inside it.** Every claim below was verified against the tree the release is being cut from, by reading the code that produces the behaviour and the test that holds it. A commit message is never the source, and neither is the CHANGELOG's wording: where the two disagreed, this page follows the code. Anything ruled but not yet landed is deliberately absent rather than described in advance.

**The section headings follow the CHANGELOG's 3.2.2 section, which is what the release publishes**; this page carries the same entries with the reasoning a reader upgrading needs.

## Added

**`intent explore <view>` opens the explorer at one of its views**: `threads`, `issues`, `projects`, `outstanding`, `help`, `settings` or `search`. The view opens exactly as typing `/<view>` in the explorer's palette opens it, through the same command. Any unique prefix of a view's name works, so `intent explore outs` and `intent explore thread` both open, and a leading `/` is accepted. A prefix that fits more than one view opens the explorer at its top level and names the views it could mean, eg `` `se` names more than one view: settings, search ``. An `intent://` address or an id still opens what it names, as before, and outside a project the view opens once a project is chosen.

## Changed

**A generated view's footer names Intent's major version alone, `Generated by Intent v3`, and so do the footers of `AGENTS.md` and `CLAUDE.md`.** The full version rewrote every generated file in a project at every patch release, for one character. A thread's or issue's views take the new footer at their next render, which any write to that record, `intent sync --apply` or `intent sync --to-disk` performs; a board takes it at its next write. Until a view is re-rendered, `intent doctor` lists it as a stale render that blocks no commit, reading `rendered by Intent v3.2.1 and this binary renders v3`, and `intent sync --to-disk` clears the list. `intent claude upgrade --apply` rewrites `AGENTS.md` and `CLAUDE.md`, and `intent agents sync` rewrites `AGENTS.md` alone. A script that matched the old footer, version and all, now meets `v3`.

**`intent index rebuild` no longer declares a `--corpus` flag it never took.** The flag was declared from the design and never built, so every `intent doctor` run that was not `--quiet` printed a line saying the flag was withheld pending a decision. The verb rebuilds every corpus, as it always has, and `doctor` no longer prints that line.

## Fixed

**A pull takes a teammate's whiteboard into the store** (issue 0554). In 3.2.1 the hooks' pass after a pull kept every pulled board the store held differently and named it, with `intent sync --to-store` as the step, and board writes refused until someone ran it; that was right for a board both clones had changed and needlessly strict for the ordinary case. The hooks' `intent sync --apply` now carries a pulled board by itself when two things hold: the file on disk moved forward, meaning the board this clone last wrote or read is in the file's recent git history, and this clone's store has not changed that board since. A board both sides moved, and a board put on disk by checking out an older commit, are still left and named, with `intent sync --to-store` as the step. `docs/concepts/working-in-a-team.md` walks through each case.

**Two clones that each add a work package to one thread no longer have to take a side** (issue 0555). Each clone numbered its new package with the next free number, so both minted the same one, and the merge offered only the choice between one clone's thread and the other's. `intent sync --apply` now plans a renumber: this clone's package moves to the next free number, and a board claim on it follows. A thread changed on either side in any way other than adding work packages still takes a side, as before.

**A CLI write no longer renders a thread's cover over a hand edit to its Objective or Context** (issue 0559). A write to a thread renders its `info.md`, and a hand edit to the cover's `## Objective` or `## Context` that the store had not yet taken was replaced without a word. A write whose render would do that now refuses first: `run intent sync --to-store <ID> to carry the edit into the store, then run this verb again -- the file is intact until you do; intent set <ID> objective|context writes either section directly`. A cover `intent st edit` realised is now carried by that command too, so the README's route of typing into the cover keeps what you typed. A hand edit to any other part of the cover is still rendered over, with a warning, because only the Objective and Context round-trip.

**Carrying a hand edit to a thread's cover back into the store no longer folds the thread's body into its Context** (issue 0568). The cover shows the opening text of the thread's body under `## Context`, and `intent sync --to-store` and intentd appended that text to the Context on each carry, so the Context grew by it every time. It is now left where it belongs. An edit to that opening text, which the cover shows but which belongs to the body, is refused by name rather than carried into the wrong field.

**`intent sync --to-store` names a hand edit to a thread's Objective or Context that it carries into the store**, where it used to say it overwrote nothing: the edit replaces what the store held, and the report now says so, per thread.

**A search-index refresh that leaves the source index damaged repairs it in the same write, and says so on its own output; intentd checks the prose index the same way beside each scheduled backup.** On Intent's own store, `intent doctor` found the source half of the search index holding terms for a file version whose row had gone, with FTS5's own check reporting a checksum mismatch, a day after a clean rebuild. The damage was traced to the scoped refresh's delete, which runs under FTS5's `secure-delete` so that a delete leaves no tombstone. **The cause below is a reading of SQLite's source, not a reproduction.** In the SQLite that Intent bundles, 3.53.2, `fts5FlushSecureDelete` looks each deleted term's row up in the index and returns success when the lookup misses, and the delete is then dropped, which leaves that term's entry behind with no row under it. Repeated delete-and-reinsert stress runs on a copy of the damaged store, under both 3.53.2 and 3.54.0, did not reproduce it, so the fault cannot be fixed here, and the repair is Intent's own: after a refresh that deleted a row from the source index, FTS5's check runs in the same write, and if it objects the table is rebuilt before the write commits. The repair is reported, never silent: intentd logs a `note:` line, `intent search` and `intent sync --apply` print it, the explorer's search pane shows it, and the MCP search answer carries it as `repaired`. The sentence names the table and what was found, eg `the search index's src_sections was damaged -- 1 orphaned docid(s) and fts5's own check objecting (orphaned docid(s): 882); it was rebuilt in the write that found it, and fts5's check now passes`. The prose index's check costs several times the source index's, too much to add to every refresh, so intentd runs it beside each scheduled backup instead. Every write to a thread or issue, and every ingest, already rebuilds the prose index whole, so the backup's check covers a project that sits idle between them. `intent doctor`'s search-index finding is unchanged, and a store damaged before the upgrade is repaired once by `intent index rebuild`.

**`intent doctor`'s hook-carrier advisory names the command that clears it**. The pre-commit carrier, `pre-commit.intent` in the project's git hooks directory, is a copy of the installed Intent's gate shim, and `doctor` reported a carrier older than its template by saying nothing re-copies it. `intent claude upgrade --apply --skip-settings` re-copies it, and the advisory now says so. **This is how a project takes the two gate fixes below**: the carrier a project holds is the shim it was last copied from, so until that command runs, its commits go through the older shim.

**`intent bootstrap --check` and the gate shim's `--where` answer `NO GATE`, and exit 1, for an install that has no gate script** (issue 0561). Both reported an install whose gate could not run as OK, because they checked that the install pointer resolved and not that the gate it names was there. They now print `state:    NO GATE (lib/templates/hooks/pre-commit.sh is missing under that root)` and the path they looked for. `intent bootstrap --check` has this as soon as the new binary is installed; the shim's `--where` has it once `intent claude upgrade --apply` re-copies the carrier.

**The pre-commit gate's shim ignores a relative `XDG_DATA_HOME`, as `intent bootstrap` does** (issue 0562), so the two read the same install pointer. With a relative value set, bootstrap wrote the pointer under `~/.local/share` while the shim looked for it relative to the directory the commit ran in. This lives in the shim, so a project has it once its carrier is re-copied.

**`intent bootstrap --check`'s divergence note names where each part of the gate comes from** (issue 0571). When the install pointer names a different install from the running binary, the note now says that the gate body comes from the pointer's install, while the guard runner and its roster come from the `intent` a commit runs, which `intent info` shows as `INTENT_HOME:`. `intent claude upgrade` prints the same note.

**The Claude Code session gate no longer blocks every prompt, `/in-session` included, when `jq` is not on `PATH`** (issue 0563). The gate read the prompt with `jq`, so without it no prompt looked like a slash command and `/in-session`, the one prompt that releases the gate, was blocked with the rest. It now reads whether the prompt opens with `/` from the raw payload, and when it blocks a plain prompt it says `jq` is missing and what else goes without it. The hook's script is served from the installed Intent, so every project has this as soon as Intent is upgraded.

**The Stop hook's `/in-finish` reminder is a `systemMessage`** (issue 0576), which Claude Code documents as shown in the transcript, rather than plain stdout, which Claude Code does not document as reaching anyone for a Stop hook. It is served from the install, like the session gate.

**The hook timeouts in the Claude Code settings template are in seconds, as Claude Code reads them** (issue 0577). The template's three hooks carried 3000 and 2000, which Claude Code read as 50 and 33 minutes; each is now 30. A project's `.claude/settings.json` takes the template only at `intent claude upgrade --apply`, only when the file is one Intent wrote, and never under `--skip-settings`, which leaves it as it is.

**The opt-in PostToolUse critic advisory speaks only when the critic reports findings or refuses** (issue 0578). It handed the model a clean run's census after every edit; it now keys on the critic's exit status and stays silent on a clean one. It remains opt-in: it runs only for a project that sets `post_tool_use_advisory: true` in `.intent_critic.yml` and wires the hook itself.

**`intent critic` no longer reports a rule as not asked when its tool declined only some of the run's files** (issue 0581). shellcheck declines a `.zsh` file, and one such file beside `.sh` files took every shellcheck-armed rule out of the census, so a run could headline `0 of 6 rule(s) ASKED` over the findings those rules had just reported. A rule the tool ran on any file is now counted as asked. The declined files are still named, and each JSON census row gains `declined`. A rule the tool declined on every file it reaches is still reported as not run.

**`intent claude rules validate` refuses a rule library whose principle links disagree** (issue 0584). A rule's `references:`, the principle's `concretised_by:` and the rule's `principles:` must name each other, and each disagreement is an error reported on the file to edit. Reviewing the links this found, the ones whose rule bodies did not argue the principle were dropped from all three fields: IN-RS-TEST-003, IN-SW-CODE-004 and IN-LU-CODE-003 from Highlander, and IN-RS-CODE-005 from PFIC.

**`intent claude rules validate` no longer reports a false duplicate id when a canon rule is named by a relative path** (issue 0575), and its help says what it checks: frontmatter keys, ids, citations and principle links (issue 0583).

**The critic subagents read a rule's status and skip a draft or deprecated rule** (issue 0582), naming each one they skipped at the top of their report. The subagents are installed per machine, so they take this at `intent claude subagents sync`.

**The staged-format guard reports a file its Elixir or Markdown formatter cannot parse as not checked, rather than as not formatted** (issue 0572). A syntax error made the formatter fail, and the guard refused the commit saying the file was not formatted, which sent the author to run a formatter that could not run. It now prints the file under `could not be checked (NOT a formatting verdict)` with the formatter's first error line; such a file blocks nothing and is left out of the count of files checked.

**`intent doctor`'s stale-render advisory names the command that clears each view.** `intent sync --to-disk` re-renders a view `.intentfiles` realises, and `intent sync --apply` removes one it does not, while the store keeps the record. `doctor -v` lists a directory's run of stale views on one line naming every file, rather than one line per view.

**`intent at edit --kind` says when it resets a row's status** (issue 0580). A status the new kind cannot hold is reset to that kind's entry state, as before, but the verb now prints a `note:` naming the row, the status it dropped and the one it set, and that `intent at green`, `red` or `na` records a verdict the row's kind can hold. Its help says so too.

**`intent init --lang` writes an `AGENTS.md` that names the languages it declared** (issue 0557). `init` rendered `AGENTS.md` before it wrote the languages into the config, so a project made with `--lang` started with an agent contract saying no languages were declared. An existing project brings its `AGENTS.md` up to date with `intent agents sync`.

**`intent init` says why it did not write each template it skipped** (issue 0558), one line per template, rather than pointing at `--help`.

**`intent claude upgrade` reports a seed identical to its template as `unchanged` rather than `preserved`** (issue 0565). `preserved` means the file is yours and differs from canon's, which was untrue of a seed nobody had touched.

**The note a fiat close prints names `st done --keep` and `st cancel --keep`** (issue 0566), rather than a bare `--keep`, which `intent fc` refuses. The header `intent organize --default` writes into a new `.intentfiles` now names `fc` among the verbs that unlist a thread; an existing `.intentfiles` keeps its header.

**`intent upgrade`'s clean-tree check lists only files whose content changed.** Before a v2 project's migration, the check refuses while the tree has uncommitted work, and it listed every file whose stat data had changed, so a tree `git status` called clean could be refused over files nobody had edited. It now compares content and still lists untracked files.

**For a project older than v2.10, `intent upgrade`'s remedy names the v2.11.14 hop it may need.** The route is v2.19.0's `intent upgrade`, then v3's, and v2.19.0 refuses a project below v2.9.0; the remedy now says that such a project goes to v2.11.14 first.

**`intent ac edit --note` on a computed criterion names the route that reaches a note.** A computed criterion takes its state from its covering tests and carries no note, and the refusal sent the author to verbs that do not apply to it. It now names `intent set <address> kind non-test`, which makes it a criterion that carries one.

**Migrating from v2 no longer refiles the first line of v2's acceptance preamble into the thread's cover.** A migration keeps any line of an acceptance file's preamble that an author wrote, moving it into the thread's `preamble` on the cover, and drops the lines v2 wrote itself. The comparison was pinned to a template that was not v2's and did not put the thread's own id into it, so v2's first line was kept as though authored. Two later lines of v2's preamble, which carry identifiers of Intent's own project, are still kept and reported under `sections not carried as-is`; delete them from the cover if they appear.

**`intent todo` and `intent todo list` are declared reads, and `intent export` a reversible write** (issue 0573), so their descriptions on MCP and in the reference say what they do: the todo views never write `intent/todo.md`, which only `intent todo update` writes, and `intent export --format md` writes files under `intent/.backup/text/`. Which verbs MCP offers does not change.

**A search answer caps its stale-resolution list and says how many more there are** (issue 0549). The JSON and MCP answers listed every file whose level-3 resolution had gone stale, however many; each language's list now names the first few in path order, with a `stale_total`, and the words read `stale: <files> and <N> more -- intent index status lists them all`.

**The reference no longer lists the live `help` and `organize` among the retired commands.** Both were retired in their v2 meaning and both are live v3 commands, and the reference's table of retired commands carried them as though they did not exist.

**The subagents' instructions match the tool.** critic-shell decides a file's dialect in the order the headless critic uses, a rule's glob, then a `# shellcheck shell=` directive, then the shebang, where it treated a file with no shebang as bash. critic-prose finds the trope catalogue where an installed Intent keeps it. The intent agent says what `intent st done` refuses and no longer sends a reader to an `intent/docs/` that `init` does not create. The language critics hand diogenes the module a test file tests. These arrive with `intent claude subagents sync`.

## Upgrading

```
  $ intent daemon stop             # or brew services stop intent, if it runs there
  $ brew upgrade matthewsinclair/intent/intent
  $ intent --version
  $ intent daemon start            # or brew services start intent, if it ran there
  $ intent claude upgrade --apply  # in each project
  $ intent claude subagents sync   # once per machine
```

**No store migrates.** The schema stays at 30, so v3.2.1 still opens a store v3.2.2 has used, and going back needs no restore.

**Run `intent claude upgrade --apply` in each project, and commit what it writes.** It re-copies the pre-commit carrier from the new install, which is the only way a project takes the gate fixes to `--where` (issue 0561) and to a relative `XDG_DATA_HOME` (issue 0562); until it runs, `intent doctor -v` reports the carrier as behind its template, and `intent claude upgrade --apply --skip-settings` is the command that advisory names. It also rewrites `AGENTS.md` and `CLAUDE.md` with the new footer and, unless you pass `--skip-settings`, brings a `.claude/settings.json` Intent wrote to the corrected hook timeouts. A project that keeps `.claude/settings.json` by hand passes `--skip-settings`, which leaves that file and `.mcp.json` as they are and applies the rest, the carrier included.

**Stop intentd before the upgrade and start it after, through the door that started it.** `brew upgrade` does not restart a running daemon, and a daemon left running goes on with the old code, so it neither takes a pulled board, nor repairs the search index, nor checks the prose index beside its backups. If intentd runs under `brew services`, use `brew services stop intent` and `brew services start intent`; if it was started with `intent daemon start`, with or without `--at-login`, use `intent daemon stop` and `intent daemon start`. `intent daemon status` names the build a running daemon was started from.

**Run `intent claude subagents sync` once on each machine** for the critic subagents that skip draft and deprecated rules and the corrected instructions. A subagent you edited is held rather than overwritten, and `--force` replaces it, reporting the checksum of what it discarded.

**Restart running Claude Code sessions to give their Intent tools the new build.** Each session's `intent mcp` server was started with the old binary. Nothing refuses meanwhile, since no schema changed; the session's tools simply run 3.2.1's code until the session restarts.

**If `intent doctor` reports the search index damaged, run `intent index rebuild` once.** A store damaged before this release is repaired by the rebuild, and from then on a refresh that leaves the source index damaged repairs it itself and says so.

**Some views re-render on their next write.** Every view carries the new major-only footer from its next render, and `intent doctor` lists the ones not yet re-rendered as stale renders that block no commit; `intent sync --to-disk` re-renders them at once.
